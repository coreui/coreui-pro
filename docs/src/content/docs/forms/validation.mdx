## How it works

Here's how form validation works with Bootstrap:

- **Client-side validation** uses CSS pseudo-classes scoped behind the `data-coreui-validate` attribute. Add `data-coreui-validate` to your `<form>` to opt in to `:user-invalid` styling—validation styles only appear **after the user interacts** with a control (e.g., typing and blurring, or attempting to submit), so required fields don't show up as invalid on page load.
- By default, **client-side validation only shows invalid styling.** To also show success styling for valid fields, set `data-coreui-validate="valid"`.
- **Server-side validation** uses the `.is-invalid` and `.is-valid` classes to indicate field state without requiring user interaction. These work globally—no `data-coreui-validate` attribute needed.
- Custom validation states beyond `valid`/`invalid` (e.g., `warning`) are supported via the `.is-*` class pattern and the `$form-validation-states` Sass map. There are no generated pseudo-classes for custom states.
- With `novalidate` as well, the [form plugin](#usage) handles the submit: it stops an invalid form, marks its invalid controls with `.is-invalid` and `aria-invalid="true"`, links the message of each to it with `aria-describedby` and moves focus to the first.
- Feedback shows when it follows the control. For a check, a radio, a switch, a `.form-control` or `.form-select` in an input group, or a control placed directly in a component frame, it can sit anywhere in the [`.form-field`](/forms/field/) around the control.
- All modern browsers support the [constraint validation API](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#the-constraint-validation-api), a series of JavaScript methods for validating form controls.
- Feedback messages may utilize the [browser defaults](#browser-defaults) (different for each browser, and unstylable via CSS) or our custom feedback styles with additional HTML and CSS.
- You may provide custom validity messages with `setCustomValidity` in JavaScript.

With that in mind, consider the following demos for our custom form validation styles, optional server-side classes, and browser defaults.

## Custom styles

For custom CoreUI for Bootstrap form validation messages, add `data-coreui-validate` and the `novalidate` boolean attribute to your `<form>`. The examples on this page use `data-coreui-validate="valid"`, so the fields that pass show their success message too. The `data-coreui-validate` attribute opts in to the `:user-invalid` styling, while `novalidate` disables the browser default feedback tooltips and hands their job to the [form plugin](#usage). Try to submit the form below.

When the form is submitted with an invalid control, the plugin stops the submit before your own `submit` handlers run, so they see `event.defaultPrevented`. It marks every invalid control with `.is-invalid` and `aria-invalid="true"`, and adds the message the stylesheet shows for it to its `aria-describedby` while it stays invalid, so a screen reader reads the error with the field. Then it moves focus to the first invalid control, as the browser does. Under `data-coreui-validate="valid"` the valid controls get `.is-valid`. The state follows the corrections the user makes until the form is reset. The message can follow the control, its frame or an element around it that carries `.is-invalid`, or sit in the `.form-field` around a check, a radio, a switch, an input group or a frame. A message placed where the stylesheet does not show it for the control can be named in `data-coreui-invalid-feedback` on the control, and a message with the `hidden` attribute is left out, so a field can keep one message per kind of error and show the one that applies. A [multi select](/forms/multi-select/#validation), a [chip input](/forms/chip-input/#validation), a [combobox](/forms/combobox/#validation), an [OTP input](/forms/otp-input/#validation), a [date input](/forms/date-input/#validation), a time input and the pickers built on them show the state themselves, on their frame and on what takes the focus, and the plugin leaves the hidden field that carries their value to them; an [autocomplete](/forms/autocomplete/#validation) does the same with its input, a [range slider](/forms/range-slider/#validation) with its handles, and a [rating](/forms/rating/#validation) with its radios; a date or time field, a chip input, an OTP input, an autocomplete, a range slider and a rating read `data-coreui-invalid-feedback` from their own element, and a combobox from its toggle.

Custom feedback styles apply custom colors, borders and focus styles to communicate feedback.

## Server side

We recommend using client-side validation, but in case you require server-side validation, you can indicate invalid and valid form fields with `.is-invalid` and `.is-valid`. Note that `.invalid-feedback` is also supported with these classes.

For invalid fields, ensure that the invalid feedback/error message is associated with the relevant form field using `aria-describedby` (noting that this attribute allows more than one `id` to be referenced, in case the field already points to additional form text).

In a form the [form plugin](#usage) validates, a `.is-invalid` or `.is-valid` you set on a control stays: the plugin leaves that control's classes to you until you remove yours, and only adds and removes its own.

For a validated input group, wrap the group in a [`.form-field`](/forms/field/) and place the feedback outside the group, so it renders under the whole frame.

## Form components

A [multi select](/forms/multi-select/#validation), a [chip input](/forms/chip-input/#validation), a [combobox](/forms/combobox/#validation), an [OTP input](/forms/otp-input/#validation), a [date input](/forms/date-input/#validation), a [time input](/forms/time-input/#validation) and the pickers built on them keep their value in a native field laid invisibly over the component. That field carries the `name`, takes part in the browser's validation and hands the focus to the component when the browser points at it. An [autocomplete](/forms/autocomplete/#validation) validates its own input, a [range slider](/forms/range-slider/#validation) its handles, and a [rating](/forms/rating/#validation) its radios. Each of these components shows one validation state, on its frame and on what takes the focus, and decides it in this order:

1. its own error, such as a date outside `minDate` and `maxDate` or an incomplete code;
2. the state you give it;
3. the state a validation reports for its field: a submit, the [form plugin](#usage), the [stepper](/forms/stepper/#form-validation), or your own `checkValidity()` or `reportValidity()` call;
4. `:user-invalid` or `:user-valid` of its field, in a form with `data-coreui-validate`.

Give a state with the `validationState` option (`data-coreui-validation-state`), or with `.is-invalid` or `.is-valid` on the component's element in the HTML the server renders. The autocomplete, the multi select and the pickers also take the deprecated `invalid` and `valid` options. The class is read once, when the component starts; after that, set the state with `setValidationState('invalid')`, since a class or an `aria-invalid` written on the element later is not read. Put the message on the page before you set the state, or call `setValidationState()` once it is there: a message added later, with no change of state, is not linked to the field.

A given state only shows: the state class and, for `'invalid'`, `aria-invalid` and the linked message, which a screen reader reads when the user reaches the field. It does not stop the submit or the [stepper](/forms/stepper/#form-validation)'s next step, since the browser checks only the constraints of the field that carries the value: a valid value is submitted under a given `'invalid'`, and an empty `required` field keeps blocking under a given `'valid'`, which shows over the reported error. A given state stays until you change it: the user's changes of the value, a native form reset and the methods of the component keep it. Clear it with `setValidationState(null)` once your verdict no longer holds, for example in a `reset` listener on the form, or in the change event of the component, which every change the user makes fires, apart from typing with no option selected in an autocomplete, which fires only `input.coreui.autocomplete` (its [recipe](/forms/autocomplete/#validation) clears the state once the text changes). The component then shows the state of the value at once. The change event also fires on a native reset and on the methods of the component that change the value, as the page of each component lists, so a listener there clears the state on them as well.

```js
const element = document.getElementById('country')
const multiSelect = coreui.MultiSelect.getOrCreateInstance(element)

multiSelect.setValidationState('invalid')

element.addEventListener('change.coreui.multi-select', () => {
  multiSelect.setValidationState(null)
})
```

You can bring your own validation in three ways:

- **Your own rules next to the browser's.** To stop the submit on your own verdict, call `setCustomValidity()` on the field that carries the value, and clear it with `setCustomValidity('')` once the verdict no longer holds, since nothing else removes it. You reach the field through `form.elements`: `form.elements[name]` for a component with one value field, the start and the end of a range by their names, and `form.elements['<name>-0']` for the first handle of a range slider. On a [rating](/forms/rating/#validation), use the radio that takes the focus: the checked one, or the first one while none is checked. Clear or move the validity in an `input` listener you add to the form with `{ capture: true }`: the components send `input` from that field when the user changes the value, apart from the two cases below, and a listener in the capture phase runs before the component reads the field, so the submit passes and the component drops the error at once. An autocomplete changes its input without `input` when the user picks an option or uses the cleaner, or when it empties the field on <kbd>Escape</kbd> or on leaving it with `allowOnlyDefinedOptions`, so listen to its `change.coreui.autocomplete` and `input.coreui.autocomplete` as well; a rating with `allowClear` takes the star off with only `change.coreui.rating`. After those events the autocomplete or the rating can keep showing the error until the user changes the value again or the focus leaves it. To stop a [stepper](/forms/stepper/#form-validation) step, set the validity in a `stepValidationComplete.coreui.stepper` listener: it counts for that validation. A field the user cannot reach, such as one in a hidden tab or a collapsed section, still blocks while the browser has nowhere to show its message, so clear the validity of a field you hide. Give a state as well when the component should show your verdict before a validation runs. A given state and a validity you set are cleared the same way, by you, so clear both in the same listener.
- **Taking the whole result over.** Call `preventDefault()` on `validate.coreui.form` and keep `event.isValid`, as [handling the result yourself](#handling-the-result-yourself) shows. No field is reported then, so the components show only `:user-invalid` or `:user-valid` of their field, as a plain field in the same form does after a submit attempt.
- **Showing the errors.** A `checkValidity()` or `reportValidity()` call reports every invalid field and each component marks itself, so make that call only when the page shows the errors.

The component links and shows its invalid feedback, the `.invalid-feedback` after it or the elements named in `data-coreui-invalid-feedback`, and never the text you pass to `setCustomValidity()`. The browser shows that text only in its own message bubble, which a form with `novalidate` does not show, and the [form plugin](#usage) and the stepper read it out only for a field without invalid feedback, when the focus stays where it is or no field can take it. Keep the feedback element next to the component.

Nothing announces a given state or a refused submit by itself. When the browser or the form plugin refuses a submit, the focus moves to the first invalid field, and a screen reader reads its message there. A page that refuses a submit in its own handler should do the same: call `form.elements[name].focus()`, which every component hands to the element the user works in (a section of a date field, the toggle of a combobox, a chip, a slot of an OTP input, the search of a multi select), or tell the user why with [`announce()`](/accessibility/screen-readers/#announcing-messages). A component without a `name`, or a chip input built with `create: false`, has no field in `form.elements`; focus the element the user works in instead.

## Usage

### Via data attributes

A form with both `data-coreui-validate` and `novalidate` is validated on submit with no code of your own:

```html
<form data-coreui-validate novalidate>
  <input class="form-control" id="email" type="email" required>
  <div class="invalid-feedback">Enter an email address.</div>
</form>
```

Without `novalidate` the browser validates the form itself, and without `data-coreui-validate` the plugin leaves the form alone.

### Via JavaScript

Validate a form without submitting it, for example before saving a draft:

```js
const form = coreui.Form.getOrCreateInstance('#signupForm')

if (form.validate()) {
  saveDraft()
}
```

### Handling the result yourself

Every validation triggers `validate.coreui.form` first, with `event.isValid` telling whether every control passed. A validity the handler sets with `setCustomValidity()`, for example when two passwords differ, counts for the rest of the validation. A submit from a button with `formnovalidate` is not validated, as with the browser's own validation. A handler that moves focus, for example to an error summary, keeps it there; the plugin still marks the controls and stops an invalid submit. A handler that calls `preventDefault()` takes the whole result over: the plugin then neither stops the submit, nor marks the controls, nor moves focus, so stop an invalid submit in your own `submit` handler. Keep `event.isValid` for that rather than calling `checkValidity()`: the call reports every invalid control again, and the components that follow those reports, such as the multi select or the date fields, then show their error.

```js
const form = document.getElementById('signupForm')
let isValid = true

form.addEventListener('validate.coreui.form', event => {
  event.preventDefault()
  isValid = event.isValid
  showErrorSummary(form, isValid)
})

form.addEventListener('submit', event => {
  if (!isValid) {
    event.preventDefault()
  }
})
```

### Methods

| Method | Description |
| --- | --- |
| `dispose()` | Removes the validation state the plugin added and destroys the instance. |
| `getInstance(element)` | Retrieves the Form instance of a `<form>` element. |
| `getOrCreateInstance(element)` | Retrieves the Form instance of a `<form>` element, or creates one. |
| `reset()` | Removes the classes, `aria-invalid` and `aria-describedby` ids the plugin added and stops following the user's corrections. Resetting the form does the same. A multi select, a chip input, a combobox, an OTP input, a date or time field and the pickers keep showing an error a validation reported until their value is valid or the form is reset. |
| `validate()` | Validates the form as a submit does, including the focus move, and returns whether it is valid. |

### Events

| Event | Description |
| --- | --- |
| `validate.coreui.form` | Fired when the form is validated, on submit or by `validate()`, before the plugin shows the result. `event.isValid` tells whether every control passed; `preventDefault()` leaves the result to you. |

## Accessibility

With the form plugin (`data-coreui-validate` on a form with `novalidate`), a failed submit:

- sets `aria-invalid="true"` on every invalid control and adds the `id` of its invalid feedback to its `aria-describedby`, keeping the ids the page set; the next validation takes both off a control that is valid again;
- moves focus to the first invalid control that can take it. When focus is already there, or no invalid control can take focus, its message is announced in the page's live region instead.

With the browser's own validation (no `novalidate`), the browser shows and reads its own messages. For server-side feedback (`.is-invalid` in the markup), associate the message with the field through `aria-describedby` yourself, as described in [Server side](#server-side).
