## Overview

The CoreUI **Bootstrap Chip Input component** lets users enter multiple values as chips inside a single field. Use it as a tag input, multi-value selector, or token field for skills, categories, email recipients, and more. The chip input component supports keyboard-friendly entry and chip removal. To let the user choose from a fixed list instead, use [Chip filter](/forms/chip-filter/).

- Type values and press `Enter` (or a separator) to create chips.
- Text stays in the field until a chip is made from it, so a duplicate, a value past `maxChips` or one the page refuses can be corrected.
- Chips can be removed with their button, <kbd>Backspace</kbd> or <kbd>Delete</kbd>.
- The input stays inline and grows as you type.
- Full form integration through a hidden field with a configurable `name`, which the browser validates like any field.

The chip input is built on top of the [Chip set](/components/chip-set/) component, so it inherits the same roving focus and keyboard navigation between chips.

## When to use Chip Input

Use the Bootstrap Chip Input component when you need:

- A **tag input** or **token field** for free-form multi-value entry
- An **email or recipient input** where users add multiple addresses
- A **skills or category selector** in forms

## Validation

The chip input carries its chips in a hidden `<textarea>` the browser validates, so `required` blocks the submit of an empty field and the browser shows its message over the chip input. The state shows on the frame and on the text field, and the message that follows the frame is linked to the text field, the way the [form plugin](/forms/validation/) does for a native field.

<Example code={`<form class="row g-4" data-coreui-validate novalidate>
    <div class="col-12">
      <div class="chip-input" data-coreui-chip-input data-coreui-name="topics" data-coreui-required="true" data-coreui-placeholder="Add a topic...">
        <label class="chip-input-label">Topics</label>
      </div>
      <div class="invalid-feedback">Add at least one topic.</div>
    </div>
    <div class="col-12">
      <button class="btn btn-primary" type="submit">Submit</button>
    </div>
  </form>`} />

The state comes from three places, in this order:

- The `validationState` option: `'valid'`, `'invalid'` or a state you added to `$form-validation-states`. In the markup, for example from a server that has already checked the value, set it with `data-coreui-validation-state`.
- A validation that reports the field invalid: a submit, `checkValidity()` or `reportValidity()`, which the form plugin and the [stepper](/forms/stepper/) call as well. From then on the chip input shows it invalid whenever its value is invalid, until a native reset of the form. This holds in a form with `data-coreui-validate`, in a form the form plugin validated, in a form with `novalidate` the stepper validated, and outside a form; in any other form the chip input shows what a native field shows after a blocked submit, the browser's message and the focus, see [Form components](/forms/validation/#form-components).
- In a form with `data-coreui-validate`, the `:user-invalid` state of the hidden field, and with `data-coreui-validate="valid"` also its `:user-valid` state.

A state you give stays until you change it: the user's changes of the chips, a native form reset and your own code with `add()`, `remove()` or `clear()` keep it. Every change of the chips fires `change.coreui.chip-input`: a value confirmed with <kbd>Enter</kbd>, a separator or by leaving the text field, a paste, or a chip removed with its button, <kbd>Backspace</kbd> or <kbd>Delete</kbd>. To clear the state when the user changes the chips, call `setValidationState(null)` in a `change.coreui.chip-input` listener. A listener there also clears the state on a native form reset and on `add()`, `remove()` and `clear()`, which fire `change.coreui.chip-input` when they change the chips. To change it, call `setValidationState()`: it updates the state without rebuilding the field. A `.is-invalid` or `.is-valid` class or an `aria-invalid` written on the chip input is not read; the class stays yours and paints the frame without giving the text field `aria-invalid` or a linked message, see [Form components](/forms/validation/#form-components). A message placed where the stylesheet does not show it for the chip input can be named in `data-coreui-invalid-feedback` on the chip input. A given state does not block the submit; to stop it on your own verdict, call `setCustomValidity()` on the field that carries the chips, `form.elements[name]`, as [Form components](/forms/validation/#form-components) shows. A native reset of the form puts back the chips the field started with, the same elements, and keeps the state.

<Example code={`<div class="chip-input" data-coreui-chip-input data-coreui-name="recipients" data-coreui-validation-state="invalid">
    <label class="chip-input-label">Recipients</label>
    <span class="chip">ana@example.com</span>
    <span class="chip">bob@example</span>
  </div>
  <div class="invalid-feedback">bob@example is not a full address.</div>`} />

In the controlled mode (`create: false`) there is no hidden field: a given state shows on the frame and the text field, and `required` is left to the component that owns the value.

## Disabled

Set disabled state on the component to make the input and managed chips non-interactive.
Use the `data-coreui-disabled="true"` option. A single chip is disabled with `data-coreui-disabled="true"` on the chip.
For disabled, non-removable chips, combine it with `data-coreui-removable="false"`.

<Example code={`<div class="chip-input" data-coreui-chip-input data-coreui-disabled="true" data-coreui-removable="false" data-coreui-placeholder="Input disabled">
    <span class="chip">Read only</span>
    <span class="chip">Locked</span>
  </div>`} />

## Readonly

Use readonly state when chips should stay visible, but values must not change. Read-only chips take no focus; the text field stays focusable.
Set `data-coreui-readonly="true"` (or `readonly: true` in JavaScript) to block adding and removing chips.

<Example code={`<div class="chip-input" data-coreui-chip-input data-coreui-readonly="true" data-coreui-placeholder="Read-only values">
    <span class="chip">JavaScript</span>
    <span class="chip">TypeScript</span>
  </div>`} />

## Usage

Initialize the Bootstrap Chip Input component via data attributes or JavaScript. The component creates a hidden `<textarea>` for the chip values; give it a `name` and the chips are submitted with the form.

### Via data attributes

Add `data-coreui-chip-input` to initialize the chip input component. Options can be passed as `data-coreui-*` attributes.

```html
<div class="chip-input" data-coreui-chip-input data-coreui-name="skills" data-coreui-placeholder="Add tags..." data-coreui-separator=","></div>
```

When initialized, Chip Input creates a hidden `<textarea>` for the chip values. It is submitted only
once you give it a name through `name` (or `data-coreui-name`).

### Via JavaScript

```js
const chipInputElement = document.querySelector('.chip-input')
const chipInput = coreui.ChipInput.getOrCreateInstance(chipInputElement, {
  separator: ',',
  maxChips: 5
})
```

### Options

Options can be passed using data attributes or JavaScript. To do this, append an option name to `data-coreui-`, such as `data-coreui-animation="{value}"`. Remember to convert the case of the option name from "_camelCase_" to "_kebab-case_" when using data attributes. For instance, you should write `data-coreui-custom-class="beautifier"` rather than `data-coreui-customClass="beautifier"`.

Starting with CoreUI 4.2.6, all components support an **experimental** reserved data attribute named `data-coreui-config`, which can contain simple component configurations as a JSON string. If an element has attributes `data-coreui-config='{"delay":50, "title":689}'` and `data-coreui-title="Custom Title"`, then the final value for `title` will be `Custom Title`, as the standard data attributes will take precedence over values specified in `data-coreui-config`. Moreover, existing data attributes can also hold JSON values like `data-coreui-delay='{"show":50, "hide":250}'`.

| Name | Type | Default | Description |
| --- | --- | --- | --- |
| `ariaAddedAnnouncement` | string, function | `'added'` | Wording appended to the values of the added chips when their addition is announced. A function receives the added values and returns the whole message. |
| `ariaRemoveLabel` | string \| function | `'Remove'` | Names each chip's remove button with the chip's label: a string has `{label}` replaced by it, or gets it appended when there is no `{label}` (`Remove React`); a function receives the label and returns the whole name. |
| `ariaRemovedAnnouncement` | string, function | `'removed'` | Wording appended to the values of the removed chips when their removal is announced. A function receives the removed values and returns the whole message. |
| `chipClassName` | string \| function \| null | `null` | Adds classes to chips. Use a string for all chips or a function `(value) => className` for per-chip styling. |
| `create` | boolean | `true` | Turns typed text into chips. Set to `false` for the controlled mode: chips come only from `add()` — a host component's selection, say — typing never creates one, and no hidden field is rendered (the host owns the value). |
| `createOnBlur` | boolean | `true` | Create chips from the input value when the input loses focus; a piece no chip comes from stays. |
| `disabled` | boolean | `false` | Disables the input and marks managed chips as non-interactive. |
| `id` | string \| null | auto-generated | Custom id for the generated hidden field. |
| `maxChips` | number \| null | `null` | Maximum number of chips allowed. `null` for unlimited. |
| `name` | string \| null | `null` | Name for the generated hidden field, which is what carries the chips into a form submission. Without a name that field is not submitted. |
| `placeholder` | string | `''` | Placeholder text for dynamically created inputs. |
| `readonly` | boolean | `false` | Prevents adding and removing chips while keeping input focus behavior. |
| `removable` | boolean | `true` | Add remove buttons to created chips. |
| `removeIcon` | string | SVG | HTML string for the remove button icon. |
| `required` | boolean | `false` | Makes the hidden field required, so an empty chip input blocks the submit, and marks the text field `aria-required`. See [Validation](#validation). |
| `separator` | string \| null | `','` | Character that triggers chip creation when typed. Set to `null` to disable. |
| `typeahead` | boolean | `true` | Moves focus to the chip whose value starts with the typed characters. |
| `unique` | boolean | `true` | Refuses a chip whose value the field already holds. A Chip Input turns this on, where a bare [Chip Set](/components/chip-set/) leaves it off. |
| `validationState` | string \| null | `null` | The state the chip input shows: `'valid'`, `'invalid'` or a state of `$form-validation-states`. `'invalid'` does not block the submit. It stays until you change it. See [Validation](#validation). |

### Methods

| Method | Description |
| --- | --- |
| `add(value)` | Adds a chip with the given value. Returns the chip element or `null` if rejected. |
| `clear()` | Removes all chips. |
| `dispose()` | Destroys the component instance and the chip instances it created, and removes the fields it built. The chips stay in the document. |
| `focus()` | Focuses the ghost input. |
| `getInstance(element)` | Static method that returns the instance associated with a DOM element, or `null`. |
| `getOrCreateInstance(element, config)` | Static method that returns the instance associated with a DOM element, creating it when there is none. |
| `getValues()` | Returns an array of all chip values. |
| `remove(chipOrValue)` | Removes a chip by element reference or value string. When the chip had focus, focus moves to the next chip, else the previous one, else the text field. Returns `true` if removed. |
| `setValidationState(state)` | Gives the field a validation state (`'valid'`, `'invalid'` or a state added to `$form-validation-states`), or drops it with `null`. The value stays. See [Validation](#validation). |

```js
const chipInputElement = document.querySelector('.chip-input')
const chipInput = coreui.ChipInput.getOrCreateInstance(chipInputElement)

chipInput.add('JavaScript')
chipInput.add('TypeScript')

// eslint-disable-next-line no-console
console.log(chipInput.getValues())

chipInput.remove('JavaScript')
chipInput.clear()
```

### Events

| Event | Description |
| --- | --- |
| `add.coreui.chip-input` | Fired before a chip is added. Call `event.preventDefault()` to cancel; a value then stays in the field, whether confirmed with <kbd>Enter</kbd>, by leaving the field, with a separator or in a paste, as it does when `maxChips` or `unique` turns the value down. |
| `change.coreui.chip-input` | Fired after any chip is added or removed; `event.value` is the array of chip values. `clear()` fires it once, after the last chip is gone and only when the chips changed, and the value field sends one native `input` and `change` when its value changed, while `remove.coreui.chip-input` still fires for every chip. |
| `input.coreui.chip-input` | Fired when the inline input value changes; `event.value` is the typed text, not the chips. Contains `relatedTarget`. |
| `remove.coreui.chip-input` | Fired before a chip is removed. Call `event.preventDefault()` to cancel. |

```js
const chipInputElement = document.querySelector('.chip-input')

chipInputElement.addEventListener('add.coreui.chip-input', event => {
  if (event.value.length < 2) {
    event.preventDefault()
  }
})

chipInputElement.addEventListener('input.coreui.chip-input', event => {
  // eslint-disable-next-line no-console
  console.log('Input value:', event.value)
})

chipInputElement.addEventListener('change.coreui.chip-input', event => {
  // eslint-disable-next-line no-console
  console.log('Current values:', event.value)
})
```

## Accessibility

The Bootstrap Chip Input component follows WAI-ARIA patterns to ensure the chip input is fully usable with keyboards and assistive technologies.

- Associate a `<label>` with the ghost input for screen readers. The `.chip-input-label` also names the grid of chips.
- The chips sit in a `role="grid"` wrapper (`.chip-input-grid`, `display: contents`) next to the text field: each chip is a `role="gridcell"` with focus, inside a `.chip-row` that is its `role="row"`. While no chip can take focus the wrapper has no role.
- Each remove button the component creates is a real button named with `ariaRemoveLabel` and the chip's label, `Remove <label>` by default. It stays out of the tab order and a screen reader can reach it.
- Adding and removing chips is announced through [`announce()`](/accessibility/screen-readers/#announcing-messages) in the live region of the page, or of the modal dialog around the set, one message per update: the values the set did not hold before, or else the values it no longer holds, joined with commas as in `Vue, Svelte added`, and nothing while the set is hidden; customize the wording with the `ariaAddedAnnouncement` and `ariaRemovedAnnouncement` options. A function in place of the word receives the values and returns the whole message, so a page can put the word first, agree it with the number of chips or give a count for a long list, as in `(values) => values.length > 3 ? values.length + ' chips added' : values.join(', ') + ' added'`.
- Use a descriptive `aria-label` or `aria-labelledby` on the chip input, which moves to the grid of chips and names the field the component creates, or a `.chip-input-label` to communicate its purpose (e.g., "Add skills" or "Recipients"). A text field you write yourself keeps its own name; `dispose()` puts the name back on the chip input.
- An `aria-describedby` on the chip input element moves to the text field, after the field's own ids, and the element gets it back on dispose; while the state is `'invalid'` the error message follows it.

### Keyboard support

#### When input is focused

| Key | Action |
| --- | --- |
| `Enter` | Create a chip from each piece of the input value; a piece no chip comes from stays |
| `,` (or separator) | Create a chip from the piece the separator completes; a piece no chip comes from stays |
| `Backspace` / `Delete` | When input is empty, move focus to the last chip, if chips take focus |
| `←` | When cursor is at start, move focus to the last chip, if chips take focus |
| `Escape` | Clear input and blur |

#### When a chip is focused

| Key | Action |
| --- | --- |
| `Backspace` / `Delete` | Remove the chip and move focus to the next chip, else the previous one, else the text field (removable chips) |
| `←` | Move to previous chip |
| `→` | Move to next chip |
| `↑` / `↓` | Move to the previous or next chip |
| `Home` | Move to first chip |
| `End` | Move to last chip |
