<Callout color="warning">
  **Work in progress.** v6 is under active development on the `v6-dev` branch —
  this page tracks every migration-relevant change as it lands, so nothing here
  is final until a v6 release ships. The **class API keeps its meaning** —
  `.btn-primary`, `.alert-success` and friends render as before. Where the Sass
  or CSS-variable surface does change, the entry below carries a
  <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span> badge.
</Callout>

## v6.0.0 (unreleased)

### Dependencies

- **Popper is gone; `@floating-ui/dom` replaces it.**
  <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  Every positioned component — tooltips, popovers, dropdowns, autocomplete,
  multi-select, and the pickers — now positions with
  [Floating UI](https://floating-ui.com). `@popperjs/core` is no longer a peer
  dependency and the bundle builds (`coreui.bundle.*`) no longer include it.
  What to change:
  - npm: replace `@popperjs/core` with `@floating-ui/dom` in your dependencies.
  - CDN (non-bundle builds): replace the `popper.min.js` script tag with the
    two Floating UI files, in this order: `floating-ui.core.umd.min.js`, then
    `floating-ui.dom.umd.min.js`.
  - The `popperConfig` option (tooltip, popover, dropdown) is now
    `floatingConfig` and receives a Floating UI
    [computePosition](https://floating-ui.com/docs/computePosition) config —
    Popper's `modifiers` array does not translate; use Floating UI middleware.
  - The tip and menu carry `data-coreui-placement` instead of Popper's
    `data-popper-placement`; CSS or JS keying on the old attribute needs the
    new name.
  - Positioning is now asynchronous (`computePosition` is promise-based).
    Code that read the tip's coordinates synchronously right after `show()`
    should wait for the `shown` event.

### Distributed files

- **The `*.rtl.css` builds are gone.**
  <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  One stylesheet now serves both directions, so `dist/css` no longer carries
  `coreui.rtl.css`, `coreui-grid.rtl.css`, `coreui-reboot.rtl.css`,
  `coreui-utilities.rtl.css`, their minified twins, source maps or SRI hashes —
  20 files in all. Everything positional was already written with logical
  properties; the six places that genuinely differ (the off-canvas panel, the
  range slider's label and tooltip, the select and validation arrows, the
  carousel controls, the breadcrumb divider) now emit their mirrored
  declaration from a `[dir="rtl"]` rule in the same file. That costs 396 bytes
  gzip, where an RTL reader used to download a second 56&nbsp;kB stylesheet.

  **What to change:** drop the `.rtl` from your stylesheet link and keep
  `dir="rtl"` on `<html>`. `$enable-rtl: false` still produces an LTR-only
  build and `$enable-ltr: false` an RTL-only one, so nothing that was possible
  before stops being possible.

### Browser support

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

**The minimum supported browsers are now Chrome 123, Edge 123, Firefox 129,
Safari 17.5 and iOS 17.5.** `light-dark()` sets the Chrome/Edge/Safari floor;
`@starting-style` and `transition-behavior: allow-discrete` set Firefox 129 (the
Menu's entry animation) and `@property` needs 128 — its `inherits: false`
registrations are what stop the colour and opacity utilities leaking into
descendants, so an older Firefox does not lose an animation, it gets a bug.
`:has()` sets a lower bound of Firefox 121, since validation and focus states on Multi Select,
Autocomplete and the pickers, the sidebar navigation indicators, calendar
ranges and the rating icons are all selected with it — and an unsupported `:has()` invalidates
the entire rule it appears in. This is the floor the v6 color system already required in practice:
theme decisions resolve in the browser via `light-dark()` and `color-mix()`
with no fallback, so on older browsers dark mode did not work regardless of
what the previous `.browserslistrc` claimed (Chrome 60 / Safari 12). v6 makes
the declaration honest and takes the wins: the compiled CSS drops legacy
vendor prefixes (about 8&nbsp;kB gzip off `coreui.min.css`) and the JavaScript
ships modern syntax un-transpiled. If you must support older browsers, stay
on v5.

### JavaScript

v6's JavaScript is written in TypeScript. The published behaviour is unchanged —
the sources were converted module by module against a gate that required the
minified bundles to stay byte-identical — but the package now carries types, and
what it ships from `js/` has changed.

#### Type declarations ship with the package

`@coreui/coreui-pro` now ships `.d.ts` files and points `types` at
`js/dist/index.d.ts`, so TypeScript consumers get the full API without
`@types` packages or hand-written module declarations:

```ts
import { Modal, MultiSelect } from '@coreui/coreui-pro'

const modal = new Modal('#example', { backdrop: 'static', keyboard: false })
const version: string = Modal.VERSION
```

Each component also exports its config type, so an options object can be typed
and reused. Declarations are generated from the sources, not maintained by hand,
and CI type-checks a consumer file against the **emitted** declarations, so the
shipped types cannot drift from the code.

#### The `js/src` sources ship as TypeScript

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

The package used to ship `js/src/**/*.js`; it now ships `js/src/**/*.ts`. The
documented per-plugin path is unaffected — **`js/dist/*.js` still ships,
unchanged and UMD-ready**, and that is what the [Webpack](/guides/webpack/),
[Vite](/guides/vite/) and [Parcel](/guides/parcel/)
guides tell you to import:

```js
import Alert from '@coreui/coreui-pro/js/dist/alert'
```

Only imports that reached into the raw sources are affected:

```diff
- import Alert from '@coreui/coreui-pro/js/src/alert.js'
+ import Alert from '@coreui/coreui-pro/js/dist/alert.js'
```

If your toolchain compiles TypeScript, you can import `js/src/*.ts` directly and
get types and tree-shaking together. The per-plugin files are typed as well —
`js/dist/alert.js` ships next to `js/dist/alert.d.ts`.

#### `js/index.esm.js` and `js/index.umd.js` are no longer published

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

These two files are the bundler's entry points, and they import the sources —
which are now TypeScript, so the files could not resolve for a consumer anyway.
They are no longer part of the published package. Use the built bundle instead:

```diff
- import { Tooltip } from '@coreui/coreui-pro/js/index.esm.js'
+ import { Tooltip } from '@coreui/coreui-pro/dist/js/coreui.esm.js'
```

or, if you are already resolving the package by name, `import { Tooltip } from
'@coreui/coreui-pro'` — `module` points at the same ESM bundle.

#### Lifecycle methods return a promise

`show()`, `hide()`, `toggle()` and `close()` returned before the transition
ended, so continuing after one meant listening for `shown.coreui.*` /
`hidden.coreui.*`. They now return a promise that resolves at the same moment
that event fires, so you can `await` the method instead:

```diff
- myCollapseEl.addEventListener('shown.coreui.collapse', () => {
-   // the area is expanded
- })
- collapse.show()
+ await collapse.show()
+ // the area is expanded
```

Collapse, Menu, Modal, Offcanvas, Popover, Sidebar and Tooltip return one from
`show`/`hide`/`toggle`, Toast from `show`/`hide`, Tab from `show`, and Alert
from `close`. The event path is unchanged and still the right tool when you must
react to changes your own code did not start.

The promise always settles — a call that does nothing (already open, a prevented
`show.coreui.*`, an instance disposed mid-transition) resolves right away rather
than stranding the caller. It resolves with no value, so it tells you the call
finished, not whether the state changed.

### Components

#### Accordion on the native `<details>`

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The accordion renders on the native `<details>`/`<summary>` elements now.**
  `.accordion-item` goes on a `<details>` element and `.accordion-header` on its
  `<summary>`; the browser opens and closes the panel, so the component needs no
  initialization and works on markup added after load.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`.accordion-button`, `.accordion-collapse` and `.collapsed` are gone.** The
  trigger is the `<summary>` itself and the panel is the element's own content,
  revealed through `::details-content`. Style the open state with
  `.accordion-item[open] > .accordion-header` instead of `:not(.collapsed)`.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **Grouping moves from `data-coreui-parent` to the `name` attribute.** Give the
  `<details>` elements of one accordion the same `name` to keep a single item
  open at a time; omit it for an always-open accordion. The `id` plumbing
  (`data-coreui-target`, `aria-controls`, `aria-expanded`) is no longer needed —
  the browser exposes the disclosure state on its own.
- **A `<summary>` is not a heading.** Where the accordion divides a page into
  sections, wrap the label in an `<h2>`–`<h6>` inside the summary; the heading
  inherits the summary's typography.
- **The header's focus ring draws 1px inside the item**
  (`--cui-focus-ring-offset: -1px` on `.accordion-header:focus-visible`), so it
  no longer overlaps the borders of adjacent items.
- **The panel animation is CSS-driven** through `interpolate-size:
  allow-keywords`, which only Chromium implements today. `accordion.js` supplies
  the same animation in Firefox and Safari; that part of it goes away, without a
  breaking change, once they ship `calc-size()`. The component's events and
  methods do not depend on it and stay either way.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The accordion's events replace Collapse's.** `shown`/`hidden.coreui.accordion`
  fire on the `.accordion-item` whenever its open state changes, mirroring the
  native `toggle` event but bubbling, so they can be delegated. There is no
  `show`/`hide` counterpart: `<details>` has no cancelable event before the
  state change, so an item is kept shut by cancelling the click on its
  `<summary>` instead of by preventing an event.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The plugin replaces Collapse's, and it is instantiated on the `.accordion`
  container, not on a panel.** Where v5 called
  `Collapse.getOrCreateInstance(panel).show()`, v6 calls
  `Accordion.getOrCreateInstance(accordion).show(item)`, with the item given as
  an element or as its index. `hide()` and `toggle()` take the same argument,
  and `showAll()` / `hideAll()` open and close the whole accordion — the latter
  pair also handles the `name` juggling the HTML Standard requires, which is why
  expanding an exclusive accordion is a plugin call rather than a loop over
  `open`. None of it is needed to open and close items; the element does that
  on its own.
- **The header draws its focus ring on `:focus-visible`, not `:focus`.** A mouse
  click no longer paints a ring, keyboard focus still does, matching `.btn`.
- **New CSS variables:** `--cui-accordion-active-border-color` (the open item's
  border and the header's inset shadow, previously stuck on the resting border
  colour), plus `--cui-accordion-content-duration` and
  `--cui-accordion-content-easing`, which drive the panel transition and are
  read back by `accordion.js` so both paths animate for the same length of time.
- **The indicator can be an element instead of a background image.** Put an
  `<svg class="accordion-icon">` in the `<summary>` and the header stops drawing
  its own icon, so any icon set or `<img>` can be used without URL escaping an
  SVG into a custom property. `--cui-accordion-btn-active-icon` selects the
  shape shown while the item is open, and a second element marked
  `.accordion-icon-active` does the same in markup — that is what a plus/minus
  accordion needs, where the icon is swapped rather than rotated. The default
  chevron and its rotation are unchanged when neither is used.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The open item is neutral, and `.theme-{color}` is what tints it.**
  `--cui-accordion-active-bg` and `--cui-accordion-active-color` were fixed to
  `--cui-primary-bg-subtle` / `--cui-primary-text-emphasis`, so every accordion
  turned the brand colour on open whether or not that suited the page. They are
  `--cui-bg-4` and `--cui-fg-body` now, and the active tokens resolve
  through `--cui-theme-fg` / `-bg-subtle` / `-border` first — so the colour is a
  decision you make per accordion instead of one baked into the component. To
  keep the old look, put `.theme-primary` on the `.accordion`.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`--cui-accordion-inner-border-radius` is gone; the header's corners follow
  `--cui-accordion-border-radius`.** The token was computed from the global
  `--cui-border-radius` when the stylesheet was built, so setting
  `--cui-accordion-border-radius` rounded the item while the header inside kept
  the page's default radius. The two corners are subtracted where they are
  used — `calc(var(--cui-accordion-border-radius) - var(--cui-accordion-border-width))`
  — so one token now shapes the whole item. Defaults render as before; drop any
  override of the removed variable.

- **One padding token and one font size for the whole control.**
  `--cui-accordion-padding-x` / `-y` and `--cui-accordion-font-size` are read by
  the header and the body alike, so resizing an accordion is one declaration
  instead of four. `--cui-accordion-btn-padding-*` and
  `--cui-accordion-body-padding-*` are no longer declared by default, but they
  still override their part where they are set, so existing overrides keep
  working.

#### Breadcrumb

- **Three breadcrumb tokens have real defaults.** `--cui-breadcrumb-bg`,
  `--cui-breadcrumb-border-radius` and `--cui-breadcrumb-font-size` were `null`
  in Sass, so the first two were emitted empty (`--cui-breadcrumb-bg: ;`) and
  the third was not emitted at all. They are `transparent`,
  `var(--cui-border-radius)` and `inherit` now. Nothing renders differently on
  a default breadcrumb, and a font size set on an ancestor still reaches it —
  the one visible change is that a breadcrumb **given a background** now has
  rounded corners like every other surface. Set
  `--cui-breadcrumb-border-radius: 0` to square it off.
- **New: `.breadcrumb-link`, an opt-in class that gives a step a padded,
  hoverable target.** Bare links keep rendering as they always did. On a
  `<button>` it looks identical to a link, which is what lets one step toggle a
  menu of collapsed items — the composition is documented under Collapsed
  items, together with the reason not to reach for `role="menu"` there.
- **New: `.breadcrumb-divider`, a separator you can put in the markup.** The
  automatic `::before` divider stays exactly as it was and existing markup is
  untouched, but a `<li class="breadcrumb-divider">` placed between two items
  carries whatever you put in it — an inline SVG, an icon, a character — with
  no URL escaping and no variable to set, and an empty one renders the default
  divider. The automatic divider steps aside wherever an element is placed
  (`.breadcrumb-item + .breadcrumb-item` stops matching), so the two never
  double up, and the spacing is identical either way. Give the element
  `aria-hidden="true"`, since a screen reader would otherwise count the
  separators as steps in the trail.

#### Avatar

- **The avatar carries its own colours, and `.theme-{color}` tints it.**
  `--cui-avatar-bg` and `--cui-avatar-color` are new: a bare avatar is a
  neutral circle instead of a transparent one, and a `.theme-*` class puts the
  theme colour behind the letters and the colour that reads on it in front of
  them. The docs used to reach for `bg-{color}` plus a hand-picked `text-*`,
  which fails WCAG AA on five of the six examples they shipped — measured 1.85
  on `bg-warning text-white`, 2.94 on info, 3.50 on success, 3.69 on danger,
  and 3.12 on `bg-secondary`, which carried no text colour at all. Every theme
  colour now lands between 4.56 and 18.03. Background utilities keep working on
  an avatar; they just no longer have to.
- **New: `.avatar-subtle`**, a tinted avatar that keeps the theme colour in the
  letters rather than behind them.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **One size token replaces the width/height pair.** `--cui-avatar-width` and
  `--cui-avatar-height` always carried the same value, in the base and in all
  four size classes, so setting a size meant writing it twice. They become
  `--cui-avatar-size`, and `--cui-avatar-status-width` / `-height` become
  `--cui-avatar-status-size` the same way.

  The label is derived from it — `calc(var(--cui-avatar-size) * .4)` — rather
  than listed per size. That ratio is what every size already used, so nothing
  renders differently; `--cui-avatar-font-size` still overrides it where a
  size needs its own.

  The Sass variables follow: `$avatar-width` / `$avatar-height` /
  `$avatar-font-size` / `$avatar-status-width` / `$avatar-status-height` become
  `$avatar-size` / `$avatar-status-size` plus `$avatar-font-size-ratio`, and
  `$avatar-sizes` keys drop to `size` and an optional `status-size`. The
  `$avatar-widths` map, deprecated since 5.1.0, is gone.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`.avatar-img` fills the avatar and crops instead of stretching.** It was
  `height: auto`, which deformed every image that was not square; it is now
  `height: 100%` with `object-fit: cover`. Square images look the same.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The status indicator's ring follows the theme.** It was `1px solid $white`,
  a hardcoded white that read as a mistake in dark mode. It now comes from
  `--cui-avatar-status-border-color`, defaulting to the body background.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **A stacked avatar lifts on hover instead of pushing its neighbours.** The
  hover changed `margin-inline-end`, which moved every avatar after it; it now
  uses `transform`, so nothing else shifts. `$avatar-transition` changes from
  `margin .15s` to `transform .15s ease-in-out` accordingly.
- **Stacked avatars wear a ring and stop pulling what follows them.** Each
  avatar in a stack gets a border in the page background colour
  (`--cui-avatar-stack-ring-width` / `-color`), so overlapping photos stay
  separated; the last avatar drops its negative margin, which used to drag
  the content after the stack underneath it. The overlap is a token now —
  `--cui-avatar-stack-spacing`, the fraction of the avatar size — and
  `.avatars-stack-sm` through `-xl` size every avatar in a stack at once.
- **The status indicator follows `.theme-{color}` and is never invisible.**
  `.avatar-status` reads the theme slot and falls back to the new
  `--cui-avatar-status-bg` (a neutral grey), so a bare indicator reads as
  "offline" instead of rendering as an empty ring. Background utilities keep
  working on it.

#### Alert

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **An alert without a theme class carries its own surface.** `--cui-alert-bg`
  falls back to `var(--cui-bg-1)` instead of `transparent`, so a plain
  `.alert` no longer takes the color of whatever it sits on. Set
  `--cui-alert-bg: transparent` on the alert to restore the old rendering.

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The alert lays its children out in a row.** It is `display: flex` with
  `align-items: start` and `--cui-alert-gap` between children, so an icon next
  to a label needs no `d-flex` and no spacing utility. Text mixed with inline
  elements is a single anonymous item and is unaffected, but an alert built
  from **several block elements** — a heading, paragraphs, an `<hr>` — now sits
  side by side. Wrap that content in a `.vstack`:

  ```html
  <div class="alert alert-success" role="alert">
    <div class="vstack">
      <h4 class="alert-heading">Great job!</h4>
      <p>…</p>
    </div>
  </div>
  ```

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **A solid alert is `.alert-solid`, not a pile of utilities.** The docs used to
  say to drop the contextual class and reach for `bg-{color}` plus a `text-*`
  class picked by hand — and the examples hard-coded `text-white`, which fails
  WCAG AA on five of the eight theme colours: measured 3.50 on success, 3.69 on
  danger, 2.94 on info, 1.85 on warning and 1.10 on light, where white text on a
  near-white background is invisible. `.alert-solid` reads the theme's own
  contrast token, so every colour lands between 4.56 and 18.03 — including a
  theme colour you define yourself. Markup using the old recipe still renders;
  it is the contrast that was never right.

- **An alert marked `.fade show` fades in when it is added to the page.** The
  classes used to animate the alert in one direction only, because an element
  inserted with `.show` already on it has no earlier state to transition from;
  `@starting-style` supplies one. Nothing to change in your code — an alert you
  append at runtime animates without the class juggling that used to be needed,
  and an alert already in the markup is unaffected.

- **The close button is a flex item, not an absolutely positioned one.** It is
  pushed to the end with `margin-inline-start: auto`, so it no longer overlaps
  the text and the alert no longer reserves three paddings of room for it.
  A `.btn-close` that is a **direct child** of the alert still lands where it
  did, with or without `.alert-dismissible`, and `.alert-dismissible` itself is
  now an empty class kept for existing markup. One case does change: a close
  button nested inside a wrapper used to be positioned by the alert, and is now
  laid out by that wrapper like any other content. Move it up to be a direct
  child of the alert to keep it at the trailing edge.

- **An `<hr>` inside an alert takes the variant's border colour.** The alert
  redeclares `--cui-hr-border-color`, so a separator in a `.alert-success` is
  green rather than the page's neutral grey.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`$alert-dismissible-padding-r` is gone; the space for the close button
  follows `--cui-alert-padding-x`.** The variable was multiplied out in Sass
  when the stylesheet was built, so raising `--cui-alert-padding-x` widened
  three sides of a dismissible alert and left the fourth on the default: at
  `2rem` the alert had 32px of padding and 48px of room for the button, which
  also kept its own 16px padding. Both are subtracted from the tokens now —
  `calc(var(--cui-alert-padding-x) * 3)` and
  `calc(var(--cui-alert-padding-y) * 1.25) var(--cui-alert-padding-x)` — so one
  token resizes the whole alert. Defaults render as before; drop any override
  of the removed variable.

#### The close button is masked, not filtered

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

`.btn-close` used to paint a black glyph baked into its SVG and recolour it for
dark mode with a filter. The colour now comes from the element, the way the
check, radio, carousel and toggler icons already work:

```diff
- background: transparent var(--cui-btn-close-bg) center / 1em auto no-repeat;
- filter: var(--cui-btn-close-filter);
+ background-color: currentcolor;
+ mask-image: var(--cui-btn-close-icon);
```

- **`--cui-btn-close-filter` is removed**, together with `$btn-close-filter` and
  `$btn-close-filter-dark`. Recolour the button with `--cui-btn-close-color`
  instead of inverting the image.
- **`$btn-close-color` defaults to `inherit`**, so the glyph follows the surface
  it sits on. A close button inside a themed alert or a dark toast no longer
  needs a rule of its own to stay legible.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`.btn-close-white` is gone**, deprecated since v5.0.0, and so is the
  dark-mode rule that forced the glyph white. Both restated what the inherited
  colour already produces on a surface that paints its own text — a
  `.text-bg-inverse` toast, a dark navbar's offcanvas, a `.bg-body.text-body`
  section under `data-coreui-theme="dark"`. Delete the class; the button
  renders identically without it. The rule additionally got the mirror case
  wrong: a `data-coreui-theme="light"` section inside a dark page inherited the
  forced white and drew a white icon on white.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The size surface is two variables instead of five.**
  `--cui-btn-close-width`, `-height`, `-padding-x` and `-padding-y` collapse
  into `--cui-btn-close-icon-size` and `--cui-btn-close-padding`, matching the
  Sass variables of the same names. Nothing changes on screen: the glyph is
  still `1em` inside `.25em` of padding, so the pointer target stays 24px at
  the default font size — the WCAG 2.2 minimum.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`--cui-btn-close-bg` is `--cui-btn-close-icon`** (`$btn-close-bg` →
  `$btn-close-icon`). It stopped being a background when the glyph moved to a
  mask; the name had been describing the old implementation.
- The SVG in `--cui-btn-close-icon` carries the shape only. A custom image works
  the same way — give it any colour, the mask ignores it.

#### Badge

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **Colour comes from `.theme-*`, and `.badge-*` now names the variant.** A bare
  `.badge` used to be white text with no background of its own, so it was
  invisible until a `.text-bg-*` utility supplied both. It renders neutral on
  its own now — `--cui-badge-color` is `inherit` and `--cui-badge-bg` is
  `--cui-bg-4` — and a `.theme-*` class colours it:
  `<span class="badge theme-danger">`. The `.badge-*` namespace carries the
  three variants instead: solid (default), `.badge-subtle` and
  `.badge-outline`, each mapping the same theme roles.

  `.text-bg-*` still works and still sets both properties, so existing markup
  keeps rendering. Markup that paired `.badge` with a background utility alone
  (`<span class="badge bg-danger">`) now shows the inherited text colour on
  that background instead of white — swap it for `.theme-danger` or add a text
  colour utility.

- **The badge lays itself out.** `display` is `inline-flex` with
  `--cui-badge-gap` between children and `--cui-badge-min-height` as the floor,
  so an icon next to a label needs no spacing utility and badges keep one
  height across a table or a list.

- **The font size has a legibility floor.** `--cui-badge-font-size` is
  `clamp(12px, .75em, .75em)`, so a badge inside small text stops shrinking at
  12px while still scaling up with a larger parent.

- **New: `--cui-badge-border-width` / `--cui-badge-border-color` (transparent),
  `.badge-lg`, and a link reset.** The border tokens are what `.badge-outline`
  switches, `.badge-lg` joins `.badge-sm` on the size scale, and `a.badge` no
  longer inherits the underline from the reboot.

#### Carousel slides by scrolling

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The engine is native CSS scroll snapping, not transforms.** The track
  (`.carousel-inner`) is a scroll container: dragging, swiping and momentum
  come from the browser, and programmatic jumps animate the scroll position
  over a fixed 300ms. The transform choreography is gone with its state
  classes — `.carousel-item-next`, `.carousel-item-prev`,
  `.carousel-item-start`, `.carousel-item-end` and `.pointer-event` no longer
  exist; react to the `slide`/`slid` events instead of styling them. The
  `.slide` class is inert — leave it in old markup or drop it, nothing reads
  it any more. The markup skeleton (indicators + inner with items +
  controls) is unchanged, and the controls, indicators and captions keep
  their overlaid layout.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`ride` is `autoplay`, `wrap` is `ends`, and `touch` is gone.**
  `data-coreui-autoplay="true"` (boolean — the `"carousel"` spelling is gone)
  cycles from page load; `ends` takes `"loop"` (default — continues
  seamlessly where the layout allows), `"wrap"` (the old jump) or `"stop"`
  (hard ends with the matching control disabled). Touch needs no option:
  the browser owns it. Autoplay now turns off for good once the user
  interacts (WCAG 2.2.2), and while it runs the active indicator fills like
  a progress bar over the slide's interval.
- **New layout knobs and a pause control.** `--cui-carousel-items`,
  `--cui-carousel-items-gap` and `--cui-carousel-items-peek` put several
  slides in the viewport; `.carousel-center` snaps the active slide to the
  middle and `.carousel-auto` lets slides keep their own width. A button
  with `.carousel-control-play-pause` (holding `.carousel-control-pause-icon`
  and `.carousel-control-play-icon`) toggles autoplay and swaps its
  `aria-label` between `data-coreui-pause-label` and
  `data-coreui-play-label`.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`.carousel-dark`, the `carousel-dark()` mixin and `$carousel-dark-*` are
  gone.** The chrome colours are `light-dark()` pairs resolved on the
  carousel itself, so the standard `data-coreui-theme="dark"` attribute is
  the dark variant — and `data-coreui-theme="light"` pins the white chrome
  on a dark page the same way.
- **Every chrome measurement is a `--cui-carousel-*` token** declared on
  `.carousel` — control width and opacities, icon images and sizes,
  indicator geometry and transitions, caption metrics, the play/pause
  button — so the whole carousel restyles at runtime without recompiling.
- **Crossfade timing moved to tokens.** `$carousel-transition-duration` and
  `$carousel-transition` are gone; the fade reads
  `--cui-carousel-fade-duration` and `--cui-carousel-fade-timing`, and the
  slides stack on a grid instead of floating.

#### Autocomplete and Multi Select share one options menu

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The generated options dropdown now uses unified `combobox-*` classes** in
  both components: `combobox-popup`, `combobox-options`, `combobox-option`
  (+`-with-checkbox`), `combobox-optgroup(-label)`, `combobox-options-empty`,
  `combobox-header`, `combobox-all`, with the state classes
  `selected` and `indeterminate`. The former `autocomplete-dropdown`/
  `autocomplete-option(s)`/`autocomplete-optgroup*` and
  `form-multi-select-dropdown*`/`-options*`/`-option*`/`-optgroup*`/`-all*`/
  `form-multi-selected`/`form-multi-select-indeterminate` classes are gone,
  along with their Sass variables and CSS custom properties — theme the
  shared surface through `$combobox-*` / `--cui-combobox-*` instead. This
  markup is generated by the plugins (authors don't write it), so only custom
  CSS targeting the dropdown internals needs updating. The field/selection
  markup of both components is unchanged.

#### Menu (new) and Dropdown

- **New component: Menu** — contextual overlays with submenus, container
  teleport, responsive placement and logical (`start`/`end`) placements,
  ported from Bootstrap v6 with CoreUI's class conventions. See the
  [Menu docs](/components/menu/).
- **Dropdown is now a compatibility layer over Menu.** The v5 markup, classes
  and `*.coreui.dropdown` events keep working unchanged — the plugin shares
  Menu's engine underneath. Where their options overlap, Dropdown also
  understands Menu's additions (for example `container`). **Deprecation
  notice: Dropdown may be removed in v7** — prefer Menu for new work.


#### Modal and Offcanvas on the native `<dialog>`

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **Both components render on the native `<dialog>` element now**, opened with
  `showModal()`/`show()` and closed with `close()`. The browser provides the
  top layer (no `z-index` management), the `::backdrop`, focus trapping,
  background inertness and the dialog ARIA semantics — the markup drops
  `role`, `aria-modal`, `aria-hidden` and `tabindex="-1"`.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The modal wrapper layers are gone.** `.modal > .modal-dialog >
  .modal-content` flattens to a single `<dialog class="modal">` holding
  `.modal-header`/`.modal-body`/`.modal-footer` directly. Size
  (`.modal-sm/-lg/-xl`) and fullscreen (`.modal-fullscreen*`) modifiers sit on
  the dialog itself. `.modal-dialog-scrollable` is renamed to
  `.modal-scrollable`; `.modal-dialog-centered` is gone — the browser centers
  a modal dialog by default. Offcanvas markup only swaps the tag:
  `<dialog class="offcanvas offcanvas-start">`.
- **Legacy v5 markup keeps working — for now.** When a component is
  instantiated on v5 markup (via data API or JavaScript), the plugin rebuilds
  it into the `<dialog>` structure at runtime and logs a console warning. The
  old element stays in the DOM as an inert `display: contents` shell around
  the new dialog, so existing element references and event listeners keep
  working (our events bubble through it). Selectors and custom CSS targeting
  `.modal-dialog`/`.modal-content` are the one thing that cannot be preserved.
  **This transitional layer will be removed in v7.**
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`.modal-backdrop` and `.offcanvas-backdrop` are gone** — the backdrop is
  the native `::backdrop` pseudo-element. Style it through the new
  `--cui-modal-backdrop-bg`/`--cui-modal-backdrop-opacity` and
  `--cui-offcanvas-backdrop-*` tokens. `$zindex-modal-backdrop` and
  `$zindex-offcanvas-backdrop` are removed.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **Animation opt-in is inverted.** Modals animate by default; `.fade` is gone
  and `.modal-instant` / `.offcanvas-instant` disable animation instead. The
  auto-upgrade maps a missing `.fade` to `.modal-instant`. The offcanvas
  `.showing` state class is replaced by the native `[open]` attribute
  (`.hiding` remains for the exit transition).
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The Modal `focus` option is removed** — the native dialog always traps
  focus. `handleUpdate()` remains as a no-op for API compatibility; the
  scrollbar-compensation logic it triggered no longer exists (scroll lock is
  `overflow: hidden` + `scrollbar-gutter: stable` on the root element, with
  the `dialog-open` class).
- **New capabilities:** a `modal: false` option opens the dialog non-modally
  (page stays interactive); a `cancel.coreui.modal` event fires when a modal
  is dismissed with Escape; toggling from a trigger inside an open modal swaps
  to the target modal with a seamless backdrop (no flash); modals can be
  stacked — the top layer manages paint order.
- **Sass:** `$modal-transition` and `$modal-show-transform` are replaced by
  `$modal-transition-duration`/`$modal-transition-timing`; the offcanvas
  transition token splits the same way
  (`--cui-offcanvas-transition-duration`/`-timing`).

#### Dialog (new) and Drawer (new)

- **New components: Dialog and Drawer** — the native-`<dialog>` popup and
  side panel with the Bootstrap 6 look and `dialog-*` / `drawer-*` classes:
  Dialog is a centered floating panel over a blurred backdrop with optional
  slide entry variants; Drawer is a floating, inset, rounded panel with
  translucent/sheet/fullscreen/fit-content variants and responsive classes
  (`.drawer-sm`…`.drawer-xxl`). Both share the DialogBase behavior with
  Modal/Offcanvas (which keep the classic look and the v5 vocabulary) —
  pick per surface, they are independent components. See the
  [Dialog docs](/components/dialog/) and [Drawer docs](/components/drawer/).

#### Calendar

- **Behavior change:** `update()` now **merges** the given options over the
  current configuration instead of resolving them against the defaults. A
  partial call like `calendar.update({ selectEndDate: true })` no longer resets
  every other option (`range`, `calendars`, `locale`, …) — this aligns
  `Calendar.update()` with `DateInput`/`TimeInput`/`DateTimeInput` `update()`
  semantics. Callers that passed the complete configuration on every update are
  unaffected.
- **Additive:** `startDateChange` and `endDateChange` now carry a `dateObject`
  property with the underlying `Date`, alongside the existing `date` property.
  `date` remains formatted per `selectionType` — a `Date` for day selection, but
  a string for week (`"2026W27"`), month (`"2026-01"`), quarter (`"2026Q1"`) and
  year (`"2026"`). Existing listeners are unaffected.

#### Date Picker / Date Range Picker

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

**The pickers are rewritten.** `DatePicker`, `DateRangePicker` and `TimePicker`
are now a composition of the section-based input fields
([date input](/forms/date-input/)), the [calendar](/components/calendar/) and a
shared popup primitive, instead of the v1 monolith. The rewrite ships **under
the existing names** — `DatePicker`, `data-coreui-toggle="date-picker"`,
`.date-picker` — so no renaming is needed on your side, but the options below
changed. The v1 shells are gone; if you need to compare against the old
behaviour, v5 is the reference. Mapping:

- **Removed — projected regions replace button configuration.** `footer`,
  `todayButton`, `todayButtonClasses`, `cancelButton`, `cancelButtonClasses`,
  `confirmButton`, `confirmButtonClasses`, `ranges`, `rangesButtonsClasses` →
  put a `<template data-coreui-template="footer">` /
  `data-coreui-template="ranges"` child in the picker element. Zero-argument
  actions bind with `data-coreui-picker-action="today|clear|reset|close"`;
  actions with arguments (range presets) go through `picker.getContext()`
  (`setDate`, `setRange`, `clear`, `reset`, `close` + read-only state).
- **Removed — obsolete with section fields.** `inputDateFormat`,
  `inputOnChangeDelay`, `inputReadOnly`, `placeholder` — the masked field is
  always a valid partial date; there is no free-text parsing to debounce.
  Section placeholders come from the input triad's `placeholders`.
- **Changed.** `timepicker: true` is replaced by the standalone
  [date time picker](/forms/date-time-picker/) — a DateTimeInput field with a
  calendar and the time selection body side by side. Because the two halves own
  different parts of one value, that picker does not auto-close: picking a day
  keeps the time and picking a time keeps the day.
- **Kept.** Calendar passthrough (`locale`, `minDate`/`maxDate`,
  `disabledDates`, `selectionType`, `showWeekNumber`, custom cell renderers, …),
  `container`, `startDate`/`endDate`/`date`, `startName`/`endName`/`name`,
  `size`, validation states, the data API
  (`data-coreui-toggle="date-picker"`), and the imperative API
  (`show`/`hide`/`toggle`/`clear`/`reset`).
- **Passthrough is by name.** Options that belong to the inner calendar or date
  input are forwarded automatically, so `data-coreui-selection-type`,
  `data-coreui-show-week-number` and `data-coreui-format` work on the picker
  element. `calendarOptions` / `inputOptions` remain as the programmatic escape
  hatch.
- **Every selection type has a matching mask.** Month and year selection narrow
  the mask to `MM/yyyy` and `yyyy`. Week selection renders the native
  `<input type="week">` presentation — a fixed localized label plus week and
  year sections (`Week 29, 2026`, `Tydzień 29, 2026`), where the year is the
  ISO week-numbering year. Quarter selection narrows to `QQQ yyyy`
  (`Q4 2026`). The v1 text input rendered `2026W27`/`2026Q1`; the submitted
  value now follows the mask (set `format="yyyy-Www"` for an ISO-style
  field), and the event still carries the v1-formatted string (`event.date`)
  next to the `Date` (`event.dateObject`). The format parser gained `ww`
  (ISO week) and `q`/`QQQ` (quarter) tokens, plus quoted literals
  (`'Week' ww` — fixed text that may contain token letters, `''` escapes a
  quote).
- **Format comes from the mask.** `inputDateFormat` is replaced by `format`
  (forwarded to the field); `inputDateParse` still applies to pasted text.
- **Footer buttons are projected, `today`/`now` actions keep the v1 gating.**
  A projected button opting into the `today` action (`now` on the time picker)
  is disabled at initialization when its target falls outside
  `minDate`/`maxDate`/`disabledDates` — matching the v1 built-in button. This
  is one-way: the picker only ever sets `disabled`, never re-enables. The
  state of any other projected button is yours — the slot context exposes
  `isDateSelectable(date)` (`isTimeSelectable` on the time picker) for
  computing it. Programmatic dates (`setDate`, actions, the initial `date`
  config) run through the same min/max validation as typed ones: out of
  range, the field turns `is-invalid`, `errorChange` fires, and
  `getDate()`/`dateChange` report `null`. `dateChange` on the shells always
  carries the validated value.
- **The calendar is built on first open, not at construction.** It accounts for
  ~83% of a date picker's DOM (and ~89% of a range picker's), and it is not
  observable before the popup opens, so the shells create it in `show()` and
  seed it from the field values. Measured over 20 pickers: date picker
  **65 ms → 15 ms** and **3200 → 540** DOM nodes, range picker **93 ms → 12 ms**
  and **6060 → 740** nodes. The first open costs a few milliseconds more (the
  calendar is built then); later opens are unchanged. Code reaching into the
  private `picker._calendar` before the first open now finds `null`.

#### Date Input / Time Input / Date Time Input

- **RTL keyboard navigation now follows the visual direction in nested RTL
  contexts.** Arrow keys (and `Home`/`End`) mirror when the field renders
  right-to-left; the direction is read from the element's computed style
  instead of `document.documentElement.dir`, so a `dir="rtl"` ancestor works
  and not only a document-level direction.

#### Time Picker / Date Time Picker (new)

- The time selection body is now a shared primitive used by both pickers, so the
  `roll` and `select` variants, the `hours`/`minutes`/`seconds` filters and the
  12/24-hour locale split behave identically in each. See
  [time picker](/forms/time-picker/) and the new
  [date time picker](/forms/date-time-picker/), which replaces v1's
  `timepicker: true` flag on the date picker.
- Same removals as the date pickers: `footer`/`cancelButton`/`confirmButton` and
  their class options give way to a projected
  `<template data-coreui-template="footer">` with
  `data-coreui-picker-action="now|clear|reset|close"`; `inputReadOnly`,
  `inputOnChangeDelay` and `placeholder` are obsolete with a section field.
- **`reset()` restores the value the picker was constructed with.** In v2 the
  shell remembers it: setting a value goes through the field's `update()`, which
  rewrites the field's own configuration, so the field can no longer restore the
  original on its own.

#### The v1 picker shell classes are gone

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

The rewritten pickers style the field through
`forms/_form-date-time.scss` and render their icons as inline SVG, so the v1
shell's own elements no longer exist: `.date-picker-input`,
`.date-picker-input-wrapper`, `.date-picker-input-preview`,
`.date-picker-cleaner`, `.time-picker-input`, `.time-picker-cleaner` and
`.time-picker-inline-icon`. Custom CSS targeting those needs rewriting against
the new structure; everything else (`.date-picker`, `.date-picker-popup`,
`.date-picker-body`, `.date-picker-footer`, the `-sm`/`-lg` size modifiers, the
`.time-picker-roll*` bodies) keeps its name.

#### The picker panel is `.date-picker-popup` / `.time-picker-popup`

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

`-dropdown` was the vocabulary of the per-family panels, and every other family
lost it when the options menu became `.combobox-popup`. The pickers were the
last holdout:

| v5 | v6 |
| --- | --- |
| `.date-picker-dropdown` | `.date-picker-popup` |
| `.time-picker-dropdown` | `.time-picker-popup` |

The rename comes with the reason for it. **The panel declares its own tokens
now** rather than inheriting them from the field's root through a
`*:not(.date-picker) > …` patch, so nothing inside it depends on having a
particular ancestor — it renders the same in place, teleported through the
`container` option, or rendered into `document.body` by a framework port's
portal.

`width: min-content` went with it: an absolutely positioned panel already
shrinks to its content, and both pickers measure identically without the
declaration.

#### `.form-select` is absorbed by `.form-control`

- **A `<select>` takes `.form-control` now**, like every other control. The two
  were already the same thing everywhere but the chevron: measured across every
  computed property, `.form-select` and `.form-control` on the same `<select>`
  differed in exactly ten — the eight `background-*` that draw the chevron and
  the padding that makes room for it. Everything else already came from the
  shared `--cui-control-*` tokens.
- **`<select class="form-control">` used to render without any arrow at all** —
  `.form-control` sets `appearance: none`, which removes the native one, and
  nothing put ours back. That is fixed by the same change.
- **New: `.form-control-caret`** puts the chevron on an element that is not a
  `<select>` — a button that opens a listbox, for instance.
- **`.form-select`, `.form-select-sm` and `.form-select-lg` keep working** as
  aliases of the `.form-control` classes, not as a second implementation.
  Deprecated in v6, removed in v7.

  ```diff
  - <select class="form-select form-select-lg">
  + <select class="form-control form-control-lg">
  ```

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The `$form-select-*` Sass variables are gone**, along with
  `scss/forms/_form-select.scss`. Most were pass-throughs to `$input-*` /
  `--cui-btn-input-*` and their `.form-control` equivalents apply
  unchanged; the chevron's own are renamed `$form-control-select-*`. The runtime
  tokens move with them: `--cui-form-select-bg-img` →
  `--cui-control-select-bg-img`, `-bg-position`, `-bg-size`,
  `-indicator-padding` → `--cui-control-select-padding-end`, and the
  `-feedback-icon-*` pair.
- **Two differences a select inherits from `.form-control`,** neither of which
  changed a rendered box in any case measured. It paints its background with
  `background-clip: padding-box`, the value `.form-control` has always used to
  avoid a rounded-corner artefact in Firefox — 0.12% of the control's pixels, the
  antialiasing of the four corners. And `.form-select-sm` / `-lg` now carry the
  `min-height` their `.form-control` counterparts always had, so a sized select
  is finally the same height as a sized input; it only shows if you have cut the
  padding below that floor.

#### Form labels carry their own weight

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`.form-label` and `.col-form-label` render medium and full-contrast by
  default.** `$form-label-font-weight` is `var(--cui-font-weight-medium)`
  (was `null` — labels inherited the surrounding weight) and
  `$form-label-color` is `var(--cui-fg-body)` (was `null`), so a label inside
  a muted or tinted context keeps the page's text colour instead of fading
  with it. Set the knobs back to `null`, or `--cui-label-font-weight` /
  `--cui-label-color` to `inherit`, for the old behaviour.

#### Input group: `.has-validation` removed

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
`.has-validation` is gone. It existed so a group could keep its corner logic
with a `-feedback` element sitting inside it as the last child — in v6 the
feedback lives **outside** the group: wrap the group in a
[`.form-field`](/forms/field/) and put the `-feedback` after it, and the
message renders under the whole frame. A group still carrying the class simply
gets the default corner handling; a group still carrying the feedback *inside*
should move it out.

```diff
- <div class="input-group has-validation">
-   <span class="input-group-text">@</span>
-   <input type="text" class="form-control is-invalid" required>
-   <div class="invalid-feedback">Please choose a username.</div>
- </div>
+ <div class="form-field">
+   <div class="input-group">
+     <span class="input-group-text">@</span>
+     <input type="text" class="form-control is-invalid" required>
+   </div>
+   <div class="invalid-feedback">Please choose a username.</div>
+ </div>
```

#### Input group: one frame class instead of five

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

`.input-group` squared off the frame of a field component by naming each
family's wrapper — `.autocomplete-input-group`, `.date-picker-input-group`,
`.time-picker-input-group`, `.form-multi-select-input-group` and
`.form-password`. All five became `.form-control-group`, so the input group
targets that one class:

```diff
- > .autocomplete:not(:last-child) > .autocomplete-input-group,
- > .date-picker:not(:last-child) > .date-picker-input-group,
- > .time-picker:not(:last-child) > .time-picker-input-group,
- > .form-multi-select:not(:last-child) > .form-multi-select-input-group,
- > .form-password:not(:last-child) > .form-control,
+ > .form-control-group:not(:last-child),
```

A field component *is* the frame — it carries `.form-control-group` on its own
root rather than nesting one — so it is a direct child of the input group like
any other control, and there is no wrapper level to reach through.

If you wrote CSS against those wrapper classes to adjust a field inside an
input group, target `.form-control-group` instead. A hand-authored group — a
password field, a chip input — is now a first-class child of `.input-group`
and needs no wrapper of its own.

**The input group styles ship in the `components` layer**, not `forms`. It
assembles controls rather than being one, and the layer it sat in lost to
`components` whatever the selector said — so a `.btn` inside a group kept the
radius it sets for itself and showed rounded corners against the field. If your
own stylesheet re-squared those corners as a workaround, the override is no
longer needed. A rule of yours that relied on the group losing to a component
now loses to the group instead; give it a layer of its own if you need it back.

#### Chip Input takes the frame class itself

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

```diff
- <div class="form-control-group chip-input" data-coreui-chip-input>
+ <div class="chip-input" data-coreui-chip-input>
```

A chip input has no control to wrap — the element *is* the frame — so it adds
`.form-control-group` to itself rather than asking you to write both. Writing
both still works; the component only removes on `dispose()` a class it added.

#### Number Input (new)

- **New component: [Number Input](/forms/number-input/)** (PRO) — a number field
  with a stepper you can actually hit. The browser's own spinner is tiny, shows
  only on hover in some engines and does not exist at all on iOS; the component
  replaces it with two buttons sized like every other adornment, on the shared
  [`.form-control-group`](/forms/form-control-group/) frame. Nothing to migrate —
  it is listed here because the `number-input` name, its classes and its Sass

#### Multi Select

- **The option checkboxes are the standard form-check surface.** The indicators
  used to re-implement the form-check visuals as `::before` pseudo-elements with
  their own variable set; they are decorative `.form-check-input` spans now
  (`aria-hidden`, since `aria-selected` carries the semantics), so size, border,
  radius, background and theming all come from the form-check surface and the
  two stay in lockstep. The per-indicator look variables are gone with
  them — only `$combobox-option-indicator-width` survives, and it follows the
  checkbox: `--cui-check-size` where the indicator can see it, and the shared
  `--cui-control-size` otherwise. Theme the option checkbox through `$check-*` /
  `--cui-check-*` instead.

#### Password Input and Number Input build their own frame

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

Both components supply their own buttons, so they supply the frame that lays
them out. The markup is a plain form control carrying the toggle:

```diff
- <div class="form-control-group">
-   <input type="password" class="form-control">
-   <button type="button" class="form-control-action" data-coreui-toggle="password" aria-label="Toggle password visibility">
-     <span class="form-password-action-icon"></span>
-   </button>
- </div>
+ <input type="password" class="form-control" data-coreui-toggle="password-input">
```

- **`data-coreui-toggle` moves from the button to the input**, and its value is
  the component's name: `password-input` (and `number-input` for the new
  [Number Input](/forms/number-input/)). The button no longer exists in your
  markup, so there is nothing left to put it on.
- **Classes you write on the input, other than `.form-control`, move onto the
  frame** — size, spacing, width. They describe the field, and once the input is
  wrapped the field is the frame; a margin left on the control would sit inside
  the border. They move back on `dispose()`.
- **An input already inside a `.form-control-group` is left where you put it**,
  so a field can share a frame with other adornments, and only a frame the
  component created is removed on `dispose()`.
- The accessible name of the toggle is the `ariaToggleLabel` option now, since
  the button is no longer yours to label.

#### Password Input: the toggle icon comes from JavaScript

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

The toggle button carried `<span class="form-password-action-icon"></span>`,
and CSS painted it as a mask that swapped through a sibling selector. The
plugin renders it now — inline SVG on `currentColor`, like every other
adornment in the library — so the button needs no icon markup at all:

```diff
  <div class="form-control-group">
    <input type="password" class="form-control">
-   <button type="button" class="form-control-action" data-coreui-toggle="password" aria-label="Toggle password visibility">
-     <span class="form-password-action-icon"></span>
-   </button>
+   <button type="button" class="form-control-action" data-coreui-toggle="password" aria-label="Toggle password visibility"></button>
  </div>
```

- `.form-password-action-icon` is gone, and `scss/forms/_form-password.scss`
  with it. That takes **2.5 kB of URL-encoded SVG out of the stylesheet** — it
  was there for every page, whether or not one had a password field.
- `$form-password-icon-show` / `$form-password-icon-hide` and the matching
  `--cui-form-password-icon-*` properties are gone. Supply your own artwork
  through the new `showIcon` / `hideIcon` options instead, the way the other
  adornments already take theirs. Both are sanitized; `allowList`, `sanitize`
  and `sanitizeFn` control that.
- The plugin now initializes on `DOMContentLoaded` for markup carrying
  `data-coreui-toggle="password"`, so the icon is present without any script of
  your own — the same data-API pass Chip, Chip Set, Chip Input and Search
  Button already make.

#### Icons rendered by JavaScript

- New components render their icons as **inline SVG on `currentColor`** (the
  chips pattern) instead of CSS `mask` data-URIs: swap them with the
  `indicatorIcon` / `separatorIcon` options (sanitized with the SVG allowlist),
  recolor them with plain CSS `color`. The corresponding
  `$date-picker-*-icon`/`-icon-size` Sass variables disappear with the v1
  shells.
- **The calendar navigation icons moved to JavaScript too.** The four
  `$calendar-nav-icon-{prev,next,double-prev,double-next}` Sass variables are
  **removed**, along with the CSS custom properties and mask rules that painted
  them. Customize them with the new `navIconPrev` / `navIconNext` /
  `navIconDoublePrev` / `navIconDoubleNext` calendar options instead (inline SVG,
  sanitized). `$calendar-nav-icon-width/-height/-color/-hover-color` stay — the
  icon inherits `color`, so recoloring is plain CSS.
- **`Calendar`'s default `allowList` is now `SVGAllowlist`** (was
  `DefaultAllowlist`), so the component can render its own inline SVG icons —
  and custom cell renderers may return SVG as well. Strictly more permissive;
  scripts and event handlers are still stripped.
- **Directional icons are resolved in JavaScript, not CSS.** v1 swapped the
  range separator with a second Sass variable
  (`$date-picker-separator-icon-rtl`) applied through an RTL mask; v2 picks
  between `separatorIcon` and `separatorIconRtl` when it renders, based on the
  element's computed direction — so a `dir="rtl"` ancestor works, not just a
  document-level direction. The calendar mirrors its prev/next icons the same
  way. **Consequence for custom code:** a component that resolves directional
  icons at construction time must be in its final DOM position when it is
  created — a detached element has no computed direction (the calendar falls
  back to the nearest `[dir]` ancestor, but placement first is the reliable
  path).

#### Range / Range Slider

- **A theme beats `--cui-range-thumb-bg`, as everywhere else.** The token carried
  the `--cui-theme-*` slot inside its own default, so setting it inside a themed
  container dropped the theme. The slot sits on the property now.
- **`--cui-range-slider-label-padding-x`/`-y` reach the label.** Both were
  declared and nothing read them, so the knob existed and did nothing. They
  default to `0`, so no label moves.

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The pressed thumb adapts to the color mode.** Its color was 70% white
  mixed into the theme color at build time, so in dark mode the pressed
  thumb flashed a near-white pastel. It now mixes toward `--cui-body-bg` at
  runtime — identical in light mode, dark and correct in dark mode.
- **Both sliders are themeable**: the filled track and the thumbs read the
  theme slots, so a `.theme-*` class recolors them; without one they stay
  on primary as before.

#### ScrollSpy

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The deprecated `offset` option is removed** — it has been a thin alias
  since the IntersectionObserver rewrite. Use `rootMargin` instead; the exact
  equivalence is `offset: 100` &rarr; `rootMargin: '100px 0px -30%'`.

#### Tab

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **Constructing a Tab outside a tab-panel parent now throws a `TypeError`**
  instead of silently returning a half-initialized instance, matching upstream.
  The silent variant hid real markup mistakes: the instance existed but never
  activated anything.
- The `data-coreui-toggle="pill"` and `"list"` toggles **stay** — they are
  documented markup, and v6 keeps documented markup working.
- **`$nav-link-transition` splits into
  `$nav-link-transition-property`/`-duration`/`-timing`**, emitted as
  `--cui-nav-link-transition-*`. The link's transition was compiled into its rule
  while `.tab-pane` in the same file already read the three-token form, so half
  the file could be retimed in the browser and half could not. Setting
  `--cui-nav-link-transition-duration` now takes effect; before it was ignored.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`.nav-link` is a flex row, and it fills on hover and when active.** The link
  lays its children out with `--cui-nav-link-gap`, `--cui-nav-link-align` and
  `--cui-nav-link-justify`, so an icon and its label line up without a wrapper.
  It also takes `--cui-nav-link-hover-bg` and `--cui-nav-link-active-bg`, rounded
  by `--cui-nav-link-border-radius` — the base nav used to change text color
  alone. Set the two backgrounds to `transparent` to keep the old look.
  Under a theme, hover reads `--cui-theme-fg` and the lighter
  `--cui-theme-bg-subtle`, and the active item the darker `--cui-theme-bg-muted`,
  so hovering a link never outweighs the selected one.
  `.nav-tabs`, `.nav-underline` and `.nav-underline-border` square the link off,
  and the two underline variants take neither fill, hover or active: they mark
  their state with a line, and a radius curves that line's ends while a fill says
  the same thing twice.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`.nav-tabs` draws its line with an inset `box-shadow`, not a border.** The
  links no longer pull themselves over the container's border with a negative
  `margin-bottom`; each link carries its own bottom border (the line colour at
  rest, the panel colour when active) and the container paints the line as
  `box-shadow: inset 0 calc(-1 * var(--cui-nav-tabs-border-width)) 0
  var(--cui-nav-tabs-border-color)`. The rendered result is pixel-identical,
  but custom CSS targeting `.nav-tabs`' `border-bottom` or the links' negative
  margin needs a second look; recolour the line through
  `--cui-nav-tabs-border-color`. `.card-header-tabs` compensates with a deeper
  negative margin instead of zeroing the border.
- **`--cui-nav-gap` is new**, declared on `.nav` and defaulting to `0`, so the
  base nav renders exactly as it did. It gives the token a home on the component
  whose name it carries: `.navbar-nav` already overrode it, and `.nav-underline`
  keeps its own `--cui-nav-underline-gap`.

#### Tooltip

- **`--cui-tooltip-opacity` now blends into the background colour instead of
  fading the whole element.** The old element-level `opacity: .9` also faded the
  label text, compositing it below the WCAG 1.4.3 contrast minimum (about
  3.5&#8758;1). The surface and arrow keep the same translucent look; the text
  renders at full opacity. The token still works — override it and only the
  background alpha changes.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`$tooltip-margin` and `--cui-tooltip-margin` are removed.** The variable
  had been `null` and deprecated since v4; the token compiled to an empty
  value and the `margin` declaration reading it never took effect. Position
  a tooltip with the JS `offset` option instead.

#### OTP input

- **A code delivered by SMS autofill or a password manager now fills the whole
  field.** Only the first slot carries `autocomplete="one-time-code"` (the rest
  are `off`), and a multi-character value arriving in any slot is spread across
  the field, as a paste already was. Previously such a value stayed in one slot
  and the submitted value was empty. The slots also gained `enterkeyhint`,
  `autocorrect="off"` and `spellcheck="false"`.

#### Alert

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **Every alert fades out when dismissed, and `.fade` no longer decides that.**
  The alert carries its own transition and
  `--cui-alert-transition-property` / `-duration` / `-timing`; the JavaScript
  marks it with `.hiding` for the length of it, then removes the element. An
  alert is already on the page, so only the exit is animated — `.fade` and
  `.show` remain the way to fade one **in** when you insert it at runtime. Add
  `.alert-instant` to an alert that should go at once, which is what an alert
  without `.fade` used to do.

- **`.alert-dismissible` is optional now.** An alert that contains a close
  button as a direct child makes room for it and positions it on its own
  (`.alert:has(> .btn-close)`). The class keeps working — and is still the way
  to go when the button is injected later or sits inside a wrapper — so no
  existing markup changes.

#### Chip / Chip set / Chip input

- **Chips expose real roles now.** A selectable chip set is a horizontal
  `role="listbox"` (with `aria-multiselectable` in multiple mode) whose chips
  are `role="option"` elements carrying `aria-selected`; a standalone
  selectable chip is a toggle button (`role="button"`) reflecting its state
  via **`aria-pressed` instead of `aria-selected`**; a non-selectable set is a
  `role="group"`. `aria-disabled` is only stamped on chips that carry a role —
  on a role-less chip the attribute was invalid and is now removed.
- **Adding and removing chips is announced.** Chip set and Chip input render a
  visually hidden `role="status"` region next to the container; the wording is
  configurable via `ariaAddedAnnouncement`/`ariaRemovedAnnouncement`.
- **Chip input: `aria-disabled`/`aria-readonly` are no longer stamped on the
  container.** The container is a generic element, so those attributes were
  invalid on it (axe `aria-allowed-attr`); the native `disabled`/`readonly`
  states on the inner `<input>` carry the semantics.
- **The remove button gets its size back, and `.chip-sm`/`.chip-lg` resize
  everything they claim to.** `.chip-remove` sized itself from a token that was
  never declared, so both dimensions were invalid at computed-value time and fell
  to `auto` — the button measured 0x0 at every chip size. It reads
  `--cui-chip-remove-size` now (16px, 14px on `.chip-sm`, 20px on `.chip-lg`), so
  a chip with a remove button is wider than it was.
- **`.chip-dismiss` is `.chip-remove`.** The rename landed with the component; a
  single selector kept the old name and styled nothing, so a disabled chip input
  never reached its remove buttons through CSS. The button's `disabled` attribute
  was doing the work on its own.
- **`--cui-chip-dismiss-size` is gone; use `--cui-chip-remove-size`.** The size
  classes wrote the first name and the glyph read the second, so the remove icon
  stayed at its base size in every chip size. Nothing read the old token, so an
  override of it never did anything.
- **`.chip-sm` and `.chip-lg` no longer swap the image and icon sizes.** They
  passed the two to `chip-size()` in the wrong order, so a large chip rendered its
  icon at 24px and its image at 20px — the reverse of the base sizes, where the
  image is the larger of the two. Large is now 24px image / 20px icon and small
  16px / 14px.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The selected chip's text follows the palette.** `$chip-active-color` was
  white at 87% opacity, computed at build time — repaint the selected
  background and the text stayed near-white. It defaults to
  `var(--cui-primary-contrast)` now (solid, slightly brighter than before),
  and a `.theme-*` class supplies its own contrast colour through the slot.
- **Hovering a themed, unselected chip no longer previews the selected
  look.** The background steps from `bg-subtle` to `bg-muted` and the text
  colour stays put; only selection paints the solid theme colour. A chip
  without a theme class hovers exactly as before.

#### Collapse

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The `toggle` option is gone.** It made the constructor change the state the
  markup declares, which surprised people — so nearly every caller passed
  `toggle: false`. The constructor now always keeps the declared state; add
  `.show` to start open, and call `show()`, `hide()` or `toggle()` to change it.

  ```diff
  - const collapse = new coreui.Collapse('#myCollapse', { toggle: false })
  + const collapse = new coreui.Collapse('#myCollapse')
  ```

  Callers that relied on the constructor toggling need an explicit call:
  `new coreui.Collapse(el).toggle()`. `data-coreui-toggle` on a *trigger* is
  unrelated and unchanged.

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **Triggers no longer get the `.collapsed` class.** Their state was written
  twice, as the class and as `aria-expanded`, and only the second is required.
  Nothing in the stylesheet had matched the class since the accordion stopped
  using it, so it survived as a hook for custom CSS — style the attribute
  instead, which is also what assistive technology reads:

  ```diff
  - .accordion-button.collapsed::after { transform: rotate(-90deg); }
  + [data-coreui-toggle="collapse"][aria-expanded="false"]::after { transform: rotate(-90deg); }
  ```

- **New `hiddenUntilFound` option.** With `data-coreui-hidden-until-found="true"`
  a collapsed area is hidden with `hidden="until-found"` rather than taken out
  of the layout, so the browser's find-in-page searches it and expands it on a
  match; the component then syncs `.show` and `aria-expanded` so the declared
  state follows what the reader sees. Off by default, and below Chrome 102 /
  Firefox 148 / Safari 26.2 it hides the content the way `hidden` always did.

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The transition is set through CSS variables, and the Sass variables split
  in two.** `$transition-collapse` and `$transition-collapse-width` were
  shorthands carrying the property, the duration and the easing at once, which
  meant retiming a collapse required restating the property. They are replaced
  by `$transition-collapse-property`, `$transition-collapse-duration` and
  `$transition-collapse-timing`, emitted as `--cui-transition-collapse-property`
  / `-duration` / `-timing` on `.collapse` and `.collapsing`, so all three can
  also be changed per instance at runtime. `$transition-fade` splits the same
  way into `$transition-fade-duration` / `$transition-fade-timing`.

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **CSS owns the collapse animation, and the class choreography follows.**
  Where `interpolate-size: allow-keywords` is supported the stylesheet
  interpolates the size to the `auto` of the open state on its own; elsewhere
  JavaScript measures the two sizes and the stylesheet still times the move.
  Three observable changes come with that:

  - **`.collapse` never leaves the element.** It used to be swapped out for
    `.collapsing` while the transition ran; now `.collapsing` is added
    alongside it, so `.collapse.collapsing` matches during a run and a selector
    keying on the *absence* of `.collapse` no longer fires mid-animation.
  - **`.show` toggles at the start of both directions.** It used to land at
    the end of the opening transition. A rule styling `.collapse.show` applies
    for the whole expansion now, and its absence marks the whole closing run.
  - **An open `.collapse-horizontal` is `fit-content` wide, not as wide as its
    container** — the open size is the animation's target, and a target of
    `auto` would spend most of the run growing an empty box past the content.
    This also removes the end-of-animation jump to full container width the
    measured animation used to make. Style the child, as the docs always
    showed, and nothing changes.

#### Button

- **A toggle button always exposes `aria-pressed` now.** The attribute has no
  default value, so a `[data-coreui-toggle="button"]` that shipped without one
  was announced as a plain button until the first click. JavaScript adds the
  missing attribute on `DOMContentLoaded`, reading the `.active` class to pick
  the value; an attribute you wrote yourself is left alone. Write it in your
  markup anyway, so the state is correct before our JavaScript runs.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`.btn` is a flex container.** It lays its content out in a row, centres it
  on both axes and separates the parts with `--cui-btn-gap`, so an icon next to
  a label no longer depends on a whitespace text node in your markup — and no
  longer gets a second space where you did leave one. `--cui-btn-min-height`
  keeps a button that holds only an icon as tall as one that holds text. Custom
  CSS that positioned button content with `display`, `line-height` or margins
  needs a second look; the caret of a `.dropdown-toggle` now takes its distance
  from the gap instead of its own margin.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **A button label no longer wraps.** `--cui-btn-white-space` is `nowrap`. In v5
  `$btn-white-space` was `null`, so no declaration was emitted at all and a long
  label broke onto a second line, leaving the button taller than the ones beside
  it — while the variable's own comment told you to set `nowrap`, which is to say
  the default was the one nobody wanted. A long label now keeps the button one
  line tall and makes it wider instead.
- **`.btn-toolbar` spaces its groups on its own** with a `.5rem` `gap`
  (`--cui-spacer-2`). Drop the `me-*` utilities that carried the spacing in
  v5, or they now add to the gap.

  It is still a token, so the old behaviour is one declaration away — on a single
  button, on a theme, or globally:

  ```css
  .btn-that-wraps { --cui-btn-white-space: normal; }
  :root { --cui-btn-white-space: normal; }
  ```

  In Sass, `$btn-white-space: normal`. The token is declared on `.btn` itself, so
  an override has to reach the button — setting it on an ancestor is not enough.

  Look at rows that hold several buttons: a flex row without `.flex-wrap` grows
  wider now instead of taller, so add it where the group should break onto a
  second line rather than push the layout out.
- **`.btn-icon` (new).** A button that holds nothing but an icon: no padding,
  and its width follows its height, so it stays square at every size.
- **A variant is a shape, the colour is a theme.** `.btn-solid`, `.btn-outline`,
  `.btn-subtle` (new) and `.btn-ghost` take their colour from a `.theme-*` class
  on the button or on any element above it, and each carries the base button
  styles on its own — `.btn` is no longer required next to them:

  ```diff
  - <button class="btn btn-primary">Save</button>
  + <button class="btn-solid theme-primary">Save</button>
  ```

  **The colour classes keep working** and stay the spelling the docs use:
  `.btn-primary` is `.btn-solid.theme-primary`, `.btn-outline-primary` is
  `.btn-outline.theme-primary`, and `.btn-subtle-*` completes the set. What
  changes is that one rule per variant now serves every colour, so a theme
  colour of your own gets the whole set for free.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **A bare `.btn` is a neutral button, not an invisible one.** It renders in the
  surface colours (`--cui-bg-4`, one step darker on hover) instead of
  being transparent and unstyled. Buttons that carry a variant or a colour class
  are unaffected. For the old behaviour use `.btn-ghost`, which is transparent
  by design.
- **`.btn-xs` (new).** A fourth size below `.btn-sm`, reading the shared
  `--cui-btn-input-xs-*` tokens.

#### Navbar

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`.navbar-expand-*` reads the navbar's own width, not the viewport's.** Every
  `.navbar` is a [query container](/utilities/container-queries/) now, so a
  navbar in a sidebar or a narrow dashboard column collapses there while a
  full-width one on the same page stays expanded. For a navbar that spans the
  page — which is most of them — nothing changes, because its width *is* the
  viewport's.
- **`flex-wrap: nowrap` and `justify-content: flex-start` moved from
  `.navbar-expand-*` onto its inner `.container*`.** A container query styles
  descendants of the container, never the container itself, and the inner
  container is where those two properties took effect anyway (the navbar's
  children inherit `flex-wrap`). A navbar written **without** an inner
  `.container`, `.container-fluid` or `.container-{breakpoint}` no longer gets
  them — wrap its content, the way every example in these docs does.
- **`--cui-navbar-text-padding-y` and `--cui-navbar-toggler-icon-size` are new.**
  The padding that lines `.navbar-text` up with the nav links, and the size of the
  hamburger glyph, were both compiled into their rules. The padding could not be
  matched from outside at all: the value it pairs with, `--cui-nav-link-padding-y`,
  is declared on `.navbar-nav`, which is `.navbar-text`'s sibling and therefore
  invisible to it. Both are declared on `.navbar` now, at their current values.
- **An expanded navbar flattens a `.drawer`, not just an `.offcanvas`.** The
  reset that turns the collapsed panel back into an inline nav named `.offcanvas`
  only, so a `.drawer` inside a `.navbar-expand-*` stayed a fixed side panel over
  the page at every width — measured at 400×868 next to the offcanvas's 1176×24.
  Both are handled now.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **Three navbar defaults move.** `.navbar` takes
  `--cui-navbar-min-height: 3.5rem`, so a navbar with short content no longer
  collapses below the height of one with a brand in it. `.navbar-brand` takes
  `--cui-navbar-brand-font-weight`, defaulting to medium rather than the body
  weight. `.navbar-nav` takes `--cui-nav-gap`, a `.25rem` gap between links that
  the link padding used to carry alone. Set any of the three to its old value to
  keep the previous rendering.
- **`.navbar-translucent` is new.** It tints and blurs the navbar the way
  `.toast-translucent` does for a toast, mixing `--cui-navbar-bg` — a new token,
  defaulting to the body background — at 85%.
- **A theme beats a navbar token, as everywhere else.** `--cui-navbar-brand-color`,
  `-brand-hover-color` and `-active-color` carried the `--cui-theme-*` slot inside
  their own default, so setting one of them inside a `.theme-{color}` navbar
  dropped the theme. The slot sits on the property now, so the theme wins — the
  same order every other component follows.

#### Checkbox, radio and switch: the class moved onto the input

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

`.check`, `.radio` and `.switch` go on the `<input>` itself. There is no wrapper
and no second element: `appearance: none` lets the control render a
pseudo-element, so the mark is drawn on the input, and its colour is a token
(`--cui-check-mark-color`) rather than a value baked into an SVG. The
separate dark-mode switch artwork is gone with it — a thumb painted from a token
follows the colour scheme by itself.

```diff
- <div class="form-check">
-   <input class="form-check-input" type="checkbox" id="c">
-   <label class="form-check-label" for="c">Label</label>
- </div>
+ <div class="form-field">
+   <input class="check" type="checkbox" id="c">
+   <label for="c">Label</label>
+ </div>
```

**The v5 spelling still works.** `.form-check`, `.form-check-input`,
`.form-check-label`, `.form-switch` and `.form-check-inline` are kept as a
compatibility layer — **aliases of the new controls**, not a second
implementation, so there is one engine to maintain and the old markup lays out
exactly as it did. Verified by measuring geometry across six markup variants and
eight dimensions each: zero differences. It is deprecated in v6 and removed in
v7. Set `$enable-deprecated-form-check: false` to leave it out of your build once
your markup has moved; that takes **455 bytes gzip** off the stylesheet and
leaves no `.form-check*` selector behind.

`.btn-check` is **not** part of that layer — toggle buttons are a current
feature, and they live with the buttons now rather than with the form check.

The variables that shape the wrapper moved with it, into `forms/_form-check.scss`,
and go when it does:

**Five Sass variables shaped the old artwork and cannot be honoured any more**,
because the compatibility layer draws through the new engine:
`$form-check-input-checked-bg-image`, `$form-check-radio-checked-bg-image`,
`$form-check-input-indeterminate-bg-image` and `$form-check-transition`. Their
replacements are `--cui-check-mark-checked`,
`--cui-radio-mark`, `--cui-check-mark-indeterminate` and the
controls' own transition tokens. `$form-check-label-color` and
`-cursor` keep working. `$form-check-btn-check-disabled-opacity` goes with the
toggle button's move to the buttons — it duplicated `$btn-disabled-opacity`,
which is now what the disabled toggle reads, through
`--cui-btn-disabled-opacity`.

<span class="badge text-danger-emphasis bg-danger-subtle">Removed</span>
**`.form-check-reverse` is gone.** It right-flushed the label and the control as
a pair — which `order` utilities express directly — and it was never the settings
row (label on the left, control on the right) that people actually reach for;
that one is `justify-content: space-between`. The React and Vue `reverse` prop
still emits the class and therefore stops having an effect; it is retired with
those components in the framework editions.

What replaces the wrapper's modifiers:

| v5 | v6 |
| --- | --- |
| `.form-check` (layout) | [`.form-field`](/forms/field/), or nothing if you only need the control |
| `.form-check-label` | a plain `<label>` |
| `.form-check-inline` | a flex row: `.d-flex.gap-3` |
| `.form-check-reverse` | `justify-content: space-between` on the field, or `order` utilities to swap the pair |
| `.form-switch-lg` / `-xl` | `.switch-lg` / `.switch-xl` |

**The switch is sized by one token, and gains `.switch-sm`.** `--cui-switch-width`
is derived from `--cui-switch-height` through the new
`$switch-aspect-ratio` — a plain number, multiplied in the browser — so a size
sets the height alone. The size classes now
scale the label as well, matching `.check-sm` / `.radio-lg`. `$switch-sizes`
replaces the width/height pairs, and the deprecated `.form-switch-lg` / `-xl`
read it too — `$form-switch-widths` is gone. Those two classes render exactly
as `.switch-lg` / `.switch-xl` now, so they grow a little: the track was
1.25em / 1.5em tall on a 2:1 ratio, and is 1.5rem / 1.75rem on the library's
1.75 ratio.

**Fixed: the switch animates again.** `--cui-switch-transition` carried a
property name inside it (`background-position .15s ease-in-out`, inherited from
v5's `$form-switch-transition`), so `transition: inset-inline-start var(…)`
resolved to something invalid and every switch transition was dropped. It is two
tokens now — `--cui-switch-transition-duration` and
`-timing` — and the thumb slides rather than the background position.

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
**The switch is redrawn.** The track is 1.25rem tall with a 1.75 aspect ratio
(was a 2:1, font-relative `em` track), pill-radiused, on the tertiary surface
with an inset shadow; the thumb is white with a drop shadow and turns
contrast-coloured when checked. A disabled unchecked switch swaps to the
disabled surface with a faded thumb instead of dimming wholesale; a checked one
dims. `--cui-switch-border` splits into `-border-width` and
`-border-color`, and `$form-switch-color`, `$form-switch-width` and
`$form-switch-border-radius` fed only the old look and are removed. The
deprecated `.form-switch-lg` / `-xl` are redrawn with the rest.

**The controls animate on shared knobs.** `:root` carries
`--cui-control-transition-duration` and `-timing` (an overshoot easing);
the checkbox tick and the radio dot pop in on them, the boxes' colours animate,
and the switch thumb slides on the same pair — the three controls move in sync
and restyle from one place. Reduced motion disables all of it as usual.

**New: checkbox and radio have sizes.** `.check-sm` / `.check-lg` and
`.radio-sm` / `.radio-lg` — v5 had none, only the switch was sizeable. Each sets
one custom property; the mark scales with the box and the alignment margin is
computed from the same value, so any size you set yourself stays on the text's
optical centre too.

Multi Select's option indicators moved with it — they render as a decorative
`.check` now, so a build with the compatibility layer off still draws them.

#### Checkbox, radio and switch: one page became four

- **Each control now owns its custom properties.** `--cui-checkbox-*`,
  `--cui-radio-*` and `--cui-switch-*` feed the shared implementation
  at runtime, so restyling checkboxes no longer drags radios along and no longer
  needs a Sass rebuild. Set them **on the control** — a token an element declares
  for itself cannot be overridden from an ancestor. The old
  `--cui-form-check-*` properties still exist and still work; they are the
  shared layer underneath.
- **The control stays on the text baseline when you resize it.** Its `margin-top`
  used to be Sass arithmetic over `$form-check-input-width`, so changing the width
  token at runtime moved the box off the line. It is a `calc()` over the size
  token now.
- **Sized switches are token overrides.** `.form-switch-lg` / `-xl` set
  `--cui-switch-width` and `--cui-switch-height` instead of writing
  their own geometry, so a size the map does not name is two custom properties
  rather than a Sass recompile.
- The Sass variables behind all of this moved into `scss/forms/_checkbox.scss`,
  `_radio.scss` and `_switch.scss`. `$form-check-*` and `$form-switch-*` keep
  working — the new per-control variables default to them.

- **The docs split.** `/forms/checks-radios/` is now
  [Checkbox](/forms/checkbox/), [Radio](/forms/radio/) and
  [Switch](/forms/switch/) — one page per control, each self-contained down to its
  own toggle-button and Sass sections. The old URL redirects to Checkbox.
  **No classes changed**: `.form-check`, `.form-check-input`, `.form-check-label`,
  `.form-switch` and `.form-check-inline` all work exactly as before;
  `.form-check-reverse` is removed.
- **New: [`.form-field`](/forms/field/)**, a grid wrapper that lays a control out
  with its label, description and validation feedback on one consistent gap, so a
  form is spaced by the field instead of by margin utilities on its parts. A bare
  `.form-check-input` (one written without its `.form-check` wrapper) switches the
  field to a two-column layout through `:has()`.

#### Stacks

- **New: `.hstack{-sm|-md|-lg|-xl|-xxl}` and `.vstack{-sm|-md|-lg|-xl|-xxl}`** switch
  direction at a breakpoint. The breakpoint is the width of the nearest query
  container, so mark an ancestor with the new `.stack-container` (or the
  [`.contains-inline`](/utilities/container-queries/) utility) — without one the
  direction never switches. Plain `.hstack` and `.vstack` are unchanged, including
  `.hstack`'s vertical centring and its shrink-to-content width.

#### Images and figures

- **`--cui-thumbnail-*` and `--cui-figure-caption-*` are declared, not just
  read.** They existed only as the fallback arm of a `var()` call, so nothing
  reported them and an override had to guess the name. `.img-thumbnail` and
  `.figure-caption` declare their full set on the element, padding, border width
  and caption font size included.
- **`--cui-figure-img-margin-bottom` is new.** The gap between a figure's image
  and its caption was compiled into the rule, so the only way to change it was to
  rebuild from Sass. `.figure-img` declares it now, and it is the one figure
  measurement you can retune in the browser.

#### Figures

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`.figure` is an inline flex column and spaces its parts with
  `--cui-figure-gap`.** `$figure-img-margin-bottom` and
  `--cui-figure-img-margin-bottom` are gone — the gap (knob: `$figure-gap`,
  same `.5rem`) replaces the image's bottom margin, and `.figure-img`
  carries no styles at all any more — keep it in your markup or drop it,
  both render the same. Documented markup renders pixel-identically;
  an `<img>` without width/height attributes can now stretch to a wider
  caption (flex `stretch`), so give figure images explicit dimensions —
  which they need anyway to avoid layout shift.

#### Reboot

- **Links change color on hover.** `--cui-link-hover-color` was declared and
  read by navs and pagination, but a plain `<a>` only ever changed its underline.
  It now switches color as well, and inside a themed surface it hovers to
  `--cui-theme-fg-emphasis`.
- **The underline sits `.2em` below the text.** `<a>` reads the new
  `--cui-link-underline-offset` token (knob: `$link-underline-offset`), so
  underlines clear descenders instead of cutting through them. The
  `.link-offset-*` utilities and `.icon-link` still override it per element;
  set the token to `auto` for the old browser default.
- **`accent-color: var(--cui-primary)` on `:root`.** Native controls we don't
  restyle — a bare checkbox, radio, range or `<progress>` — follow the brand
  color instead of the browser's blue.
- **Every segment of a date or time input gets its padding removed.** The list
  covered five pseudo-elements and one of them (`::-webkit-datetime-edit-minute`)
  had been renamed by browsers years ago; seconds, milliseconds, the week number
  and the AM/PM field were never in it. `<input type="time" step="1">` no longer
  renders taller than a text input.
- **`tel`, `url`, `email` and `number` inputs stay LTR everywhere.** The rule was
  scoped to `[dir="rtl"]` elements, so it missed pages that set the direction on
  `<html>` through the language rather than the attribute.
- `pre` reserves scrollbar space (`scrollbar-gutter: stable`), so a horizontal
  scrollbar no longer covers the last line of a code block.
- **Reboot's type and spacing are CSS variables on `:root`.** Heading margin,
  family, style, weight and line height, paragraph margin, `hr`, `legend`, `dt`,
  `sub`/`sup`, `mark` padding, the code font size and `--cui-list-padding-x` are
  declared rather than compiled in, so a subtree can be retyped without a class.
  `<kbd>` carries its own set on the element, `--cui-kbd-border-radius`
  included.
- **`.h1`–`.h6`, `.small`, `.mark` and `.initialism` are defined in Reboot**,
  next to the elements they mirror, instead of `@extend`-ing them from
  `_type.scss`. Only `.initialism` changes cascade layer (`content` → `reboot`);
  the others were already emitted there, because `@extend` hoists a class to
  wherever the extended selector is defined. `_type.scss` keeps `.lead` and
  `.display-*` and no longer depends on the Reboot module.
- **Hardcoded spacing in Reboot now reads the `--cui-spacer-*` scale**
  (`address`, `ol`/`ul`/`dl`, `dd`, `blockquote`, `pre`, `figure`). Values are
  unchanged.

#### Floating labels

- **The label may now come first.** `.form-floating` matches the control's state
  in both directions — forward from the label with `:has()`, backward from the
  control with `~` — so `<label>` before the control floats and disables exactly
  like the v5 order, which keeps working. Writing the label first lets a screen
  reader announce it before the field's value, and the docs examples do.
- **A textarea's label stays at the top.** The label is a flex box centred on the
  control, and `label:has(~ textarea)` anchors it to the start instead, so it
  floats correctly however tall the textarea is.

#### Lists

- **`--cui-list-inline-padding` is new.** The gap between `.list-inline-item`s was
  compiled into the rule, so respacing an inline list meant rebuilding from Sass.
  `.list-inline` declares it, at the same `.5rem`.

#### Tables

- **`.table-responsive*` is a query container.** It still scrolls horizontally
  below its breakpoint; the addition is that things inside it can now respond to
  its width.
- **New: `.table-stacked{-sm|-md|-lg|-xl|-xxl}`** turns rows into stacked blocks
  below the breakpoint, reading the width from the `.table-responsive*` wrapper.
  Give every `<td>` past the first a `data-cell` attribute for its label; the
  header is hidden visually and kept in the accessibility tree. See
  [Stacked tables](/content/tables/#stacked-tables).
- **Cell padding, vertical alignment and the border width are CSS variables
  now.** `--cui-table-cell-padding-y`, `--cui-table-cell-padding-x`,
  `--cui-table-cell-vertical-align`, `--cui-table-border-width` and
  `--cui-table-group-separator-color` are declared on `.table` instead of being
  compiled into the cell rule. This also fixes stacked tables, which read
  `--cui-table-cell-padding-*` and `--cui-table-border-width` while nothing
  declared them, so their rows collapsed to zero padding and lost the separating
  line.
- **`.table-sm` sets the padding variables** on the table instead of overriding
  the padding on every cell. Anything that raised specificity to beat
  `.table-sm > :not(caption) > * > *` can set `--cui-table-cell-padding-y`/`-x`
  instead.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The contrast factors are percentages.** `$table-striped-bg-factor`,
  `$table-active-bg-factor` and `$table-hover-bg-factor` changed from unit-less
  fractions (`.05`) to percentages (`5%`), because they now ship as the
  `--cui-table-*-bg-factor` variables that `color-mix()` reads at runtime.
- **The state colours follow `--cui-table-color`.** `--cui-table-striped-color`,
  `--cui-table-active-color` and `--cui-table-hover-color` default to
  `var(--cui-table-color)`, and the matching backgrounds are mixed from it, so a
  variant only has to set `--cui-table-color`, `--cui-table-bg` and
  `--cui-table-border-color`.

#### Blockquote

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The source line reads `--cui-secondary-color`.** `.blockquote-footer` was
  painted with `--cui-gray-600`, a fixed value that never flipped with the
  colour mode: 4.15:1 on the light background and 3.65:1 on the dark one, both
  under the 4.5:1 minimum. The secondary colour is defined per mode and clears
  the threshold in both.
- **The quote lays its children out with flex and `gap`.** Spacing inside a
  multi-paragraph quote is `--cui-blockquote-gap` rather than each paragraph's
  own bottom margin, and `.blockquote > :last-child { margin-bottom: 0 }` is
  gone with the margins it existed to cancel.
- **The footer no longer pulls itself up with a negative margin.** A quote
  followed by `.blockquote-footer` drops its own bottom margin instead
  (`:has()`), so the two spacings can be set independently:
  `--cui-blockquote-margin-y` and `--cui-blockquote-footer-margin-y`.

#### Toast

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The fade moved to CSS.** Toast was the last component driving its animation
  from JavaScript — it toggled `.fade`, forced a reflow, then juggled `.show`,
  `.showing` and a deprecated `.hide` class to fake an exit. Menu and the picker
  popup already express this with `@starting-style` and a discrete `display`
  transition, and Toast now does the same. JavaScript only toggles `.show`.
  - The `animation` option and `data-coreui-animation` are gone. Add
    `.toast-instant` to skip the animation.
  - `.showing` and the deprecated `.hide` class are gone, and toasts no longer
    get the generic `.fade` class. Replace any CSS or tests that depend on them.
  - The transition is tuned with `--cui-toast-transition-duration` and
    `--cui-toast-transition-timing`.
  - `isShown()` returns `false` as soon as `hide()` is called, rather than when
    the fade-out ends.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **Toasts are opaque by default.** `--cui-toast-bg` and `--cui-toast-header-bg`
  resolved to `color-mix(in srgb, var(--cui-body-bg) 85%, transparent)`, so every
  toast let 15% of whatever sat behind it through — with no blur to settle it,
  text underneath read straight through the message. Both now resolve to
  `var(--cui-body-bg)`. Add `.toast-translucent` for the see-through look, which
  puts `blur(5px) saturate(180%)` behind the toast and thins the header to match,
  the same way `.card-translucent` and `.menu-translucent` work.

#### Card

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`.card-header-pills` is gone.** It only pulled the pill row out to the
  header's padding edge, which is wrong for pills — they carry their own
  background, so flush against the header's inner edge they touch the border.
  Drop the class and keep `.nav.nav-pills`.
- **The footer follows the theme colour like the header does.** A themed card
  (`.card.theme-inverse`, say) used to paint the footer's background from the theme
  while leaving its text at the body colour, so the label sank into the fill.
  The footer now reads `--cui-theme-contrast` with `--cui-card-cap-color` as the
  fallback, the same expression the header already used.
- **Every card token now carries a real value.** `--cui-card-title-color`,
  `--cui-card-subtitle-color`, `--cui-card-cap-color`, `--cui-card-color`,
  `--cui-card-height` and `--cui-card-box-shadow` shipped as empty declarations
  (`--cui-card-title-color: ;`), because their Sass variables were `null` and
  interpolating `null` yields an empty string rather than dropping the entry.
  An empty custom property makes every `var()` that reads it invalid at
  computed-value time, so the rendered result happened to be right, but the
  token read as blank in devtools and could not be told apart from one you had
  cleared yourself. They now ship `inherit`, `auto` and `none`, which compute to
  the same thing and make the customization surface inspectable.
- **The last card in a `.card-group` gets its bottom-left corner squared.** The
  rule targeting it was written `> card-footer`, without the leading dot, so it
  matched an element type that does not exist and never applied.
- **A theme class works on a single section, not just the whole card.**
  `<div class="card-header theme-primary">` used to paint white text on a
  neutral header, because the background came from `--cui-card-cap-bg`, a token
  declared on `.card` — a custom property resolves where it is declared, and
  `--cui-theme-base` was set one level below it, on the header. The theme
  indirection moved to the point of use, so each section reads the theme in its
  own scope. A theme class on the `.card` itself behaves exactly as before.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`.card-body` is a flex column.** It spaces its children with
  `--cui-card-body-gap` and zeroes their block margins, so nothing in a card
  needs `.mb-*` to sit correctly any more. Two consequences for existing markup:
  a direct child takes its natural width rather than filling the card (add
  `.w-100` where a block child has to stretch), and `text-align` no longer moves
  a button or a link, because they are flex items — use `.mx-auto` or `.ms-auto`
  instead.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`.card-link` is gone**, along with `--cui-card-title-spacer-y`. Both existed
  to space children the gap now handles; the class's inline margin only ever
  worked because the links were inline. Wrap them yourself:
  `<div class="hstack gap-3">…</div>`.
- **New: `.card-row`** lays a card out along the inline axis, with
  `.card-img-start` and `.card-img-end` for an image cap on either side. It
  replaces the `.row.g-0` + `.col-md-*` recipe, which needed a wrapper per
  section and drew no divider between them.
- **New: `.card-subtle`** swaps the theme's solid fill for its subtle
  background, border and emphasis text.
- **New: `.card-translucent`** blurs and saturates whatever is behind the card
  and thins out the caps to match. Tuned at build time through
  `$card-translucent-bg-opacity`, `$card-translucent-cap-bg-opacity` and
  `$card-translucent-backdrop-filter`.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`.card-group` attaches its cards from a container query, not a media
  query.** The `sm` breakpoint is now the width of the nearest query container,
  which is what a group inside a column actually has to fit — the viewport
  being wide never meant the group was. Mark an ancestor with
  [`.contains-inline`](/utilities/container-queries/); without a container the
  query has nothing to read and the cards stay stacked at every width.

#### List group

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`.list-group-horizontal-{sm|md|lg|xl|xxl}` turns horizontal from a
  container query.** Same change and same fix as `.card-group`: put
  [`.contains-inline`](/utilities/container-queries/) on an ancestor, or the
  list stays vertical. Plain `.list-group-horizontal` is unconditional and
  needs no container.

#### Tab

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **A tab pane fades on its own — `.fade` on a `.tab-pane` does nothing for
  it.** `.tab-pane` carries the transition and
  `--cui-tab-pane-transition-property` / `-duration` / `-timing`, and
  `@starting-style` supplies the state to fade from. Drop `.fade` from your
  panes; add `.tab-pane-instant` to a pane that should switch without one.
  `.fade` itself stays as a generic helper for your own markup.

- **The pane no longer waits a full transition before it starts fading.** The
  JS added `.show` from inside the callback it had queued on the pane's own
  transition — so it waited out a fade that had not begun, then began it. Both
  classes land in the same frame now, and `shown` waits on the pane, the
  element that actually animates, instead of the tab button, which only
  transitions its colours.

#### Modal

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **A size modifier applies at every viewport.** `.modal-lg` and `.modal-xl`
  were withheld until the `lg` and `xl` breakpoints, so on a tablet a large
  modal was **500 px** — the same as one with no modifier at all — and an
  extra-large modal on a 1100 px screen was 800 px. Both ask for their width
  everywhere now, capped by `max-width: calc(100% - margin * 2)` exactly as
  before, which is what kept horizontal scrollbars away in the first place.
  At 768 px `.modal-lg` goes 500 → 712 px, and at 1100 px `.modal-xl` goes
  800 → 1044 px.

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`.modal-sm` is narrow on phones too.** It used to fall back to the default
  width below the `sm` breakpoint, so on a 360 px screen it filled the width;
  it is 300 px there now. Drop the modifier for markup that should fill a small
  screen.

- **`$modal-sizes` replaces the three breakpoint blocks.** Sizes come from a map
  and a loop, the same shape `.dialog-*` already used — one model for both
  windows instead of two.

#### Pagination

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **A page link is sized from the shared control scale.** Pagination kept its
  own padding values, so `.pagination-lg` did not match `.btn-lg` or
  `.form-control-lg` — it measured **56 px** against their 48. The tokens read
  `--cui-btn-input-*` now, `.page-link` is a centred flex box with
  `--cui-pagination-min-height`, and all three sizes line up. The base and small
  sizes are unchanged; the large one loses 8 px of height and some horizontal
  padding.

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`pagination-size()` is removed**, together with
  `$pagination-padding-{x|y}-{sm|lg}` and
  `$pagination-border-radius-{sm|lg}`. Sizes are generated by a loop over
  `$pagination-sizes`; add an entry to it and define the matching
  `--cui-btn-input-<size>-*` values instead of calling the mixin.

- **Keyboard focus keeps the theme colours.** `:focus-visible` read
  `--cui-pagination-focus-color` and `-focus-bg` with no theme slot, so tabbing
  to a link inside `.theme-success` dropped it back to the plain link colour.
  Both now read `--cui-theme-fg-emphasis` / `--cui-theme-bg-subtle` first, like
  every neighbouring state.

- **`$pagination-margin-start` is removed.** The overlap between links is
  `calc(-1 * var(--cui-pagination-border-width))`, so it follows a border width
  changed at runtime instead of the value frozen at build time. The Sass
  conditional that compared the variable against that expression is gone with
  it.

#### Placeholder

- **The two opacities are CSS variables.** `--cui-placeholder-opacity-max` and
  `--cui-placeholder-opacity-min` are declared on `.placeholder` and
  `.placeholder-wave`, and both animations read them, so the resting opacity,
  the glow's pulse and the wave's gradient can be retuned on an instance. They
  were compiled in, and the wave's trough was Sass arithmetic
  (`1 - $placeholder-opacity-min`) resolved at build time — it is
  `calc(1 - var(…))` now.

#### Popover and Tooltip

- **The fade moved to CSS.** Neither component renders the `fade` helper class
  any more; `.show` alone drives the transition, with `@starting-style`
  supplying the state to animate from. `animation: false` renders
  `.popover-instant` / `.tooltip-instant` instead of omitting `fade`, and a
  custom `template` opts out with the same class. The option itself is
  unchanged; only custom CSS targeting `.popover.fade` or `.tooltip.fade` needs
  updating. Tune the motion with `--cui-popover-transition-duration` /
  `-timing` and their tooltip counterparts.

- **A bottom-placed popover's arrow is filled like the header it points into.**
  The arrow sits above the header and was drawn in the body background, so it
  read as a notch cut out of the header strip. It takes
  `--cui-popover-header-bg` when a header follows it, and stays on
  `--cui-popover-bg` when there is none.

- **`--cui-popover-header-color` reads `--cui-heading-color`.** It resolved
  `$headings-color` at build time, so a runtime override of the heading colour
  skipped the popover header. The default is unchanged.

#### Progress

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`$progress-bar-animation-timing` is replaced by `$progress-bar-animation`,
  which carries the keyframes name too.** The stripe animation is a CSS variable
  now — `--cui-progress-bar-animation` — so its speed, easing and keyframes can
  be changed on an instance instead of only at build time. A Sass override that
  passed just the timing (`1s linear infinite`) has to pass the whole shorthand
  (`progress-bar-stripes 1s linear infinite`).

- **The label font size follows `--cui-font-size-sm`.** It was three quarters of
  the body font size, a value only this component used; it is the shared small
  size now, which makes it one step larger. Set `--cui-progress-font-size` to go
  back.

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`.progress-group`, `.progress-group-prepend`, `.progress-group-header` and
  `.progress-group-bars` are removed.** Four classes carried a flex row, a
  100 px label column, a header row and a 2 px gap between bars — all of which
  utilities already do. Use `.hstack` / `.vstack` with a `gap-*` and put the
  label column's width in a style, as the Grouping bars examples now show.

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`.progress-thin` is removed.** It did nothing an inline height does not. Use
  `style="height: 4px"` on the `.progress`, as the Height section shows, or set
  `--cui-progress-height` if you want the stripe geometry to follow the height
  too.

- **`.progress-white` sets tokens, and paints with `currentcolor` instead of
  literal white.** It was painting `background-color` past
  `--cui-progress-bg`, so nothing could adjust it and a theme class on the same
  bar overrode the white. On the coloured cards it is made for, the surrounding
  text colour is the readable one, so the bar renders exactly as before — and on
  a surface whose text is dark, the bar now follows instead of disappearing into
  the background.

#### Spinner

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **Spinners are sized in `em`, not `rem`.** `.spinner-border` and
  `.spinner-grow` are now `1em` square with a `.125em` border, so a spinner
  takes the font size of whatever it sits in instead of being a fixed 32 px
  block. Inside a button or a paragraph it lands at the size you previously had
  to ask for with a modifier; standalone it is half of what it was. Set
  `--cui-spinner-width` / `-height`, or the `$spinner-width` /
  `$spinner-height` Sass variables, to go back to a fixed size.

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`.spinner-border-sm` and `.spinner-grow-sm` are replaced by one
  `.spinner-sm`.** The small variant no longer has to correct the border width,
  so a single class serves both spinners.

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`--cui-spinner-vertical-align` is gone.** Spinners are
  `inline-flex` and assume a flex parent; the `-.125em` baseline nudge it used
  to need no longer applies.

- **The animation timing function is a token.** `.spinner-border` keeps
  `linear`, while `.spinner-grow` now eases with `ease-in-out` instead of
  pulsing linearly. Override
  `--cui-spinner-animation-timing-function` to change either.

- **`.spinner-rotate` is new.** It applies only the rotation, so you can spin
  your own SVG or icon without inheriting the bordered circle.

- **`.btn-loading` sizes its spinner from the button.** `LoadingButton` no
  longer adds a `-sm` class to the spinner it injects; the spinner follows the
  button's font size, so it now scales with `.btn-sm` and `.btn-lg`.

### Helpers

- **`.link-{color}` is gone; a theme class colours a link.** Reboot resolves a
  link's colour from `--cui-theme-fg`, which every `.theme-*` class sets, so the
  colour follows the theme instead of needing its own class:

  ```html
  <!-- v5 -->
  <a href="#" class="link-primary link-underline-opacity-25">Primary link</a>

  <!-- v6 -->
  <a href="#" class="theme-primary link-underline link-underline-opacity-25">Primary link</a>
  ```

  Two things change beyond the class name. The theme slot is a **tone picked for
  text** rather than the raw brand colour — it darkens on a light background and
  lightens on a dark one, where `.link-*` gave the same colour in both, so the
  link is more readable in dark mode and slightly different in light. And the
  underline needs `.link-underline` to carry it; its colour now defaults to
  `currentColor`, so it follows the theme unless you name one with
  `.link-underline-{color}`.

  `.link-body-emphasis` becomes `.text-body-emphasis`.

  The removed classes also computed their `:hover` colour in Sass, which froze it
  at build time — overriding `--cui-primary` at runtime never reached the hover
  state. The theme slots are tokens, so it does.


- **`.ratio` is now a native aspect-ratio utility.** The helper built its ratio from a
  `::before` with a percentage `padding-top`, which required a wrapper and absolutely
  positioned its only child. The class names are unchanged — `.ratio-1x1`, `.ratio-4x3`,
  `.ratio-16x9`, `.ratio-21x9` — but they now set the CSS `aspect-ratio` property on the
  element itself.

  ```html
  <!-- v5 -->
  <div class="ratio ratio-16x9">
    <iframe src="..."></iframe>
  </div>

  <!-- v6 -->
  <iframe class="w-100 ratio-16x9" src="..."></iframe>
  ```

  The wrapper and the bare `.ratio` class are gone; put the ratio class on the element you
  want sized. A custom ratio moves from a percentage to a ratio:
  `--cui-aspect-ratio: 50%` becomes `--cui-ratio: 2 / 1`, on `.ratio-auto`. The
  `$aspect-ratios` map moved from `helpers/_ratio.scss` to `_config.scss` and its values
  are ratios rather than percentages.

### Sass architecture & design tokens

v6 adopts the Bootstrap v6 SCSS architecture: CSS cascade layers, per-component
design-token maps, one shared styling surface for every text control, and
runtime color math in place of precompiled shades. Sass variables remain the
primary customization API — every component knob still works through
`@use ... with()` — but several things below are breaking and are called out
as such.

#### A numeric radius scale replaces the one global radius

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **Components read stops of a radius scale, and most got rounder.** `:root`
  emits `--cui-radius-0` through `--cui-radius-9` (multiples of `$radius`,
  `.5rem` by default) plus `--cui-radius-pill`, and component tokens read
  stops instead of the one global `--cui-border-radius`: buttons, inputs,
  alerts, list groups, tabs, nav links, progress, tooltips, thumbnails,
  callouts, combobox options and the range slider's tooltip sit on
  `--cui-radius-5` (`.5rem`), badges, cards, popovers, dialogs, drawers,
  menus, accordions, toasts, dropdowns and popups on `--cui-radius-7`
  (`.75rem`), pills on `--cui-radius-9` (`1.5rem`).
  Everything that used the `.375rem` default is visibly rounder. To keep a
  component on its old radius, set its own token
  (`--cui-card-border-radius: .375rem`); to retune the whole page, override
  the stops or `$radius`. The `$border-radius(-sm/-lg/-xl/-xxl/-pill)`
  variables and their tokens are unchanged and keep driving the `rounded-*`
  utilities.

#### Interaction surfaces sit two rungs lighter on the ladder

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **Hover, active and disabled surfaces read lighter ladder rungs.** Hover
  states read `--cui-bg-1` (was `--cui-bg-3`), active and disabled states
  `--cui-bg-2` (was `--cui-bg-4`), across list groups, menus, navs,
  pagination, breadcrumb links, the accordion's open header, the file-input
  button and disabled controls; the badge's neutral fill, the popover
  header, the progress track, the avatar fallback and input-group addons
  step down the same way. Interaction feedback is a tint rather than a
  block of gray — the same relationships, two rungs closer to the page.
  Set the component's own token to keep a darker surface.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The neutral button steps down the ladder with everything else.** A `.btn`
  without a theme colour rests on `--cui-bg-2` (was `--cui-bg-4`) and hovers
  on `--cui-bg-3` (was a hard-coded `gray-300`/`gray-700` pair outside the
  ladder); the neutral subtle variant rests on `--cui-bg-2` and the ghost
  variant's hover wash is `--cui-bg-1`. The default button is visibly
  lighter. Its corners also now read `--cui-btn-input-border-radius`
  (`--cui-radius-5`, `.5rem`) instead of the global `--cui-border-radius`,
  so buttons match the fields they sit next to in input groups; `.btn-group`
  clips to the same stop. Set `$btn-bg`/`$btn-hover-bg` or the `--cui-btn-*`
  tokens to keep the old look.

#### Every theme colour gets an action-background slot

`:root` emits `--cui-{color}-bg` for every theme colour, pointing at the
colour's base token. Active and checked states read the slot instead of the
base directly — `--cui-list-group-active-bg`, `--cui-menu-item-active-bg`,
`--cui-pagination-active-bg`, `--cui-nav-pills-link-active-bg`,
`--cui-progress-bar-bg` and `--cui-range-thumb-bg` are all
`var(--cui-primary-bg)` now. The resolved values are unchanged; the slot is a
single place to retune what "filled with the theme colour" means without
touching the base colour that text and borders derive from. (The `secondary`
colour's slot takes over the name of the former surface alias — see the
ladder entry above.)

#### Colour decisions are written, not computed

v6 stops evaluating colours at build time, the way upstream v6 does — Sass
assembles maps of CSS expressions and the browser resolves them.

- **`$theme-colors-contrast` holds written values** instead of
  `color-contrast()` results. The computed and written values are identical, so
  nothing renders differently; the point is that a theme colour no longer has to
  be a Sass colour for the contrast pass to run over it. Upstream keeps a
  `"contrast"` key per colour and never calls the function either.
- **Table variants read the theme tokens.**
  <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  `.table-primary` and friends still exist, but they are generated the way
  `.btn-primary` is: the class sets `--cui-theme-*` and the base `.table`
  rules read it. `$table-variants` is now a **list of colour names**, not a map
  of pre-shifted colours, and `$table-bg-scale` / `$table-border-factor` are
  gone. A theme colour you add yourself now gets a table variant without
  compiling Sass.
  Two visible consequences: the variant background is the colour's
  `bg-subtle` token rather than a `shift-color()` of the base, and striped /
  hover / active are `color-mix()` overlays on the text colour rather than
  opaque mixes — so they compose over the row's own background. Table variants
  also follow colour modes now, where before they stayed on light-palette
  values in dark mode.

#### RGB channel tokens and the elevation system removed

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

- **Every `--cui-{name}-rgb` custom property is gone**, along with the
  `$theme-colors-rgb` and `$theme-colors-rgb-dark` maps, the `to-rgb()`
  function's role in `:root`, and the `rgba-css-var()` helper (now
  `translucent-css-var()`). They existed only so
  `rgba(var(--cui-primary-rgb), .5)` could apply an alpha to a token; that is
  what `color-mix()` does directly:

  ```diff
  - background-color: rgba(var(--cui-primary-rgb), .5);
  + background-color: color-mix(in srgb, var(--cui-primary) 50%, transparent);
  ```

  Upstream v6 carries no rgb triplets either. The opacity utilities
  (`.text-opacity-50`, `.bg-opacity-25`, `.link-opacity-75`) are unchanged —
  they now scale the token through `calc(var(--cui-bg-opacity) * 100%)`.
- **The elevation system is gone**: `$elevations`, `$enable-elevations`,
  `$elevation-base-color`, the `elevation()` mixin and the `.elevation-*`
  utilities. It was disabled by default (`$enable-elevations: false`), so the
  utilities were the only reachable part. Use the shadow utilities
  (`.shadow`, `.shadow-sm`, `.shadow-lg`) or set `box-shadow` directly.
- **The button focus ring is the theme ring.** `--cui-btn-focus-shadow-rgb` and
  the per-variant `$btn-*-focus-shadow-rgb` Sass variables are gone without a
  renamed successor, and so is `--cui-btn-focus-ring`: the button draws the ring
  from the global width and the theme's colour, so a colour button rings in its
  colour and a neutral one gets the global ring. To restyle it, set
  `--cui-focus-ring-color` (or `--cui-theme-focus-ring`) on the button. Two
  visible consequences: a colour button's ring uses the focus-ring opacity
  (fainter than the old 50% mix), and the neutral outline/ghost buttons ring in
  the global colour instead of a grey.

#### Focus rings are keyboard-only on activation controls

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

Controls you click to act — checkboxes, radios, switches, both range sliders,
pagination links, stepper buttons, the search, close, sidebar and navbar
togglers — draw their focus ring on `:focus-visible`, so clicking no longer
flashes it and keyboard focus still shows it, joining the buttons which
already worked this way. Fields you type into — text inputs, the OTP cells,
the date-time sections — keep `:focus`: a field shows its ring on mouse focus
by design.

Two suppressed rings are restored: the header toggler and the carousel
controls declared `outline: 0` with no replacement, so keyboard focus was
invisible on both.

#### A validation state is a theme colour, not a palette of its own

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

`$form-validation-states` carried a colour, a border colour, a focus ring and a
pair of tooltip colours per state, and `_root.scss` emitted four tokens to feed
them. A state names a theme colour now, and every value is a slot of it.

```diff
  $form-validation-states: (
    "valid": (
-     "color": var(--cui-form-valid-color),
-     "border-color": var(--cui-form-valid-border-color),
-     "tooltip-bg-color": var(--cui-success),
-     …
+     "theme": "success",
      "icon": …,
    ),
  )
```

- **`--cui-form-valid-color`, `-valid-border-color`, `-invalid-color` and
  `-invalid-border-color` are removed**, together with the Sass variables behind
  them (`$form-valid-*`, `$form-invalid-*`, `$form-feedback-valid-color`,
  `$form-feedback-invalid-color`). Retint a state by retinting its theme colour,
  or override the slot on the map.
- **Feedback text and the invalid border are one step darker**, because both
  read the state colour's `fg` slot instead of the raw brand colour. That is a
  fix, not a preference: measured against the body background, the old pair
  scored **3.50** (valid) and **3.69** (invalid), both under WCAG AA; the new
  pair scores **5.13** and **5.39**. Text and border stay the same colour, as
  they were before.
- **`$input-btn-focus-color-opacity` is removed.** The validation ring comes
  from the colour's `focus-ring` slot, which reads
  `--cui-focus-ring-opacity`; set that instead.
- **`$focus-ring` is removed and `$focus-ring-color` reads the slot.** The
  colour was `rgba($primary, $focus-ring-opacity)`, resolved at build time, so
  neither retinting `--cui-primary` nor changing
  `--cui-focus-ring-opacity` at runtime moved the default ring. It is
  `var(--cui-primary-focus-ring)` now — the slot every `.theme-*` ring
  already mixed from. `$focus-ring` itself only restated
  `--cui-focus-ring`, which `_root.scss` composes, so the two variables
  that read it (`$btn-close-focus-shadow`, `$sidebar-toggler-focus-shadow`)
  take the token instead.
- **`form-validation-state()` takes `$theme` where it took `$color`**, and the
  variables moved from `scss/_config.scss` into the partials that use them
  alongside `$form-text-*` and `$form-feedback-*`.

#### `$component-active-color` and `$component-active-bg` are removed

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

One shared pair in `_config.scss` fed every active state in the library — the
list group, pagination, the menu, nav pills, the dropdown, both range sliders
and the checkable controls. Each component names its own default now and points
it at the colour's slots, so nothing is defined in a file that never renders it.

```diff
- $list-group-active-color:  $component-active-color;
- $list-group-active-bg:     $component-active-bg;
+ $list-group-active-color:  var(--cui-primary-contrast);
+ $list-group-active-bg:     var(--cui-primary);
```

- **Active text is fully opaque.** `$component-active-color` was
  `rgba($white, .87)`, a colour frozen at build time, so an active state
  recoloured to a light background kept near-white text. It reads the
  `contrast` slot now. Against the default primary that lifts the ratio from
  **4.71** to **5.65**, and it matches `.text-bg-primary`, which already used
  the slot — the two whites in the library are one white again. Our own
  Bootstrap theme was already overriding the pair to pure white, so it renders
  as before.
- **Override the colour, not the pair.** Set `$primary` (or
  `--cui-primary` at runtime) to move every active state at once, or the
  component's own knob to move one. Per instance, `.theme-*` still wins where a
  component reads `--cui-theme-*`.
- **The switch has no SVG knob at all any more.** The thumb is painted with
  `background-color` in every state, so `$switch-thumb-bg` and
  `$switch-checked-thumb-bg` are ordinary colour knobs; the v5 knob images and
  the variables that fed them (`$form-switch-bg-image` and friends) are gone.

#### A theme colour is one nested map entry

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

`$theme-colors` carried one value per colour and three further families carried
the rest, so a theme colour was defined in four places and adding one meant
editing four blocks. It is a map of maps now — one name, eight slots.

- **Twenty-four Sass variables are removed**: `$primary-text-emphasis` and its
  seven siblings, `$primary-bg-subtle` and its seven, `$primary-border-subtle`
  and its seven. Override a slot through the map instead:

  ```diff
  - $success-bg-subtle: #e8f5ec;
  + $theme-colors: map.merge($theme-colors, (
  +   "success": map.merge(map.get($theme-colors, "success"), ("bg-subtle": #e8f5ec))
  + ));
  ```

  Every `--cui-{color}-*` custom property keeps its name and its value, so
  a runtime override is unaffected.
- **`$theme-colors` is a map of maps**, so `@each $name, $value in $theme-colors`
  now yields a map. Use `map-slot($theme-colors, "base")` where a flat
  `name → colour` map is what you want; the `$theme-colors-*` families in
  `scss/_theme.scss` are built that way.
- **New slots:** `fg` (the state colour readable as text, one step lighter than
  `text-emphasis`), `bg-muted` (between `bg-subtle` and the solid colour) and
  `focus-ring` (the hue the `.theme-*` ring mixes from). They emit
  `--cui-{color}-fg`, `-bg-muted` and `-focus-ring`, and reach components
  as `--cui-theme-fg`, `--cui-theme-bg-muted` and
  `--cui-theme-focus-ring`; the emphasis text reaches them as
  `--cui-theme-fg-emphasis`.

#### The OTP input defaults to the shared frame

Twenty-five `$form-otp-control-*` variables were one-to-one aliases of the
`$input-*` family — `$form-otp-control-bg: $input-bg` and so on down to the
focus ring. They now default to the `--cui-btn-input-*` tokens on `:root`
instead, so the cell picks up a runtime restyle of the text controls without
going through a second Sass tier. The variables themselves stay, and so does
every rendered value.

One consequence for Sass customization: setting `$input-bg` (or another
`$input-*` knob) no longer reaches the OTP cell, because the cell now reads the
root token rather than that variable. Restyle the whole family through the
`--cui-btn-input-*` tokens, or set the matching `$form-otp-control-*` variable
alongside it.

#### The input frame is complete on `:root`

The shared `--cui-btn-input-*` frame gains the slots every field was
still deriving at Sass level: `border-color`, `border-radius` (with `-sm`/`-lg`),
`box-shadow`, `font-weight` and the `focus-color`/`-bg`/`-border-color` trio.
The `$input-*` knobs keep working — they read the tokens now — so a `with()`
override reaches the whole family as before, and a runtime override of one
root token restyles every text control at once.

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`$input-focus-border-color` is a `var()` reference, not a Sass colour.**
  It was `tint-color($primary, 50%)`, frozen at build time — retint the
  palette and the focus border stayed on the old primary. It reads
  `--cui-btn-input-focus-border-color` now (the same 50% mix, computed
  in the browser). Sass colour functions on it no longer compile; override
  the token or the variable with a colour of your own instead.

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`$time-picker-roll-cell-selected-hover-bg` is computed in the browser.**
  It was a `light-dark()` pair of `color.scale($primary, …)`, frozen at build
  time, so a retinted palette moved the selected cell but left its hover state
  on the old indigo. It darkens the primary the way the solid button darkens
  its own background — `oklch(from var(--cui-primary) calc(l * .85) c h)` —
  which also drops the separate dark-mode variant, since the formula works in
  both. Sass colour functions on it no longer compile.

#### The field transition is three tokens, not one shorthand

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

`--cui-control-transition` held a whole shorthand
(`border-color .15s ease-in-out, box-shadow .15s ease-in-out`), so retiming a
field meant restating the property list. It splits into
`--cui-control-transition-property`, `-duration` and `-timing`, and the rules
set the three `transition-*` longhands. `$input-transition` splits the same way,
and so do the components that derived from it — `$chip-input-transition`,
`$search-button-transition`, `$form-otp-control-transition`,
`$accordion-transition`, `$btn-transition`.

The floating label follows the same rule: `--cui-form-floating-transition` and
`$form-floating-transition` are replaced by
`--cui-form-floating-transition-property`, `-duration`, `-timing` (and the
matching Sass variables). So does the range thumb — `$form-range-thumb-transition`
becomes `$form-range-thumb-transition-property`, `-duration` and `-timing`.

`--cui-btn-input-transition` is gone with them. The frame carries the parts
instead — `--cui-btn-input-transition-duration`, `-timing`, `-property` (what a
plain field animates: `border-color, box-shadow`) and
`--cui-btn-input-action-transition-property` (what a button or an action part
animates: the same plus `color` and `background-color`). One declaration retimes
every control on the page:

```css
:root { --cui-btn-input-transition-duration: .3s; }
```

One easing changes with the split: the accordion animated `border-radius` on
`ease` while everything else used `ease-in-out`; the longhands take a single
easing, so it is `ease-in-out` throughout.

The split also removes a trap the shorthand carries: a trailing duration binds
to the last property only, so adding `color` to the front of the old list would
have left it at `0s`. The rendered animation is unchanged.

#### `$form-check-*` is now named for what it configures

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

The checkbox, the radio and the switch shared their defaults through variables
named after `.form-check` — the v5 wrapper they no longer use. The names said
"deprecated wrapper" while the role was "the three current controls":

| v5 | v6 |
| --- | --- |
| `$form-check-input-width` | `$control-size` |
| `$form-check-input-focus-border` | `$control-focus-border` |
| `$form-check-input-active-filter` | `$control-active-filter` |
| `$form-check-input-disabled-opacity` | `$control-disabled-opacity` |
| `$form-check-label-disabled-opacity` | `$control-label-disabled-opacity` |
| `$form-check-input-checked-bg-color` | `$control-checked-bg` |
| `$form-check-input-checked-border-color` | `$control-checked-border-color` |
| `$form-check-input-indeterminate-bg-color` | `$control-indeterminate-bg` |
| `$form-check-input-indeterminate-border-color` | `$control-indeterminate-border-color` |

All nine sit in `_root.scss` and are emitted as `--cui-control-*` on `:root`,
so the three controls can also be retuned together without recompiling:

```css
:root { --cui-control-disabled-opacity: .3; }
```

`$form-check-input-bg`, `-border`, `-border-radius`, `-checked-color` and
`$form-check-radio-border-radius` are gone without a replacement: they were one
control's value reached through another control's name. Set `$check-*`,
`$radio-*` or `$switch-*` — the variables of the control you mean.

The five that shape the deprecated `.form-check` wrapper keep their names and
move into `forms/_form-check.scss`, so they leave the build with it.

The class names are unchanged. `.form-check`, `.form-check-input` and
`.form-check-label` still work exactly as before.

#### The `$input-*` variables are gone; configure the frame once

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

`$input-padding-y`, `$input-color`, `$input-bg`, `$input-border-radius` and the
30 others were aliases: each one held nothing but `var(--cui-btn-input-…)`, the
token the frame already declares on `:root`. Components read them in some places
and wrote the token out in others, so a Sass override reached part of the
library and not the rest — `$input-color: lime` recoloured the file-input button
and the input group addon but not the input's own text.

There is one place to configure the frame now. `$input-btn-*` in `_root.scss`
holds the values, and every component reads the `--cui-btn-input-*` token it is
emitted as:

```scss
// before
@use "@coreui/coreui-pro" with ($input-padding-y: 1rem);

// after — Sass
@use "@coreui/coreui-pro" with ($input-btn-padding-y: 1rem);
```

```css
/* after — runtime, no recompile */
:root { --cui-btn-input-padding-y: 1rem; }
```

`$input-height-inner`, `-half` and `-quarter` are geometry rather than aliases,
so they follow the validation mixin they serve into `scss/mixins/_forms.scss`;
`$input-height-border` had one reader and is written where it is used.

#### The control variables moved out of the shared config

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

`$input-*` described one thing — the frame every field component draws — but sat
in `_config.scss` next to the breakpoints and the spacing scale. It lives in
`scss/forms/_form-control.scss` now, with `.form-control` itself.

- **Nothing changes for CSS.** The compiled stylesheet is identical; the
  `--cui-control-*` and `--cui-btn-input-*` tokens are untouched, so
  runtime customisation is unaffected.
- **A Sass override needs the new path** when you `@use` the partial directly.
  Overriding through `@use "@coreui/coreui-pro" with (...)` is unchanged.
- **`$input-btn-*` stays in the config**: those are the values the button and
  the field agree on, and `buttons/_button.scss` reads them.
- **`$input-height`, `$input-height-sm` and `$input-height-lg` are removed.**
  They existed to be baked into `--cui-btn-input-min-height`, which now
  computes from `--cui-btn-input-line-height`, `-padding-y` and
  `-border-width` in the browser. Set those tokens, or
  `--cui-btn-input-min-height` itself, instead of recompiling.

#### Shadows are computed at runtime

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

A shadow's alpha is now `base * strength * opacity`, computed on the element
rather than resolved when the stylesheet is built. That is what makes a shadow
tintable and lets dark mode deepen every shadow at once.

- **`$box-shadow`, `$box-shadow-sm`, `$box-shadow-lg` and `$box-shadow-inset`
  are replaced by the `$shadows` map.** The `--cui-box-shadow*` custom
  properties are unchanged in name and in rendered value — they are generated
  from the map — so runtime overrides keep working. Only the Sass override point
  moved:

  ```diff
  - $box-shadow-sm: 0 .125rem .25rem rgba($black, .1);
  + $shadows: map.merge($shadows, (sm: 0 .125rem .25rem rgba($black, .1)));
  ```

  A literal value like that opts the entry out of the runtime knobs, which is
  the point of overriding it.
- **New: `$shadow-color`, `$shadow-strength`, `$shadow-strength-dark`** and the
  `--cui-shadow-color` / `--cui-shadow-strength` tokens they emit.
  Setting the colour once at the root recolours every shadow in the page,
  components included.
- **New utilities:** `.shadow-{color}` for the theme colours plus
  `current`/`black`/`white`, and `.shadow-opacity-{25|50|75|100}`. They write
  `--cui-shadow-tint` and `--cui-shadow-opacity`, both registered
  `inherits: false`, so a tinted element does not recolour the shadows nested
  inside it.
- **Dark mode raises `--cui-shadow-strength` to 2.5** instead of carrying
  a second set of shadow values. The same alpha reads as weaker against a dark
  surface, which is why the light-mode values looked almost absent there.

#### Theme gradients removed

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

- **`.bg-{color}-gradient` and `.text-bg-{color}-gradient` are gone**, along
  with the `$theme-gradients` / `$theme-gradients-dark` maps that generated
  them, the per-colour `$primary-gradient` … `$dark-gradient` variables (and
  their `-dark` twins), and the `--cui-{color}-start` / `--cui-{color}-stop`
  custom properties they read. These were CoreUI-only additions with no Bootstrap counterpart.
  Replace a removed class with the base colour plus the generic gradient —
  `class="bg-primary bg-gradient"` — or write the two-stop gradient yourself if
  you need the exact 45° ramp.
- **`.bg-gradient` itself stays**, as do `$gradient`, `--cui-gradient`,
  `$enable-gradients` and the `gradient-bg()` mixin — that is the gradient
  system Bootstrap has, and components keep using it.

#### Cascade layers

- **All library CSS now lives in cascade layers**, declared as
  `@layer colors, config, root, reboot, layout, content, forms, components, custom, helpers, utilities;`.
  Three of those are empty and reserved for you: `colors` and `config` sit below
  everything, for a palette or a configuration sheet that should lose to nothing
  but still beat the library, and `custom` slots between components and helpers.
- **Unlayered CSS wins over layered CSS regardless of specificity**, so your
  existing stylesheets now override the library more easily, not less. No
  action needed — selectors that worked before keep working, and low-specificity
  overrides that used to lose on specificity now win.
- **Utilities no longer carry `!important`.**
  <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  `$enable-important-utilities` now defaults to `false`, because the layer order
  above already puts every utility past every component — the suffix was doing
  nothing our own stylesheet needed. That takes 556 bytes gzip (19 kB
  uncompressed) off the build.

  The one case it did cover is your own **unlayered** CSS: since unlayered styles
  beat every layer, a plain `.card-title { text-align: left }` in a stylesheet
  loaded after ours now wins over `.text-center`. Two ways out, and the choice is
  yours per rule rather than ours for all of them — move that CSS into
  `@layer custom` so utilities win, or set
  `$enable-important-utilities: true` to keep the v5 behavior everywhere.

- If your build concatenates CoreUI with other CSS, make sure the layer
  declaration (emitted at the top of the bundle) is not stripped by a minifier
  that predates `@layer`.

#### Design-token maps

- **Every component that emits CSS custom properties now builds them from a
  `$<component>-tokens` Sass map** merged over your overrides with the new
  `defaults()` function. Override the whole surface at once:

  ```scss
  @use "@coreui/coreui-pro/scss/coreui" with (
    $alert-tokens: (
      --cui-alert-bg: hotpink,
      --cui-alert-margin-bottom: null, // null removes the token entirely
    )
  );
  ```

  Classic per-variable overrides (`$alert-padding-y: 2rem`) keep working — the
  map defaults are built from the same Sass variables.
- **Component Sass variables moved from `_config.scss` into their component
  partials.** `@use ... with()` is unaffected — the entry point forwards every
  module — but if you imported `scss/_config.scss` directly for its
  definitions, component blocks are no longer there.
- Two silent duplicates were dropped along the way: `$nav-link-height` was
  declared twice (navbar and header blocks — the header copy is gone) and the
  calendar emitted `--cui-calendar-cell-week-number-color` twice.
- **Time picker: the v1-only tokens are gone.** The rewritten shell draws its
  adornments as inline SVG on `currentColor` and styles them through
  [`.form-control-action` / `.form-control-cleaner`](/forms/form-control-group/),
  so nothing read them any more — `--cui-time-picker-cleaner-*` (5 tokens),
  `--cui-time-picker-indicator-icon`, `--cui-time-picker-indicator-icon-size`,
  `--cui-time-picker-gap` and `--cui-time-picker-placeholder-color`, together
  with their Sass variables (`$time-picker-cleaner-icon-size-sm`/`-lg` were
  also declared twice). `--cui-time-picker-indicator-icon-color` stays and now
  carries the validation color as well. The validation state itself moved off
  the root element: v1 recoloured the frame from `.time-picker.is-invalid` with
  `!important` overrides, v2 reads it from the field inside the group, so
  `$time-picker-invalid-border-color` / `$time-picker-valid-border-color` and
  the matching indicator-icon variables are gone — theme the state through the
  standard `$form-invalid-*` / `$form-valid-*` variables instead. Section
  placeholders come from the field's `placeholders` option, not a colour token.
- `$input-padding-x-lg` was removed: `.form-control-lg` reads
  `--cui-btn-input-lg-padding-x` from the shared button/input token system, and
  the time picker's dead `gap-lg` was the variable's last consumer.
  `$input-padding-x`, `$input-padding-x-sm` and `$input-padding-y-*` are
  unaffected.

#### Theme tokens

- New `--cui-theme-*` indirection plus generated `.theme-primary` …
  `.theme-inverse` classes: a themed container sets `--cui-theme-fg`,
  `--cui-theme-bg-subtle`, `--cui-theme-border`, and token-driven components
  (alert, buttons) read them. Contextual classes like `.alert-success` are now
  implemented through these tokens — same rendering, new mechanics.
- **`--cui-theme-focus-ring` joins the set.** It carries the state colour mixed
  at `$focus-ring-opacity` — a colour, like every other slot; the width stays
  global. Every component draws its ring as
  `var(--cui-focus-ring-width) solid var(--cui-theme-focus-ring, var(--cui-focus-ring-color))`,
  so a themed ancestor recolours the ring and the global colour applies
  everywhere else.
- **`--cui-{color}-contrast` custom properties are new root tokens.** Previously
  only buttons computed their own contrast colour; the root tokens now carry it,
  written in `$theme-colors-contrast`. `.text-bg-*` reads the token instead of
  calling `color-contrast()`.

#### `--cui-mobile-breakpoint` removed

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

The token carried the **name** of the sidebar's breakpoint (`lg`), not a length,
so it could not be used in a media query or in `calc()`, and nothing in the
library read it. Read `--cui-breakpoint-lg` for the value.

It also sat one letter away from a mechanism that does work and looks similar.
The sidebar tells its plugin about the mobile layout with `--cui-is-mobile`,
which is declared **inside** the media query, so it is `"true"` below the
breakpoint and empty above — the plugin only tests whether it is set. The
removed token was declared on `:root` unconditionally, so the same
`Boolean(getPropertyValue(…))` test against it answered "mobile" at every
width.

The Sass variable `$mobile-breakpoint` is unchanged; the sidebar's own media
queries are built on it.

#### Colour scales, and `_variables-dark.scss` removed

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

Dark mode no longer has a second set of Sass variables. Every colour is declared
once, as a native
[`light-dark()`](https://developer.mozilla.org/en-US/docs/Web/CSS/color_value/light-dark)
pair, and `[data#{$data-infix}theme="dark"]` only declares `color-scheme: dark`.

- **`scss/_variables-dark.scss` is gone.** All 59 `$*-dark` variables it held are
  gone with it; do not `@import "variables-dark"` any more. The values live
  inline in the light variable:

  ```diff
  - $body-color:      rgba(shift-color($gray-base, +26%), .95);
  - $body-color-dark: rgba($white, .87); // in _variables-dark.scss
  + $body-color:      light-dark(rgba(shift-color($gray-base, +26%), .95), rgba($white, .87));
  ```

  Two exceptions remain, because `light-dark()` resolves to a `<color>` and these
  are not colours: `$body-bg-dark` and `$body-tertiary-bg-dark` still exist (the
  `color-translucent()` helper has to run in Sass), and the colours baked into the
  select chevron and switch knob SVGs keep a dark counterpart next to their
  component (`$form-select-indicator-dark`, `$form-switch-bg-image-dark`).
- **Every theme colour gets a 100–900 scale of tokens in `:root`**, mixed at
  runtime from the colour's own token: `--cui-primary-100` …
  `--cui-primary-900`, for each key of `$theme-colors`. Knobs:
  `$color-tints`, `$color-shades`, `$color-mix-space` (`lab`), `$tint-color`,
  `$shade-color`. Override `$primary` — or the `--cui-primary` token at
  runtime — and the whole family retints.
- **`-bg-subtle`, `-border-subtle` and `-text-emphasis` are pairs of those
  stops** rather than hand-picked hexes:

  ```scss
  $primary-bg-subtle:     light-dark(var(--cui-primary-100), var(--cui-primary-900));
  $primary-border-subtle: light-dark(var(--cui-primary-300), var(--cui-primary-600));
  $primary-text-emphasis: light-dark(var(--cui-primary-800), var(--cui-primary-200));
  ```

  **This fixes a real dark-mode bug.** Only `light` and `dark` had genuine dark
  variants before; for the six chromatic colours `$primary-bg-subtle-dark` was an
  alias of the light value, so `.alert-success`, `.list-group-item-info` and
  `.table-warning` rendered a pale light-mode surface in dark mode. They now
  darken. Light mode shifts slightly too: subtle backgrounds are a shade lighter
  (an 80% tint rather than ~70%) and emphasis text a shade darker; borders are
  unchanged for practical purposes. Emphasis-on-subtle contrast improves in every
  colour — the weakest pair goes from 6.03:1 to 7.57:1.
- **The dark grey palette is gone**: `$gray-100-dark` … `$gray-900-dark` and the
  `$grays-dark` map. Every one of them was defined as exactly its light
  counterpart, so they generated nothing — read `$gray-*` directly. The bundled
  Bootstrap theme no longer passes `$grays-dark: ()` through its `with()` block.
- **`$theme-colors-dark` is gone**, along with `$theme-colors-text-dark`,
  `$theme-colors-bg-subtle-dark`, `$theme-colors-border-subtle-dark` and
  `$theme-colors-contrast-dark`, and the eight `$primary-dark` … `$dark-dark`
  variables behind them. Theme colours themselves no longer change
  between colour modes — the old dark variants were a 10% desaturation, which
  upstream does not do either. Consequence: the eight
  `[data#{$data-infix}theme="dark"] .text-bg-*` overrides are gone.
- **The `--cui-{name}-dark` root tokens are gone**
  (`--cui-body-color-dark`, `--cui-body-bg-dark`,
  `--cui-emphasis-color-dark`, `--cui-secondary-color-dark`,
  `--cui-secondary-bg-dark`, `--cui-tertiary-color-dark`,
  `--cui-tertiary-bg-dark`). They existed so a component could pin the dark
  palette while the page stayed light; declare `color-scheme: dark` instead and
  the `light-dark()` pairs follow — which is exactly what `.sidebar-dark` now
  does, having dropped its eight token overrides.
- **`$link-shade-percentage` no longer drives `$link-hover-color`**, which is now
  `light-dark(var(--cui-primary-600), var(--cui-primary-400))`. The
  variable still exists and still drives the `.link-*-*` hover helpers.
- **Two dead table knobs were removed**: `$table-th-font-weight` and
  `$table-caption-color`. Reboot owns those declarations, so use `$th-font-weight`
  and `$caption-color`.
- Setting `$enable-dark-mode: false` still yields a light-only page: `:root`
  declares `color-scheme: light` and nothing ever declares `dark`, so every
  `light-dark()` pair resolves to its light side.

#### The neutral surfaces are a numbered ladder

`.bg-body-secondary`, `.bg-body-tertiary`, `.text-body-secondary` and
`.text-body-tertiary` are deprecated. The replacements are ordinal:
`.bg-1` … `.bg-4` for surfaces and `.fg-body`, `.fg-1` … `.fg-4` for the text
hierarchy, with two new rungs (`.bg-1`, `.bg-2` on new `gray-025` / `gray-050`
stops) between the body and the old surfaces. The deprecated names render
identically and are removed in v7.

The adjectives ran backwards for backgrounds — "tertiary" sat *closer* to the
page than "secondary" — because for text, where the names came from, "stronger"
means more visible, while for a surface it means further from the page. Numbers
say how far from the body a rung sits and read the same on both sides.

Two consequences for the tokens:

- <span class="badge text-warning-emphasis bg-warning-subtle">Deprecated</span>
  **The surface tokens move out of the theme-color namespace.**
  `--cui-bg-body`, `--cui-bg-1` … `--cui-bg-4` and `--cui-fg-body`,
  `--cui-fg-1` … `--cui-fg-4` are canonical; `--cui-body-bg`, `--cui-body-color`,
  `--cui-secondary-color`, `--cui-tertiary-bg` and `--cui-tertiary-color`
  remain as aliases with identical values, and go away in v7 — at which point
  the `--cui-secondary-*` prefix belongs to the `secondary` theme color alone.
  One alias is already gone:
  <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`--cui-secondary-bg` is the `secondary` theme color's action-background
  slot now** (see the entry below), not a surface alias. Markup that read it
  for the surface gets a similar but lighter gray — read `--cui-bg-4`
  instead. This name is exactly why the ladder moved out of the theme-color
  namespace: a page surface sat next to `--cui-secondary-bg-subtle` (a
  theme-color slot) with no way to tell which system a token belonged to.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The dark side of the ladder is palette stops, and the page got darker.**
  The grays gain `--cui-gray-950` (`#15181f`) and `--cui-gray-975` (`#0e1115`),
  and every dark rung is a stop instead of a `color-mix()` between `gray-800`
  and `gray-900`: the body sits on `gray-975` (was `gray-900`), `bg-1` on
  `gray-950`, `bg-2` on `gray-900`, `bg-3` on `gray-800` and `bg-4` on
  `gray-700`. Dark mode reads darker overall and surfaces have more room to
  step away from the page; the light side is unchanged. Translucent values
  un-blended against the body (`$border-color-translucent`, the tertiary
  surface) carry a higher alpha for the same rendered color over the darker
  page. Override the `$bg-*` knobs or the `--cui-bg-*` tokens to keep the
  previous palette.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The text ladder is solid grays, and components use all of its rungs.**
  `--cui-fg-body` through `--cui-fg-4` were alpha blends of one color
  (`rgba(…, .95)` down to `.25`), which made the two deepest rungs
  illegible and left every component crowded onto `fg-body`/`fg-2`. Each
  rung is a palette stop now — `fg-body` on `gray-900/050`, `fg-1` on
  `800/200`, `fg-2` on `700/300`, `fg-3` on `600/500`, `fg-4` on `500/600`
  — so contrast is the same on any surface and can be audited once.
  Components spread across the rungs: secondary text (breadcrumb links,
  toast headers, captions, blockquote footers) reads `fg-3` instead of
  `fg-2`, disabled states read `fg-3`/`fg-4` and stay legible, dividers
  read `fg-4`, and the strongest text (tables, active nav links, the
  tooltip surface) reads `fg-body` instead of `--cui-emphasis-color`.
  Nav links are neutral (`fg-2`, darkening through `fg-1` to `fg-body`
  when active) instead of link-colored — a `.theme-*` class still
  recolors them. `$gray-base` fed the alpha blends and is removed.
  Override the `$fg-*` knobs or the `--cui-fg-*` tokens to keep the
  previous rendering.
- **`.text-body` and `.text-body-emphasis` are unaffected** — they are not
  ordinal, any more than `.text-primary` is.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The Sass knobs follow the ladder.** `$fg-body`, `$fg-1` … `$fg-4`,
  `$bg-body`, `$bg-1` … `$bg-4` replace `$body-color`, `$body-bg`,
  `$body-secondary-color`, `$body-secondary-bg`, `$body-tertiary-color` and
  `$body-tertiary-bg`; every knob holds one `light-dark()` expression, so
  `$body-bg-dark` and `$body-tertiary-bg-dark` are gone too — the translucent
  tints that needed their Sass colors read the grays inline, which also means
  the bundled Bootstrap theme recomputes them from its own grays instead of
  forwarding frozen copies.

#### `light` and `dark` are replaced by `inverse`

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

`light` and `dark` were theme colours whose names described a colour scheme, and
they behaved like it: `.theme-dark` sat next to `data-coreui-theme="dark"`
meaning something else entirely, and neither followed the reader's scheme — a
`.btn-dark` stayed near-black on a near-black page. There are seven theme colours
now, and the two neutrals swap ends of the gray scale between schemes.

- **`inverse` replaces `dark`.** It resolves to `gray-900` in light mode and
  `gray-100` in dark, so `.btn-inverse`, `.text-bg-inverse` and
  `.table-inverse` stand against the page in both.
- **`secondary` takes over what `light` did.** It is a light neutral now
  (`gray-100` in light mode, `gray-600` in dark) rather than the mid gray-blue
  `#6b7785`, so `.btn-secondary` and `.bg-secondary` change appearance.
- **Every `-light` and `-dark` class is gone.** Rename `-dark` to `-inverse` and
  `-light` to `-secondary` across `alert`, `bg`, `border` (and its per-side
  variants), `btn`, `btn-ghost`, `btn-outline`, `btn-subtle`, `callout`, `chip`,
  `focus-ring`, `link-underline`, `list-group-item`, `shadow`, `table`, `text`,
  `text-bg` and `theme`, plus the `-subtle` and `-emphasis` families. The
  colour-scheme opt-ins keep their names: `.navbar-dark`, `.dropdown-menu-dark`,
  `.carousel-dark` and `.sidebar-dark` are unaffected, as is `.fw-light`.
- **A surface is not a theme colour.** Where `.bg-light` was a neutral panel,
  reach for `.bg-4` or `.bg-3`; where `.bg-dark` was a
  fixed dark backdrop, set `data-coreui-theme="dark"` on the container and let
  the surface classes follow.
- **`--cui-theme-base` is now `--cui-theme-bg`.** The contextual token that
  components read for a fill was named after the map slot rather than the job;
  the slot is still `base`, and `--cui-{color}` is unchanged.
- **Colour utilities read the slot that stays legible.** `.text-*` points at
  `--cui-{color}-fg` instead of the raw colour, and `.btn-outline-*` and
  `.btn-ghost-*` take their text from it too. For the five chromatic colours this
  is a shade darker in light mode and a shade lighter in dark; for the neutrals it
  is the difference between readable and gray-on-gray. `.btn-outline-*` also
  takes its border from the `border` slot, so the outline is a subtle line
  rather than a full-strength one. `.bg-*` and `.border-*` keep reading the
  colour itself.
- **`$light` and `$dark` are removed; `$inverse` is new.** `$secondary` and
  `$inverse` hold a `light-dark()` expression rather than a Sass colour, so they
  cannot be passed to `color-contrast()` or the tint/shade functions — read
  `$gray-*` for that.
- **`$utilities-colors` is removed.** It was a flat `name → colour` copy of the
  map's `base` slot, and no utility reads the raw colour for every family any
  more. Call `map-slot($theme-colors, "base")` where you need one, or
  `theme-color-refs("fg")` for the slot a text utility uses.
- **`$theme-lightness-overrides` is now `$theme-state-colors`** and carries
  ready values rather than lightness multipliers. A single multiplier cannot
  serve a colour that is dark in one scheme and light in the other, so the two
  neutrals step along the gray scale instead.

#### Component icons render through CSS masks

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

The accordion chevron and the carousel arrows were `background-image` SVGs with
the colour written inside the markup, which is why each needed a dark-mode rule —
the accordion swapped in a second SVG, the carousel inverted the first with a
`filter`. They are now painted through a CSS `mask`, so the colour lives on
`background-color` as an ordinary token and follows the root colours by itself.
Upstream v6 does the same, with a `mask-icon()` mixin.

- **The accordion's icon is one shape recoloured per state, not two images.**
  `--cui-accordion-btn-active-icon` no longer has to carry a second copy
  of the artwork: it defaults to `--cui-accordion-btn-icon`, and the open
  state changes `--cui-accordion-btn-active-icon-color` instead. Set it
  only when the open state is a genuinely different shape — a minus against a
  plus. New tokens: `--cui-accordion-btn-icon-color` and
  `--cui-accordion-btn-active-icon-color`.
- **A custom icon is now a shape, not a coloured image.** Whatever colour you put
  inside `$accordion-button-icon` or `$carousel-control-prev-icon-bg` /
  `$carousel-control-next-icon-bg` is ignored — only the alpha of the SVG is used.
  Set the colour through the token (`--cui-accordion-btn-icon-color`,
  `--cui-carousel-control-color`).
- **`$accordion-icon-color` and `$accordion-icon-active-color` are
  `currentcolor` now**, not Sass colours — Sass colour functions on them no
  longer work. The icon therefore takes the header's colour in every state, so
  anything that recolours an open header (`--cui-accordion-active-color`,
  a `.theme-{color}` class) carries the icon with it. Both tokens stay, for the
  case where the icon is meant to differ from the text.
- **`$carousel-control-icon-filter` is removed**, with its
  `--cui-carousel-control-icon-filter` custom property and its two dark
  companions (`$carousel-control-icon-filter-dark`,
  `$carousel-dark-control-icon-filter`), along with the four accordion
  dark variables (`$accordion-icon-color-dark`,
  `$accordion-icon-active-color-dark`, `$accordion-button-icon-dark`,
  `$accordion-button-active-icon-dark`). The accordion's dark-mode block is gone
  entirely.
- **The carousel's colours are tokens.** `--cui-carousel-control-color` is
  new; `.carousel-dark` pins the dark side of each pair through
  `$carousel-dark-control-color`, `$carousel-dark-indicator-active-bg` and
  `$carousel-dark-caption-color` (previously `$carousel-*-dark` in
  `_variables-dark.scss`). RTL still swaps the two arrows, now through
  `mask-image`.
- **Visible in dark mode**: the old dark accordion chevron was a *filled* glyph
  where the light one was *stroked*. Both modes now use the stroked shape — same
  colour, same size, slightly different drawing. Worth knowing if you diff
  screenshots.

#### Buttons

- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`button-variant()` takes a variant name, not a colour pair**, and reads it
  from `$button-variants`. Each entry of that map names, per state, the theme
  token a button variable reads and the neutral value behind it; `disabled`
  repeats `base`. `button-outline-variant()` and `button-ghost-variant()` are
  **removed** (they are entries in the map now), and `scss/mixins/_buttons.scss`
  no longer exists — the mixin lives next to the map in
  `scss/buttons/_button.scss`.
- **Hover and active shades are computed in CSS** with
  `oklch(from var(--cui-primary) calc(l * …) c h)` instead of precompiled
  `shade-color()`/`tint-color()`. Shades shift slightly (measured 8–23 per RGB
  channel). The win: a theme color you add yourself gets correct hover/active
  states without compiling Sass.
- **The eight shade/tint amount knobs are removed**:
  `$btn-hover-bg-shade-amount`, `$btn-hover-bg-tint-amount`,
  `$btn-hover-border-shade-amount`, `$btn-hover-border-tint-amount` and the four
  `$btn-active-*` counterparts. They fed the Sass mixes that no longer happen.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The interaction shade belongs to the theme, not to the button.** Every
  `.theme-*` class emits `--cui-theme-hover` and `--cui-theme-active` — its own
  colour, shifted in lightness — and the button variants read them, so a
  component that wants "this theme colour, one step darker" no longer has to
  recompute it. The knobs moved with them: `$btn-hover-lightness`,
  `$btn-active-lightness` and `$btn-lightness-overrides` are now
  `$theme-hover-lightness`, `$theme-active-lightness` and
  `$theme-state-colors` in `scss/_theme.scss`.
- **The dark-mode button block is gone** (~160 lines of CSS) — variants follow
  the root color tokens, which already switch in dark mode.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **The `$btn-*` variables that only forwarded a shared value are removed**:
  `$btn-color`, `$btn-padding-y`, `$btn-padding-x`, `$btn-font-family`,
  `$btn-font-size`, `$btn-line-height`, `$btn-border-width`,
  `$btn-border-radius`, `$btn-disabled-opacity`, `$btn-transition-*` and the
  `-sm`/`-lg` pairs. They pointed at `--cui-btn-input-*`, so a value assigned to
  them was overwritten by the token anyway. Configure the frame once on `:root`
  with the `$input-btn-*` variables, or set `--cui-btn-*` on the button.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`button-size()` is removed.** Sizes are a loop over `$button-sizes`, which
  points the button's tokens at the matching `--cui-btn-input-{size}-*` set. Add
  a size by adding its tokens on `:root` and its name to the map.
- **New tokens on `.btn`:** `--cui-btn-gap`, `--cui-btn-min-height`,
  `--cui-btn-white-space` and `--cui-btn-transition-property` /
  `-duration` / `-timing`. The transition was read straight from the shared
  `--cui-btn-input-*` tokens before, so it could not be retuned per button.
- <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  **`.btn-close` draws its focus ring as an `outline`,** like every other
  control; `$btn-close-focus-shadow` and `--cui-btn-close-focus-shadow` are
  removed. A box-shadow ring was clipped by the `overflow: hidden` of the modal,
  toast or drawer the close button usually sits in. Its geometry is tokens now
  too: `--cui-btn-close-width`, `-height`, `-padding-x`, `-padding-y`.
- `.btn-primary`, `.btn-outline-*`, `.btn-ghost-*` class APIs are unchanged.
- **Toggle buttons: `.btn-check` moves onto the `<label>`, with the input nested
  inside.** A toggle button was two elements held together by an `id`/`for`
  pair; it is one element now, so nothing can fall out of sync:

  ```diff
  - <input type="checkbox" class="btn-check" id="t" autocomplete="off">
  - <label class="btn btn-primary" for="t">Toggle</label>
  + <label class="btn btn-primary btn-check">
  +   <input type="checkbox" autocomplete="off">
  +   Toggle
  + </label>
  ```

  The states read the nested input with `:has()` instead of sibling selectors,
  and a `.btn-group` stops having to reason about a hidden child that is not a
  button. **The old spelling keeps working** — the label carries `.btn` in the
  new one, so the two select themselves apart — and renders identically; it is
  deprecated in v6 and removed in v7. One behavior is deliberately carried over:
  a disabled toggle is dimmed rather than repainted, so a disabled checked
  toggle still reads as checked.

#### Utilities API: one `property` map replaces `css-var`, `css-variable-name` and `local-vars`

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

Three keys said one thing between them — *a utility may write custom
properties, real properties, or both* — and `property` now says it alone. Give
it a map: a `null` entry receives the utility's value, everything else is
written as declared.

```diff
  "background-color": (
-   property: background-color,
-   local-vars: ("bg-opacity": 1),
+   property: (
+     --#{$prefix}bg: null,
+     --#{$prefix}bg-opacity: 1,
+     background-color: color-mix(in srgb, var(--#{$prefix}bg) calc(var(--#{$prefix}bg-opacity) * 100%), transparent),
+   ),
    class: bg,
    values: $utilities-bg-colors
  )

  "bg-opacity": (
-   css-var: true,
+   property: (--#{$prefix}bg-opacity: null),
    class: bg-opacity,
    values: (25: .25, 50: .5, 75: .75)
  )
```

The class API does not change — `.bg-primary` and `.bg-opacity-50` still exist
and still compose. What changes is where the translucency expression lives:

- **`$utilities-text-colors`, `$utilities-bg-colors`, `$utilities-border-colors`
  and `$utilities-links-underline` now carry plain token references**
  (`var(--cui-primary)`, `var(--cui-primary-fg)`) instead of a `color-mix()`
  expression per entry. The
  expression is written once, in the utility's `property` map. If you built a
  map of your own by calling `translucent-css-var()`, call the new
  `color-var-ref()` instead — same arguments, without the wrapper.
- **`.text-muted`, `.text-black-50`, `.text-white-50` and `.text-body-secondary`
  now respond to `.text-opacity-*`.** They rendered the same colour before and
  render the same colour now; they simply went through the plain value and so
  ignored the opacity knob every other colour utility honoured.
- Every custom property a utility assigns is registered
  `@property { inherits: false }`, which now covers `--cui-bg`, `--cui-text`,
  `--cui-border` and `--cui-link-underline` as well — so a colour set on a
  container cannot leak into a descendant that only carries an opacity class.

`at-property: false` still opts a utility out of that registration, for the one
case that writes an inheriting global token (`.focus-ring-*`).

#### Utilities API: child selectors and attribute selectors (new)

Two keys join the `$utilities` API, ported from Bootstrap's v6 branch:

- **`child-selector`** makes a utility style the children of the element it is
  applied to instead of the element itself, wrapped in `:where()` so it adds no
  specificity. This is what the new spacing and divider utilities are built on.
- **`selector`** (`class`, `attr-starts`, `attr-includes`) writes an attribute
  selector rather than a class, so one rule can serve a whole family of classes.

They bring four new utilities with them, all responsive and direction-aware:

| class | what it does |
| --- | --- |
| `.space-x-*`, `.space-y-*` | margin between children — `gap` without needing a flex or grid container |
| `.divide-x`, `.divide-y` (+ `-0`) | a border between children, none on the outer edges |

Nothing existing changes; these are additions. See
[the utilities API](/utilities/api/#child-selector),
[spacing](/utilities/space/) and
[borders](/utilities/divide/).

#### Utilities API: theme variants and the `rtl` key removed

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

- **The `dark:` theme-variant utilities are gone** (40 classes:
  `.dark\:bg-*`, `.dark\:text-*`). They were generated for the colour
  utilities only, duplicating every value under a `[data-coreui-theme=dark]`
  selector, and were never documented. The palette already resolves per theme
  through `light-dark()`, so `.bg-body`, `.text-body-secondary` and friends
  follow the colour mode on their own. The `dark-mode` key of a `$utilities`
  entry is no longer read.
- **The `rtl` key of a `$utilities` entry is no longer read.** It did two
  jobs: `rtl: false` wrapped the output in RTLCSS `/* rtl:remove */`
  directives, and `rtl: true` accepted `("ltr": …, "rtl": …)` value maps that
  emitted a `[dir="rtl"]` counterpart. Direction is expressed with logical
  properties now (the position utilities are `inset-inline-start`/`-end`), so
  the flag has nothing left to do. One behaviour change comes with it:
  the RTL behaviour of `.translate-middle` / `.translate-middle-x` is written
  as a plain `[dir="rtl"]` rule instead of a generator option — `transform` is
  not direction-aware, so centring on a logical inset still needs the flip, but
  it is the only utility that does and it no longer costs the whole API a key.

#### RFS removed

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

- **The RFS engine is gone** — no `vendor/rfs`, no `font-size()` / `rfs()`
  mixins, no `$enable-rfs`, no `rfs` option in the utilities API, and none of
  the `$rfs-*` knobs (`$rfs-base-value`, `$rfs-breakpoint`, `$rfs-factor`,
  `$rfs-mode`, `$rfs-unit`, `$rfs-two-dimensional`, `$rfs-class`, …). Fluid type is
  written as literal `clamp()` values in `$h1-font-size`–`$h4-font-size`,
  `$display-font-sizes` and `$legend-font-size`; rendering is unchanged at
  every viewport width.
- **Headings no longer derive from `$font-size-base`** — a `clamp()` cannot be
  multiplied. Override the `$h*-font-size` variables directly.
- A temporary `scss/vendor/_rfs.scss` shim (pass-through `font-size()`/`rfs()`
  mixins) exists only for the docs engine and will be removed — do not depend
  on it.

#### One styling surface for all text controls

- **Shared root knobs**: `:root` now carries the control frame
  (`--cui-btn-input-padding-y/-x`, `-font-family/-size`, `-line-height`,
  `-border-width`, `-transition`, `-color`, `-bg`, `-disabled-opacity`, plus
  `-sm-*`/`-lg-*` size sets) and the selection state
  (`--cui-control-checked-bg/-border-color`,
  `--cui-control-indeterminate-bg/-border-color`). Restyle these once and
  every control follows: inputs, selects, checks, switches, OTP, chip input,
  autocomplete, multi select, and the pickers — including the checkbox-style
  option indicators inside autocomplete and multi select.
- **Every text control consumes per-element `--cui-control-*` tokens**
  (padding, font, colors, border, radius, shadows, focus and disabled sets)
  that default to those knobs. Override a single control on its element;
  override everything at `:root`.
  <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  The component-namespace custom properties that duplicated this frame are
  **renamed**: `--cui-autocomplete-padding-y`, `--cui-date-picker-font-size`,
  `--cui-time-picker-bg`, `--cui-form-multi-select-border-color`,
  `--cui-chip-input-padding-x` and the rest of their frame sets are now
  `--cui-control-*` on the same elements. Runtime overrides written against
  the old names must be updated. Component-specific tokens (indicators,
  dropdowns, tags, cells, cleaner buttons) keep their names.
- **Component Sass variables survive with new defaults**: `$date-picker-bg`,
  `$autocomplete-padding-y` and the rest now default to the shared knob
  (`var(--cui-btn-input-bg)` …). Untouched, the control follows the shared
  surface; overridden through `with()`, it detaches just that control —
  exactly what reaching for a component knob means.
- **The select's indicator geometry is computed at runtime.**
  `$form-select-indicator-padding` and `$form-select-feedback-icon-padding-end`
  are now `calc()` expressions over `var(--cui-control-padding-x)` instead of
  Sass products, and `$form-select-bg-position` carries the `var()` inside it
  (the mirrored keyword comes from the `[dir="rtl"]` rule in the same sheet).
  <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  Sass arithmetic on these variables in your own stylesheets no longer works —
  they are CSS calc strings now, not numbers. Override them with your own
  `calc()` or a plain length instead.
- **Form tooltips reuse the tooltip's runtime tokens.** Add the `.tooltip`
  class to a feedback tooltip (`class="tooltip invalid-tooltip"`) and it
  follows tooltip theming — `--cui-tooltip-padding-*`, `-font-size`,
  `-border-radius` — the upstream v6 contract. Bare `.invalid-tooltip` markup
  keeps rendering exactly as before through built-in fallbacks.
  <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  The Sass-level derivation is gone: `$form-feedback-tooltip-*` no longer
  default to `$tooltip-*`, so overriding `$tooltip-padding-y` alone no longer
  moves feedback tooltips at compile time — use the runtime link (add the
  class) or set `$form-feedback-tooltip-*` explicitly. The tooltip variables
  moved to `scss/_tooltip.scss`, the feedback set to `scss/mixins/_forms.scss`.
- **Validation composes through the tokens**: `.is-invalid` / `.is-valid` set
  `--cui-control-border-color`, `-focus-border-color` and `-focus-ring`
  instead of restating declarations, so state styling follows any control
  automatically.

#### Opacity utilities no longer cascade to descendants

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

The opacity utilities compose through custom properties — `.text-opacity-50` sets
`--cui-text-opacity` and the colour utilities read it. Custom properties
inherit, so the value leaked into every descendant. The colour utilities that
restate their own opacity (`.text-primary` declares
`--cui-text-opacity: 1`) were immune; the ones reading it through a
`var(…, 1)` fallback were not.

Reachable consequences in v5: `.bg-opacity-25` on a container faded every nested
`.text-bg-*`, and `.link-opacity-50` faded every nested link — including bare
`<a>` elements, which read `--cui-link-opacity` too.

Five names are now registered with
[`@property`](https://developer.mozilla.org/en-US/docs/Web/CSS/@property) as
`inherits: false`, so each utility is scoped to the element it is applied to:
`--cui-text-opacity`, `--cui-bg-opacity`,
`--cui-border-opacity`, `--cui-link-opacity`,
`--cui-link-underline-opacity`. Upstream v6 does the same.

- **If you relied on the leak** — one `.link-opacity-*` on a wrapper fading a
  whole block of links — put the utility on each element, or set the custom
  property yourself in your own CSS (a hand-written declaration still inherits;
  only the registration changes how *utilities* behave).
- `.focus-ring-*` is deliberately **not** registered: it writes
  `--cui-focus-ring-color`, which is a global `:root` token, and components
  read it without a fallback. A custom utility that writes a `:root` token name
  must opt out the same way, with `at-property: false` in its `$utilities` entry.
- Compiled output is otherwise byte-identical — the five `@property` blocks are
  the whole diff.

#### The CSS Grid ships, and its responsive classes are container queries

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

`$enable-cssgrid` is `true` by default, so `.grid` and the `.g-col-*` /
`.g-start-*` classes are in the compiled CSS instead of waiting behind a Sass
flag. Set it to `false` if you do not want them.

Every `.grid` is now a **query container** (`container-type: inline-size`), so
`.g-col-md-6` responds to the width of the grid rather than to the viewport — a
grid inside a narrow column switches layout on that column's width. This is
what upstream v6 does, and it is the point of having a second grid at all.

`container-type` implies layout containment, so a `.grid` is the containing block
for absolutely and fixed-positioned descendants: `position: fixed` inside a grid
is positioned against the grid, not the viewport. Our own floating panels render
through a portal and are unaffected; your own fixed markup has to live outside.

#### The CSS Grid declares its variables, and nested grids no longer inherit

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

`.grid` read `--cui-rows`, `--cui-columns` and `--cui-gap` through a `var()`
fallback and declared none of them. Two consequences: the variables did not
appear in dev tools, and — because a custom property that is never declared
simply inherits — a nested `.grid` picked up the column count of the grid
around it.

All three are declared on `.grid` now, so every grid starts from twelve
columns, one row and the standard gap regardless of its surroundings. A
component built on `.grid` keeps its own layout wherever it is dropped.

If you relied on a nested grid inheriting, set the variable on that grid too:

```html
<div class="grid" style="--cui-columns: 3;">
  <div>
    <div class="grid" style="--cui-columns: 3;">...</div>
  </div>
</div>
```

#### The `cq-*` grid is gone

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

v5.3.0 shipped a second, experimental grid — `.cq-container`, `.cq-row`,
`.cq-col-*`, `.cq-offset-*`, `.cq-g-*` — behind `$enable-container-queries`,
with its own `$cq-grid-breakpoints` map that duplicated `$grid-breakpoints`
value for value. It never shipped in the default build, and maintaining two
grids to express one idea is what the CSS Grid above now does properly.

The flag, the map, the classes and the `make-c-grid-columns()` mixin are all
removed. If you configured `$enable-container-queries`, drop it: `@use ... with
()` errors on a variable the module no longer declares. If you had opted in: `.cq-row`/`.cq-col-*` map onto the CSS Grid
(`.grid` + `.g-col-*`), which is container-based by default, or onto the flexbox
grid (`.row`/`.col-*`) if you want viewport breakpoints. To keep the container
behaviour on markup of your own, mark the element with
[`.contains-inline`](/utilities/container-queries/) and write the query with the
`container-breakpoint-*` mixins.

#### Breakpoint mixins emit range queries

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

`media-breakpoint-*` now emits `(width >= 768px)` / `(width < 768px)` instead of
`(min-width: 768px)` / `(max-width: 767.98px)`. The `.02px` subtraction existed
to work around `min-`/`max-` prefixes on fractional viewports; range syntax makes
it unnecessary.

**`breakpoint-max()` returns the raw breakpoint value now** (`768px`, not
`767.98px`). If you call it yourself inside a `max-width:` query, subtract the
`.02px` there or move that query to range syntax too — otherwise the two
breakpoints overlap on exactly `768px`.

The `container-breakpoint-*` mixins use the same syntax, take an optional
container name as their second argument, and default to `$grid-breakpoints`:

```scss
@include container-breakpoint-up(md) { … }              // nearest container
@include container-breakpoint-up(md, sidebar) { … }      // @container sidebar (width >= 768px)
```

`set-container($type, $name)` is new and marks an element as a query container.

#### New: container-type utilities

`.contains-inline` and `.contains-size` set `container-type`, so you can make any
element a query container from markup. See
[Container queries](/utilities/container-queries/).

#### Sass file layout follows Bootstrap v6

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

Upstream's directories mirror the cascade layers, so partials now live in the
directory named after the layer they emit into. **The old paths no longer
resolve** — point your `@use` rules at the paths on the right.

| Was | Is |
| --- | --- |
| `scss/_variables.scss` | `scss/_config.scss` |
| `scss/_grid.scss`, `scss/_containers.scss` | `scss/layout/` |
| `scss/mixins/_breakpoints.scss` | `scss/layout/_breakpoints.scss` |
| `scss/_reboot.scss`, `scss/_type.scss`, `scss/_images.scss`, `scss/_tables.scss` | `scss/content/` |
| `scss/_buttons.scss` | `scss/buttons/_button.scss` |
| `scss/_button-group.scss`, `scss/_close.scss`, `scss/_loading-button.scss`, `scss/_search-button.scss` | `scss/buttons/` |
| `scss/_spinners.scss` | `scss/_spinner.scss` |
| `scss/_placeholders.scss` | `scss/_placeholder.scss` |
| `scss/_mixins.scss`, `scss/_helpers.scss`, `scss/_forms.scss` | `scss/mixins/index.scss`, `scss/helpers/index.scss`, `scss/forms/index.scss` |
| `scss/forms/_form-check.scss` | `scss/forms/_check.scss` |
| `scss/forms/_form-otp.scss` | `scss/forms/_otp-input.scss` |

The list rules from `_type.scss` moved to `content/_lists.scss` and the blockquote
rules to `content/_blockquote.scss`, matching upstream's filenames.

The three aggregators are unaffected: Sass resolves `@use "mixins"` to
`mixins/index.scss` on its own.

#### `@import` is no longer supported

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

The 87 `*.import.scss` files that let `@import` reach our modules are gone, so an
`@import` of anything under `scss/` no longer resolves. Load the library with
`@use` instead:

```scss
// Was
@import "../node_modules/@coreui/coreui/scss/coreui";

// Is
@use "@coreui/coreui/scss/coreui";
```

Configuration moves with it. Where `@import` let you set variables by declaring
them before the import, `@use` takes them in a `with ()` clause, and the rule has
to be the first thing in the file:

```scss
@use "@coreui/coreui/scss/coreui" with (
  $body-bg: #000,
  $body-color: #111
);
```

Sass deprecated `@import` and removes it in Dart Sass 3.0.0, so this is where it
was heading regardless. The [Sass migration guide](https://sass-lang.com/documentation/breaking-changes/import/)
covers the rules; `sass-migrator module` automates most of a conversion.

One consequence worth calling out: a module is configured once, at load time. If
your change has to *read* a default before changing it — merging into
`$utilities`, for instance — it goes in a partial you load before the library.
The [utilities API page](/utilities/api/#using-the-api) shows both patterns.

**What we deliberately did not copy.** Upstream renamed three components *and their
classes* — `.modal`, `.offcanvas`, `.dropdown`, `.dropdown-menu` and
`.dropdown-item` are gone from Bootstrap v6, replaced by `.dialog`, `.drawer`,
`.menu` and `.menu-item`. Those are three of the most-used components in any
Bootstrap app, so `_modal.scss`, `_offcanvas.scss` and `_dropdown.scss` keep their
names and their classes here.

#### The colour system has its own modules

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

`_config.scss` no longer defines a single colour. The palette — the base
colours, the grays and their maps — lives in `scss/_colors.scss`; the theme
colour system — `$primary`…`$inverse`, the `$theme-colors` map, the runtime
colour-scale knobs and the `$theme-colors-*` slot maps — lives in
`scss/_theme.scss`. `scss/_maps.scss` is dissolved: the `$utilities-*` maps and
`$negative-spacers` sit in `scss/_utilities.scss` next to the `$utilities`
definitions they feed, and `$gutters` in `scss/_config.scss` with the rest of
the grid settings.

- **Nothing changes for CSS** — the compiled stylesheet is byte-identical, and
  every custom property keeps its name.
- **Overriding through `@use "@coreui/coreui-pro/scss/coreui" with (...)` is
  unchanged** — the entry point forwards all of these modules.
- **`scss/maps` is gone** and `scss/variables` is not part of the public surface
  any more. Load `.../scss/config`, `.../scss/colors`, `.../scss/theme` or
  `.../scss/utilities` directly, depending on what you need.

#### The type scale is one named map

One scale now carries every font size the library renders, each stop with the
line height that belongs to it — upstream's mechanic, with our values, so
**nothing moves on screen**:

```scss
$font-sizes: (
  "xs":  ("font-size": .75rem,        "line-height": 1.5),
  ...
  "4xl": ("font-size": $h1-font-size, "line-height": 1.2)
);
```

- **`$font-sizes` changed shape** — it was `(1: $h1-font-size, … 6: $h6-font-size)`
  and is now keyed `xs`, `sm`, `md`, `lg`, `xl`, `2xl`, `3xl`, `4xl`, `5xl`, `6xl`,
  with a nested map per stop. The two top stops sit above the headings — display
  sizes (`$font-size-5xl`/`-6xl`, up to `3rem` and `3.5rem`) continuing the same
  fluid progression, numerically level with `.display-5` and `.display-4`.
  <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  If you overrode `$font-sizes`, move your values into the new shape. The numeric
  keys live on in `$font-sizes-legacy`, which is derived from the named scale.
- **`:root` gets `--cui-font-size-*` and `--cui-line-height-*` per
  stop**, and `h1`–`h6` read the tokens instead of the Sass variables. Restyling a
  stop at runtime now moves every heading and utility that uses it.
  `$h1-font-size` … `$h6-font-size` are unchanged and still feed the scale.
- **New: `.fs-{stop}`** alongside `.fs-1` … `.fs-6`, which keep working and render
  identically — `.fs-1` is `.fs-4xl`, down to `.fs-6`, which is `.fs-md`.
- **New: `.text-{stop}`**, which sets `font-size` and `line-height` together.

**We did not follow upstream's classes here.** Bootstrap v6 deletes `.fs-1` …
`.fs-6`, every `.display-*` and `.lead`, and retunes the sizes — h1–h3 grow up to
10px on small screens while h4–h6 shrink at every width. Those classes stay, at
their current sizes.

#### The focus ring is an outline

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

Focus rings were drawn with `box-shadow` and are now drawn with `outline`,
following upstream v6. The practical win is that an outline is **not clipped by an
ancestor's `overflow`** — the ring stays visible inside scroll containers, where a
box-shadow ring was cut off.

- **The per-component ring custom properties are gone**, not renamed. Every
  `--cui-*-focus-box-shadow` — button, pagination, accordion button, check,
  radio, switch, calendar cell and nav button, stepper indicator, range-slider
  thumb, search button, combobox, chip — had exactly one value, and the ring is
  now drawn from the global width and the theme's colour wherever it appears.
  Restyle it with `--cui-focus-ring-color` / `--cui-focus-ring-width` for the
  whole page, or set either on the component itself for one instance.

  ```diff
  - --cui-btn-focus-box-shadow: 0 0 0 .25rem rgba(88, 86, 214, .5);
  + --cui-focus-ring-color: rgba(88, 86, 214, .5);
  ```

  A runtime override written against an old name is now inert — there is no
  fallback path, because the value goes to a different property.

  `--cui-control-focus-ring` is the exception that stays: the field frame keeps
  it because a validation state writes it once and the whole family — text
  input, select, control group, date-time, OTP cell — reads it. Its value is now
  a **colour**, not an outline shorthand.
- **The Sass variables follow**: `$focus-ring-box-shadow` → `$focus-ring`, and
  the per-component ones (`$btn-focus-box-shadow`, `$pagination-focus-ring`,
  `$combobox-focus-ring`, `$form-check-input-focus-ring`, …) are removed.
- **`$focus-ring-blur` is gone**, along with `--cui-focus-ring-x`,
  `-y` and `-blur`. An outline has no blur or offset vector. **New:**
  `$focus-ring-offset` / `--cui-focus-ring-offset` (defaults to `0`), which
  pushes the ring away from the element, and `--cui-focus-ring`, the
  composite shorthand the mixin reads.
- **`focus-ring()` changed signature** to
  `focus-ring($offset: false, $color: null)`. It no longer emits `outline: 0`.
  Every ring in the library is drawn through it; with no arguments it draws the
  themed ring, and `$color` swaps the hue for one rule — which is how the
  validation states ring in red and green.
- **`--cui-focus-ring-offset` actually applies.** The mixin emits
  `outline-offset` wherever a ring is drawn, so one declaration moves every ring
  in or out. It was previously read by the `.focus-ring` helper alone, which
  made the token look supported while doing nothing on any component.
- `$pagination-focus-outline` is gone — the outline is now the ring itself.
- **A component ring is a reference to the global one, not a copy of it.** Every
  ring resolves as
  `var(--cui-focus-ring-width) solid var(--cui-theme-focus-ring, var(--cui-focus-ring-color))`,
  so setting `--cui-focus-ring-color` or `--cui-focus-ring-width` at the root
  reaches every control, and a `.theme-{color}` region tints the rings inside it.
  Previously each component baked the resolved value in at build time, which is
  why a runtime change to the global ring left the components behind.

  ```diff
  - --cui-pagination-focus-ring: .25rem solid rgba(88, 86, 214, .25);
  + /* nothing to declare — the pagination link rings from the global tokens */
  ```
- **`$input-btn-focus-color` no longer reaches the input and control rings.**
  They read the global ring now; set `$focus-ring-color` (or
  `--cui-focus-ring-color`) instead. `$input-btn-focus-width` is
  unaffected — it still sizes the validation rings and the button.

**Sizes and colours are unchanged**, so the ring keeps its width
(`$focus-ring-width`, `.25rem`) and its translucent theme colour. What changes is
the property drawing it, which also means the ring no longer participates in a
`box-shadow` transition.

#### Everything deprecated before v6 is removed

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

Some of these carried a "to be removed in v6" note since v4.2. This is v6.

**Sass mixins** — all three were already unreachable, forwarded from nothing:
`alert-variant()`, `list-group-item-variant()`, `avatar()`. The contextual classes
they used to build are generated by a Sass loop over the theme tokens instead.

**Sass variables** — `$variable-prefix` (use `$prefix`), `$border-radius-2xl` (use
`$border-radius-xxl`), `$text-muted`, `$hr-bg-color`, `$hr-height`,
`$alert-bg-scale`, `$alert-border-scale`, `$alert-color-scale`,
`$list-group-item-bg-scale`, `$list-group-item-color-scale`,
`$tooltip-arrow-color`, `$popover-arrow-color`, `$popover-arrow-outer-color`,
`$accordion-button-focus-border-color`,
`$dropdown-header-padding` (use `-padding-y` / `-padding-x`),
`$nested-kbd-font-weight`, `$btn-close-white-filter` and `$btn-close-filter-dark`,
`$high-emphasis`, `$medium-emphasis`, `$disabled`, `$high-emphasis-inverse`,
`$medium-emphasis-inverse`, `$disabled-inverse`.

Thirteen of those were already dead — nothing read them, so removing them changed
no output at all.

**CSS custom properties** — `--cui-high-emphasis`,
`--cui-medium-emphasis`, `--cui-disabled`, and the three
`-inverse` counterparts, plus `--cui-border-radius-2xl` (use
`--cui-border-radius-xxl`).

**Classes** — eleven, every one a CoreUI-only addition:

| Removed | Use instead |
| --- | --- |
| `.text-high-emphasis`, `.text-medium-emphasis` | `.text-body`, `.fg-2` |
| `.text-disabled` | `.fg-3` |
| `.text-high-emphasis-inverse`, `.text-medium-emphasis-inverse`, `.text-disabled-inverse` | `.text-white` with an opacity utility |

(The `.dark:` variants of the emphasis utilities go with them.)

**What we deliberately kept.** `.text-muted`, `.text-black-50`, `.text-white-50`
and `.navbar-light` are all deprecated, and Bootstrap v6 deletes all four. They
are Bootstrap heritage rather than CoreUI additions, and they are in the markup of
a very large number of existing projects — so they stay, at their current
rendering.

`.sidebar-brand-full`, `.sidebar-brand-narrow` and `.d-narrow-none` stay too,
though they are CoreUI's own. They are the brand pair every admin template ships
in its sidebar header, and they are exact aliases of `.d-sidebar-narrow-none` /
`.d-sidebar-narrow` — two extra selectors in a rule that already exists. Removing
them would break the most recognisable piece of CoreUI markup, silently: both
logos would render at once in the narrow state, with nothing to indicate why.
Prefer the `.d-sidebar-narrow*` names in new markup.

### Sass & CSS

- The picker shell styling is a lean partial (`_date-picker.scss`,
  ~110 lines / 16 CSS-var tokens vs v1's 369 lines / 79 Sass variables per
  picker): the shell styles only the dropdown panel, the input-group frame, the
  footer/ranges layout, and the indicator. The field is styled by the date
  input partial, the popup content by the calendar, projected footer/ranges
  content is userland (style your own buttons). **Sass overrides targeting the
  v1 input-layer classes** (`.date-picker-input`, `.date-picker-input-wrapper`,
  `.date-picker-input-preview`, `.date-picker-cleaner`, `.date-picker-separator`
  icon masks) **will not apply to the v2 markup** — those layers no longer
  exist. Overrides on the surviving classes (`.date-picker-popup`,
  `.date-picker-footer`, `.date-picker-ranges`) keep working — but the frame
  and the indicator now come from the shared primitive below.
- **The frame of every field component is
  [`.form-control-group`](/forms/form-control-group/).** Autocomplete, chip
  input, multi select, password input and all four pickers each drew their own
  copy of it before; they now share one. What this changes for you:

  | v5 | v6 |
  | --- | --- |
  | `.date-picker-input-group`, `.time-picker-input-group`, `.autocomplete-input-group`, `.form-multi-select-input-group`, the frame on `.chip-input`, the `.form-password` wrapper | `.form-control-group` |
  | `.date-picker-indicator`, `.time-picker-indicator`, `.autocomplete-indicator`, `.form-multi-select-indicator`, `.form-password-action` | `.form-control-action` |
  | `.autocomplete-cleaner`, `.form-multi-select-cleaner` | `.form-control-cleaner` |
  | `.autocomplete-input` | plain `.form-control` — the group strips its frame, so the editable needs no class of its own |
  | `.autocomplete-buttons`, `.form-multi-select-buttons` | gone: the adornments are children of the group, which lays them out |
  | `.form-multi-select-tag`, `.form-multi-select-tag-delete` | `.chip`, `.chip-remove` |
  | `.date-picker-separator` | `.form-control-icon` |
  | `.date-picker-sm/-lg`, `.time-picker-sm/-lg`, `.autocomplete-sm/-lg`, `.form-multi-select-sm/-lg` | `.form-control-sm/-lg` on the group (the components apply it from `size` themselves) |

- **Multi Select renders every selection as a Chip.** `selectionType: 'tags'`
  and `'chips'` used to be the same idea built twice, the default `'tags'`
  being a private copy of the chip without the roles chips carry. Both values
  are still accepted and now produce the same markup, so a selection is a chip
  everywhere in the library — style it through the `--cui-chip-*`
  properties. The `$form-multi-select-tag-*` variables are gone with it.

- **The per-family frame variables are gone.** `$autocomplete-font-size`,
  `$date-picker-border-color`, `$time-picker-focus-bg`,
  `$form-multi-select-padding-y` and the rest of each family's copy of the
  input look mirrored the shared frame value for value — and since the frame
  declares the `--cui-control-*` properties on itself, an override
  through them never reached it. Theme the frame once through the `$input-*`
  variables, or per instance through `--cui-control-*` on
  `.form-control-group`. Each family keeps only the variables for what is
  genuinely its own (placeholder colours, the pickers' footers, the tag row).

  Markup you write by hand has to be updated: the password input wrapper
  (`<div class="form-control-group">` with a `.form-control-action` button) and
  the chip input (`<div class="form-control-group chip-input">`). The
  components that build their own DOM do it for you.

  The adornment icons are inline SVG rendered by the component now, not CSS
  masks, so they take their colour from the button (`currentColor`) and follow
  it through hover, validation and disabled — the per-family icon, icon colour
  and icon size variables are gone with them. Every adornment across the
  library is the same mark at the same size.

  Sass overrides move with the classes. Because the group *is* the control
  frame, theming `.form-control` — or the `--cui-control-*` custom
  properties — now reaches all of these components at once, which is what the
  per-family variables were emulating. The families keep the variables for what
  they actually own (calendars, the time roll, listboxes, chips), and the ones
  that only aliased `$input-*` are gone.
- **The floating panel of every field component is the `.popup` primitive.**
  The pickers' dropdowns and the combobox listbox drew the same box three
  times; the generated panel now carries `.popup` (alongside its structural
  class), and the chrome lives in one place. Sass-wise,
  `$date-picker-dropdown-*`, `$time-picker-dropdown-*`, the chrome half of
  `$combobox-popup-*` and the per-family `-zindex` variables are replaced by
  `$popup-zindex/-bg/-border-width/-border-color/-border-radius/-box-shadow`
  and the `--cui-popup-*` custom properties — theme the popup once and
  every field component's panel follows. **The panel fades in and out**, the way
  Menu already animated: `@starting-style` supplies the state to animate from
  and a discrete `display` transition keeps it laid out through the fade, tuned
  with `--cui-popup-transition-duration` / `-timing`. Its anchored
  placement is unchanged; a fullscreen mode for mobile is designed at this
  primitive and lands separately.
- **Validation and sizing ride the standard machinery.** `.is-invalid` /
  `.is-valid` on the group behave exactly as on a `.form-control`, and the
  state also propagates from the control inside it. The per-family
  `!important` overrides that forced the invalid border in v5 are gone.
- **Markers are hidden with `list-style-type: ""`, not `list-style: none`.**
  Safari drops the `list` role — and VoiceOver stops announcing the item count —
  when a list is styled with `list-style: none`. The empty string hides the
  markers with the same visual result while keeping the list exposed to
  assistive technologies. Swept through nav, navbar, header, sidebar-nav,
  dropdown, breadcrumb and the `list-unstyled` mixin; your own `list-style: none`
  overrides still win, they just reintroduce the problem.
- **Transitions are emitted inside `prefers-reduced-motion: no-preference`.**
  The `transition()` mixin used to emit a transition and then switch it off
  again under `prefers-reduced-motion: reduce`, so every animated rule shipped
  an override block. It now emits the transition inside a `no-preference` query
  instead, which drops those blocks. The trade-off: a browser that does not
  support the media feature gets no transition at all. Rules that force
  `transition: none` stay outside the query — they disable motion on purpose,
  so they have to reach every reader.
