<Callout color="warning">
  **Work in progress.** v6 is under active development on the `v6-dev` branch —
  this page tracks every migration-relevant change as it lands, so nothing here
  is final until a v6 release ships. The **class API keeps its meaning** —
  `.btn-primary`, `.alert-success` and friends render as before. Where the Sass
  or CSS-variable surface does change, the entry below carries a
  <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span> badge.
</Callout>

## v6.0.0 (unreleased)

### Dependencies

- **New peer dependency: `@floating-ui/dom`.** The new anchored-overlay
  primitive (used by the rewritten pickers, and over time by autocomplete,
  multi-select, and dropdown) positions with [Floating UI](https://floating-ui.com)
  instead of Popper. During the transition **both** `@floating-ui/dom` and
  `@popperjs/core` are peer dependencies — components not yet migrated keep
  using Popper. Bundle builds (`coreui.bundle.*`) include both engines, so no
  action is needed for CDN users; npm users installing peer dependencies
  manually should add `@floating-ui/dom`.

### Components

#### Calendar

- **Behavior change:** `update()` now **merges** the given options over the
  current configuration instead of resolving them against the defaults. A
  partial call like `calendar.update({ selectEndDate: true })` no longer resets
  every other option (`range`, `calendars`, `locale`, …) — this aligns
  `Calendar.update()` with `DateInput`/`TimeInput`/`DateTimeInput` `update()`
  semantics. Callers that passed the complete configuration on every update are
  unaffected.
- **Additive:** `startDateChange` and `endDateChange` now carry a `dateObject`
  property with the underlying `Date`, alongside the existing `date` property.
  `date` remains formatted per `selectionType` — a `Date` for day selection, but
  a string for week (`"2026W27"`), month (`"2026-01"`), quarter (`"2026Q1"`) and
  year (`"2026"`). Existing listeners are unaffected.

#### Date Picker v2 / Date Range Picker v2 (preview)

The pickers are being rewritten as a composition of the section-based input
fields ([date input](/forms/date-input/)), the [calendar](/components/calendar/),
and a shared popup primitive — replacing the v1 monolith. Preview pages:
[date picker v2](/forms/date-picker-v2/),
[date range picker v2](/forms/date-range-picker-v2/). The v2 shells currently
ship **alongside** the v1 pickers under new names; at release the rewrite takes
over the existing `DatePicker`/`DateRangePicker` names, and this section becomes
the option-by-option migration map. Planned mapping:

- **Removed — projected regions replace button configuration.** `footer`,
  `todayButton`, `todayButtonClasses`, `cancelButton`, `cancelButtonClasses`,
  `confirmButton`, `confirmButtonClasses`, `ranges`, `rangesButtonsClasses` →
  put a `<template data-coreui-template="footer">` /
  `data-coreui-template="ranges"` child in the picker element. Zero-argument
  actions bind with `data-coreui-picker-action="today|clear|reset|close"`;
  actions with arguments (range presets) go through `picker.getContext()`
  (`setDate`, `setRange`, `clear`, `reset`, `close` + read-only state).
- **Removed — obsolete with section fields.** `inputDateFormat`,
  `inputOnChangeDelay`, `inputReadOnly`, `placeholder` — the masked field is
  always a valid partial date; there is no free-text parsing to debounce.
  Section placeholders come from the input triad's `placeholders`.
- **Changed.** `timepicker: true` is replaced by the standalone
  [date time picker](/forms/date-time-picker-v2/) — a DateTimeInput field with a
  calendar and the time selection body side by side. Because the two halves own
  different parts of one value, that picker does not auto-close: picking a day
  keeps the time and picking a time keeps the day.
- **Kept.** Calendar passthrough (`locale`, `minDate`/`maxDate`,
  `disabledDates`, `selectionType`, `showWeekNumber`, custom cell renderers, …),
  `container`, `startDate`/`endDate`/`date`, `startName`/`endName`/`name`,
  `size`, validation states, the data API
  (`data-coreui-toggle="date-picker-v2"`), and the imperative API
  (`show`/`hide`/`toggle`/`clear`/`reset`).
- **Passthrough is by name.** Options that belong to the inner calendar or date
  input are forwarded automatically, so `data-coreui-selection-type`,
  `data-coreui-show-week-number` and `data-coreui-format` work on the picker
  element. `calendarOptions` / `inputOptions` remain as the programmatic escape
  hatch.
- **Week and quarter selection display the underlying date.** A section mask is
  built from date sections, so it cannot render `2026W27` or `2026Q1` the way
  the v1 text input did — the field shows the first day of the selected week or
  quarter. The formatted value stays available on the event (`event.date`).
  Dedicated week/quarter sections are an open design item. Month and year
  selection **do** adapt: the mask narrows to `MM/yyyy` and `yyyy`.
- **Format comes from the mask.** `inputDateFormat` is replaced by `format`
  (forwarded to the field); `inputDateParse` still applies to pasted text.
- **The calendar is built on first open, not at construction.** It accounts for
  ~83% of a date picker's DOM (and ~89% of a range picker's), and it is not
  observable before the popup opens, so the shells create it in `show()` and
  seed it from the field values. Measured over 20 pickers: date picker
  **65 ms → 15 ms** and **3200 → 540** DOM nodes, range picker **93 ms → 12 ms**
  and **6060 → 740** nodes. The first open costs a few milliseconds more (the
  calendar is built then); later opens are unchanged. Code reaching into the
  private `picker._calendar` before the first open now finds `null`.

#### Date Input / Time Input / Date Time Input

- **RTL keyboard navigation now follows the visual direction in nested RTL
  contexts.** Arrow keys (and `Home`/`End`) mirror when the field renders
  right-to-left; the direction is read from the element's computed style
  instead of `document.documentElement.dir`, so a `dir="rtl"` ancestor works
  and not only a document-level direction.

#### Time Picker v2 / Date Time Picker v2 (preview)

- The time selection body is now a shared primitive used by both pickers, so the
  `roll` and `select` variants, the `hours`/`minutes`/`seconds` filters and the
  12/24-hour locale split behave identically in each. Preview pages:
  [time picker v2](/forms/time-picker-v2/),
  [date time picker v2](/forms/date-time-picker-v2/).
- Same removals as the date pickers: `footer`/`cancelButton`/`confirmButton` and
  their class options give way to a projected
  `<template data-coreui-template="footer">` with
  `data-coreui-picker-action="now|clear|reset|close"`; `inputReadOnly`,
  `inputOnChangeDelay` and `placeholder` are obsolete with a section field.
- **`reset()` restores the value the picker was constructed with.** In v2 the
  shell remembers it: setting a value goes through the field's `update()`, which
  rewrites the field's own configuration, so the field can no longer restore the
  original on its own.

#### Icons rendered by JavaScript

- New components render their icons as **inline SVG on `currentColor`** (the
  chips pattern) instead of CSS `mask` data-URIs: swap them with the
  `indicatorIcon` / `separatorIcon` options (sanitized with the SVG allowlist),
  recolor them with plain CSS `color`. The corresponding
  `$date-picker-*-icon`/`-icon-size` Sass variables disappear with the v1
  shells.
- **The calendar navigation icons moved to JavaScript too.** The four
  `$calendar-nav-icon-{prev,next,double-prev,double-next}` Sass variables are
  **removed**, along with the CSS custom properties and mask rules that painted
  them. Customize them with the new `navIconPrev` / `navIconNext` /
  `navIconDoublePrev` / `navIconDoubleNext` calendar options instead (inline SVG,
  sanitized). `$calendar-nav-icon-width/-height/-color/-hover-color` stay — the
  icon inherits `color`, so recoloring is plain CSS.
- **`Calendar`'s default `allowList` is now `SVGAllowlist`** (was
  `DefaultAllowlist`), so the component can render its own inline SVG icons —
  and custom cell renderers may return SVG as well. Strictly more permissive;
  scripts and event handlers are still stripped.
- **Directional icons are resolved in JavaScript, not CSS.** v1 swapped the
  range separator with a second Sass variable
  (`$date-picker-separator-icon-rtl`) applied through an RTL mask; v2 picks
  between `separatorIcon` and `separatorIconRtl` when it renders, based on the
  element's computed direction — so a `dir="rtl"` ancestor works, not just a
  document-level direction. The calendar mirrors its prev/next icons the same
  way. **Consequence for custom code:** a component that resolves directional
  icons at construction time must be in its final DOM position when it is
  created — a detached element has no computed direction (the calendar falls
  back to the nearest `[dir]` ancestor, but placement first is the reliable
  path).

### Sass architecture & design tokens

v6 adopts the Bootstrap v6 SCSS architecture: CSS cascade layers, per-component
design-token maps, one shared styling surface for every text control, and
runtime color math in place of precompiled shades. Sass variables remain the
primary customization API — every component knob still works through
`@use ... with()` — but several things below are breaking and are called out
as such.

#### Colour decisions are written, not computed

v6 stops evaluating colours at build time, the way upstream v6 does — Sass
assembles maps of CSS expressions and the browser resolves them.

- **`$theme-colors-contrast` holds written values** instead of
  `color-contrast()` results. The computed and written values are identical, so
  nothing renders differently; the point is that a theme colour no longer has to
  be a Sass colour for the contrast pass to run over it. Upstream keeps a
  `"contrast"` key per colour and never calls the function either.
- **Table variants read the theme tokens.**
  <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  `.table-primary` and friends still exist, but they are generated the way
  `.btn-primary` is: the class sets `--#{$prefix}theme-*` and the base `.table`
  rules read it. `$table-variants` is now a **list of colour names**, not a map
  of pre-shifted colours, and `$table-bg-scale` / `$table-border-factor` are
  gone. A theme colour you add yourself now gets a table variant without
  compiling Sass.
  Two visible consequences: the variant background is the colour's
  `bg-subtle` token rather than a `shift-color()` of the base, and striped /
  hover / active are `color-mix()` overlays on the text colour rather than
  opaque mixes — so they compose over the row's own background. Table variants
  also follow colour modes now, where before they stayed on light-palette
  values in dark mode.

#### RGB channel tokens and the elevation system removed

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

- **Every `--#{$prefix}{name}-rgb` custom property is gone**, along with the
  `$theme-colors-rgb` and `$theme-colors-rgb-dark` maps, the `to-rgb()`
  function's role in `:root`, and the `rgba-css-var()` helper (now
  `translucent-css-var()`). They existed only so
  `rgba(var(--cui-primary-rgb), .5)` could apply an alpha to a token; that is
  what `color-mix()` does directly:

  ```diff
  - background-color: rgba(var(--cui-primary-rgb), .5);
  + background-color: color-mix(in srgb, var(--cui-primary) 50%, transparent);
  ```

  Upstream v6 carries no rgb triplets either. The opacity utilities
  (`.text-opacity-50`, `.bg-opacity-25`, `.link-opacity-75`) are unchanged —
  they now scale the token through `calc(var(--cui-bg-opacity) * 100%)`.
- **The elevation system is gone**: `$elevations`, `$enable-elevations`,
  `$elevation-base-color`, the `elevation()` mixin and the `.elevation-*`
  utilities. It was disabled by default (`$enable-elevations: false`), so the
  utilities were the only reachable part. Use the shadow utilities
  (`.shadow`, `.shadow-sm`, `.shadow-lg`) or set `box-shadow` directly.
- **Button focus rings take a colour, not channels.**
  `--#{$prefix}btn-focus-shadow-rgb` becomes
  `--#{$prefix}btn-focus-shadow`, and the Sass variables follow:
  `$btn-outline-focus-shadow-rgb` → `$btn-outline-focus-shadow`, likewise for
  the ghost and link variants.

#### Theme gradients removed

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

- **`.bg-{color}-gradient` and `.text-bg-{color}-gradient` are gone**, along
  with the `$theme-gradients` / `$theme-gradients-dark` maps that generated
  them, the per-colour `$primary-gradient` … `$dark-gradient` variables (and
  their `-dark` twins), and the `--cui-{color}-start` / `--cui-{color}-stop`
  custom properties they read. These were CoreUI-only additions with no Bootstrap counterpart.
  Replace a removed class with the base colour plus the generic gradient —
  `class="bg-primary bg-gradient"` — or write the two-stop gradient yourself if
  you need the exact 45° ramp.
- **`.bg-gradient` itself stays**, as do `$gradient`, `--cui-gradient`,
  `$enable-gradients` and the `gradient-bg()` mixin — that is the gradient
  system Bootstrap has, and components keep using it.

#### Cascade layers

- **All library CSS now lives in cascade layers**, declared as
  `@layer root, reboot, layout, content, forms, components, custom, helpers, utilities;`.
  The `custom` layer is empty and reserved for you: put your own layered styles
  there to slot between the library's components and helpers.
- **Unlayered CSS wins over layered CSS regardless of specificity**, so your
  existing stylesheets now override the library more easily, not less. No
  action needed — selectors that worked before keep working, and low-specificity
  overrides that used to lose on specificity now win.
- If your build concatenates CoreUI with other CSS, make sure the layer
  declaration (emitted at the top of the bundle) is not stripped by a minifier
  that predates `@layer`.

#### Design-token maps

- **Every component that emits CSS custom properties now builds them from a
  `$<component>-tokens` Sass map** merged over your overrides with the new
  `defaults()` function. Override the whole surface at once:

  ```scss
  @use "@coreui/coreui-pro/scss/coreui" with (
    $alert-tokens: (
      --cui-alert-bg: hotpink,
      --cui-alert-margin-bottom: null, // null removes the token entirely
    )
  );
  ```

  Classic per-variable overrides (`$alert-padding-y: 2rem`) keep working — the
  map defaults are built from the same Sass variables.
- **Component Sass variables moved from `_variables.scss` into their component
  partials.** `@use ... with()` is unaffected — the entry point forwards every
  module — but if you imported `scss/_variables.scss` directly for its
  definitions, component blocks are no longer there.
- Two silent duplicates were dropped along the way: `$nav-link-height` was
  declared twice (navbar and header blocks — the header copy is gone) and the
  calendar emitted `--cui-calendar-cell-week-number-color` twice.

#### Theme tokens

- New `--cui-theme-*` indirection plus generated `.theme-primary` …
  `.theme-dark` classes: a themed container sets `--cui-theme-fg`,
  `--cui-theme-bg-subtle`, `--cui-theme-border`, and token-driven components
  (alert, buttons) read them. Contextual classes like `.alert-success` are now
  implemented through these tokens — same rendering, new mechanics.
- **`--cui-{color}-contrast` custom properties are new root tokens.** Previously
  only buttons computed their own contrast colour; the root tokens now carry it,
  written in `$theme-colors-contrast`. `.text-bg-*` reads the token instead of
  calling `color-contrast()`.

#### Colour scales, and `_variables-dark.scss` removed

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

Dark mode no longer has a second set of Sass variables. Every colour is declared
once, as a native
[`light-dark()`](https://developer.mozilla.org/en-US/docs/Web/CSS/color_value/light-dark)
pair, and `[data#{$data-infix}theme="dark"]` only declares `color-scheme: dark`.

- **`scss/_variables-dark.scss` is gone.** All 59 `$*-dark` variables it held are
  gone with it; do not `@import "variables-dark"` any more. The values live
  inline in the light variable:

  ```diff
  - $body-color:      rgba(shift-color($gray-base, +26%), .95);
  - $body-color-dark: rgba($white, .87); // in _variables-dark.scss
  + $body-color:      light-dark(rgba(shift-color($gray-base, +26%), .95), rgba($white, .87));
  ```

  Two exceptions remain, because `light-dark()` resolves to a `<color>` and these
  are not colours: `$body-bg-dark` and `$body-tertiary-bg-dark` still exist (the
  `color-translucent()` helper has to run in Sass), and the colours baked into the
  select chevron and switch knob SVGs keep a dark counterpart next to their
  component (`$form-select-indicator-dark`, `$form-switch-bg-image-dark`).
- **Every theme colour gets a 100–900 scale of tokens in `:root`**, mixed at
  runtime from the colour's own token: `--#{$prefix}primary-100` …
  `--#{$prefix}primary-900`, for each key of `$theme-colors`. Knobs:
  `$color-tints`, `$color-shades`, `$color-mix-space` (`lab`), `$tint-color`,
  `$shade-color`. Override `$primary` — or the `--#{$prefix}primary` token at
  runtime — and the whole family retints.
- **`-bg-subtle`, `-border-subtle` and `-text-emphasis` are pairs of those
  stops** rather than hand-picked hexes:

  ```scss
  $primary-bg-subtle:     light-dark(var(--cui-primary-100), var(--cui-primary-900));
  $primary-border-subtle: light-dark(var(--cui-primary-300), var(--cui-primary-600));
  $primary-text-emphasis: light-dark(var(--cui-primary-800), var(--cui-primary-200));
  ```

  **This fixes a real dark-mode bug.** Only `light` and `dark` had genuine dark
  variants before; for the six chromatic colours `$primary-bg-subtle-dark` was an
  alias of the light value, so `.alert-success`, `.list-group-item-info` and
  `.table-warning` rendered a pale light-mode surface in dark mode. They now
  darken. Light mode shifts slightly too: subtle backgrounds are a shade lighter
  (an 80% tint rather than ~70%) and emphasis text a shade darker; borders are
  unchanged for practical purposes. Emphasis-on-subtle contrast improves in every
  colour — the weakest pair goes from 6.03:1 to 7.57:1.
- **The dark grey palette is gone**: `$gray-100-dark` … `$gray-900-dark` and the
  `$grays-dark` map. Every one of them was defined as exactly its light
  counterpart, so they generated nothing — read `$gray-*` directly. The bundled
  Bootstrap theme no longer passes `$grays-dark: ()` through its `with()` block.
- **`$theme-colors-dark` is gone**, along with `$theme-colors-text-dark`,
  `$theme-colors-bg-subtle-dark`, `$theme-colors-border-subtle-dark` and
  `$theme-colors-contrast-dark`, and the eight `$primary-dark` … `$dark-dark`
  variables behind them. Theme colours themselves no longer change
  between colour modes — the old dark variants were a 10% desaturation, which
  upstream does not do either. Consequence: the eight
  `[data#{$data-infix}theme="dark"] .text-bg-*` overrides are gone.
- **The `--#{$prefix}{name}-dark` root tokens are gone**
  (`--#{$prefix}body-color-dark`, `--#{$prefix}body-bg-dark`,
  `--#{$prefix}emphasis-color-dark`, `--#{$prefix}secondary-color-dark`,
  `--#{$prefix}secondary-bg-dark`, `--#{$prefix}tertiary-color-dark`,
  `--#{$prefix}tertiary-bg-dark`). They existed so a component could pin the dark
  palette while the page stayed light; declare `color-scheme: dark` instead and
  the `light-dark()` pairs follow — which is exactly what `.sidebar-dark` now
  does, having dropped its eight token overrides.
- **`$link-shade-percentage` no longer drives `$link-hover-color`**, which is now
  `light-dark(var(--#{$prefix}primary-600), var(--#{$prefix}primary-400))`. The
  variable still exists and still drives the `.link-*-*` hover helpers.
- **Two dead table knobs were removed**: `$table-th-font-weight` and
  `$table-caption-color`. Reboot owns those declarations, so use `$th-font-weight`
  and `$caption-color`.
- Setting `$enable-dark-mode: false` still yields a light-only page: `:root`
  declares `color-scheme: light` and nothing ever declares `dark`, so every
  `light-dark()` pair resolves to its light side.

#### Component icons render through CSS masks

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

The accordion chevron and the carousel arrows were `background-image` SVGs with
the colour written inside the markup, which is why each needed a dark-mode rule —
the accordion swapped in a second SVG, the carousel inverted the first with a
`filter`. They are now painted through a CSS `mask`, so the colour lives on
`background-color` as an ordinary token and follows the root colours by itself.
Upstream v6 does the same, with a `mask-icon()` mixin.

- **The accordion's two icons collapse into one.**
  `$accordion-button-active-icon` and the `--#{$prefix}accordion-btn-active-icon`
  custom property are **removed**; the active state changes
  `--#{$prefix}accordion-btn-active-icon-color` instead of the whole image. New
  tokens: `--#{$prefix}accordion-btn-icon-color` and
  `--#{$prefix}accordion-btn-active-icon-color`.
- **A custom icon is now a shape, not a coloured image.** Whatever colour you put
  inside `$accordion-button-icon` or `$carousel-control-prev-icon-bg` /
  `$carousel-control-next-icon-bg` is ignored — only the alpha of the SVG is used.
  Set the colour through the token (`--#{$prefix}accordion-btn-icon-color`,
  `--#{$prefix}carousel-control-color`).
- **`$accordion-icon-color` and `$accordion-icon-active-color` are `var()`
  references now** (`var(--#{$prefix}body-color)`,
  `var(--#{$prefix}primary-text-emphasis)`), not Sass colours — Sass colour
  functions on them no longer work.
- **`$carousel-control-icon-filter` is removed**, with its
  `--#{$prefix}carousel-control-icon-filter` custom property and its two dark
  companions (`$carousel-control-icon-filter-dark`,
  `$carousel-dark-control-icon-filter`), along with the four accordion
  dark variables (`$accordion-icon-color-dark`,
  `$accordion-icon-active-color-dark`, `$accordion-button-icon-dark`,
  `$accordion-button-active-icon-dark`). The accordion's dark-mode block is gone
  entirely.
- **The carousel's colours are tokens.** `--#{$prefix}carousel-control-color` is
  new; `.carousel-dark` pins the dark side of each pair through
  `$carousel-dark-control-color`, `$carousel-dark-indicator-active-bg` and
  `$carousel-dark-caption-color` (previously `$carousel-*-dark` in
  `_variables-dark.scss`). RTL still swaps the two arrows, now through
  `mask-image`.
- **Visible in dark mode**: the old dark accordion chevron was a *filled* glyph
  where the light one was *stroked*. Both modes now use the stroked shape — same
  colour, same size, slightly different drawing. Worth knowing if you diff
  screenshots.

#### Buttons

- **`button-variant()` changed signature** — it takes a variant name from the
  new `$button-variants` map (`"solid"`, `"outline"`, `"ghost"`) instead of a
  color pair, and reads the theme tokens.
  <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  `button-outline-variant()` and `button-ghost-variant()` mixins are **removed**
  (replaced by map entries), and `scss/mixins/_buttons.scss` no longer exists —
  the variant and size mixins live in `scss/_buttons.scss`.
- **Hover and active shades are computed in CSS** with
  `oklch(from var(--cui-theme-base) calc(l * …) c h)` instead of precompiled
  `shade-color()`/`tint-color()`. Shades shift slightly (measured 8–23 per RGB
  channel); `.btn-dark` keeps brightening on hover via the
  `$btn-lightness-overrides` map. The win: a theme color you add yourself gets
  correct hover/active states without compiling Sass.
- **The eight shade/tint amount knobs are removed**:
  `$btn-hover-bg-shade-amount`, `$btn-hover-bg-tint-amount`,
  `$btn-hover-border-shade-amount`, `$btn-hover-border-tint-amount` and the four
  `$btn-active-*` counterparts. They fed the Sass mixes that no longer happen.
  The runtime equivalents are `$btn-hover-lightness`, `$btn-active-lightness` and
  the per-colour `$btn-lightness-overrides` map.
- **The dark-mode button block is gone** (~160 lines of CSS) — variants follow
  the root color tokens, which already switch in dark mode.
- `.btn-primary`, `.btn-outline-*`, `.btn-ghost-*` class APIs are unchanged.

#### RFS removed

<span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>

- **The RFS engine is gone** — no `vendor/rfs`, no `font-size()` / `rfs()`
  mixins, no `$enable-rfs`, no `rfs` option in the utilities API, and none of
  the `$rfs-*` knobs (`$rfs-base-value`, `$rfs-breakpoint`, `$rfs-factor`,
  `$rfs-mode`, `$rfs-unit`, `$rfs-two-dimensional`, `$rfs-class`, …). Fluid type is
  written as literal `clamp()` values in `$h1-font-size`–`$h4-font-size`,
  `$display-font-sizes` and `$legend-font-size`; rendering is unchanged at
  every viewport width.
- **Headings no longer derive from `$font-size-base`** — a `clamp()` cannot be
  multiplied. Override the `$h*-font-size` variables directly.
- A temporary `scss/vendor/_rfs.scss` shim (pass-through `font-size()`/`rfs()`
  mixins) exists only for the docs engine and will be removed — do not depend
  on it.

#### One styling surface for all text controls

- **Shared root knobs**: `:root` now carries the control frame
  (`--cui-btn-input-padding-y/-x`, `-font-family/-size`, `-line-height`,
  `-border-width`, `-transition`, `-color`, `-bg`, `-disabled-opacity`, plus
  `-sm-*`/`-lg-*` size sets) and the selection state
  (`--cui-control-checked-bg/-border-color`,
  `--cui-control-indeterminate-bg/-border-color`). Restyle these once and
  every control follows: inputs, selects, checks, switches, OTP, chip input,
  autocomplete, multi select, and the pickers — including the checkbox-style
  option indicators inside autocomplete and multi select.
- **Every text control consumes per-element `--cui-control-*` tokens**
  (padding, font, colors, border, radius, shadows, focus and disabled sets)
  that default to those knobs. Override a single control on its element;
  override everything at `:root`.
  <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  The component-namespace custom properties that duplicated this frame are
  **renamed**: `--cui-autocomplete-padding-y`, `--cui-date-picker-font-size`,
  `--cui-time-picker-bg`, `--cui-form-multi-select-border-color`,
  `--cui-chip-input-padding-x` and the rest of their frame sets are now
  `--cui-control-*` on the same elements. Runtime overrides written against
  the old names must be updated. Component-specific tokens (indicators,
  dropdowns, tags, cells, cleaner buttons) keep their names.
- **Component Sass variables survive with new defaults**: `$date-picker-bg`,
  `$autocomplete-padding-y` and the rest now default to the shared knob
  (`var(--cui-btn-input-bg)` …). Untouched, the control follows the shared
  surface; overridden through `with()`, it detaches just that control —
  exactly what reaching for a component knob means.
- **The select's indicator geometry is computed at runtime.**
  `$form-select-indicator-padding` and `$form-select-feedback-icon-padding-end`
  are now `calc()` expressions over `var(--cui-control-padding-x)` instead of
  Sass products, and `$form-select-bg-position` carries the `var()` inside it
  (the RTL build still flips the `right`/`left` keyword at compile time).
  <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  Sass arithmetic on these variables in your own stylesheets no longer works —
  they are CSS calc strings now, not numbers. Override them with your own
  `calc()` or a plain length instead.
- **Form tooltips reuse the tooltip's runtime tokens.** Add the `.tooltip`
  class to a feedback tooltip (`class="tooltip invalid-tooltip"`) and it
  follows tooltip theming — `--cui-tooltip-padding-*`, `-font-size`,
  `-border-radius` — the upstream v6 contract. Bare `.invalid-tooltip` markup
  keeps rendering exactly as before through built-in fallbacks.
  <span class="badge text-danger-emphasis bg-danger-subtle">Breaking</span>
  The Sass-level derivation is gone: `$form-feedback-tooltip-*` no longer
  default to `$tooltip-*`, so overriding `$tooltip-padding-y` alone no longer
  moves feedback tooltips at compile time — use the runtime link (add the
  class) or set `$form-feedback-tooltip-*` explicitly. The tooltip variables
  moved to `scss/_tooltip.scss`, the feedback set to `scss/mixins/_forms.scss`.
- **Validation composes through the tokens**: `.is-invalid` / `.is-valid` set
  `--cui-control-border-color`, `-focus-border-color` and `-focus-box-shadow`
  instead of restating declarations, so state styling follows any control
  automatically.

### Sass & CSS

- The v2 picker shell styling is a lean partial (`_date-picker-v2.scss`,
  ~110 lines / 16 CSS-var tokens vs v1's 369 lines / 79 Sass variables per
  picker): the shell styles only the dropdown panel, the input-group frame, the
  footer/ranges layout, and the indicator. The field is styled by the date
  input partial, the popup content by the calendar, projected footer/ranges
  content is userland (style your own buttons). **Sass overrides targeting the
  v1 input-layer classes** (`.date-picker-input`, `.date-picker-input-wrapper`,
  `.date-picker-input-preview`, `.date-picker-cleaner`, `.date-picker-separator`
  icon masks) **will not apply to the v2 markup** — those layers no longer
  exist. Overrides on the surviving classes (`.date-picker-dropdown`,
  `.date-picker-footer`, `.date-picker-indicator`, `.date-picker-ranges`) keep
  working.
- In v2 the **input group carries the form-control frame** (border, background,
  focus ring); the section fields inside are borderless. In v1 the frame was on
  the group as well, but the inner fake-inputs had their own styling hooks —
  those are gone.
